# 主要聊天与派活（agent_invoke / chat_start）

## 背景

主要聊天模式把 WebClient 收成「一个主窗口」：导航里突出当前主聊天，隐藏「新建」。用户侧体验是只有一个对话入口。

平台侧执行规则没有跟着变：一个聊天同一时刻只能有一个 Run。主聊天一旦在跑长任务，后续输入只能走插话（steer），要等当前模型调用或工具步骤结束才被看到；卡在审批时直接 409。

同时存在两套「派给别的智能体干活」的能力：

- **`agent_invoke`**：同步子任务，最多 5 个并发；主 Run 会一直等到全部结束；子任务结果整段塞回主上下文。
- **`chat_start`**（`builtin.task-control`）：在目标 Agent 的会话里异步起 Run；可用 `wait` / `chat_get_status` 取结果；固定一层（`callerOrigin` → `run_chaining_not_allowed`）；目标忙则 `active_run_conflict`，无排队。

两者都能「调度别人」，但同步/异步、自我调用、错误码、返回值、文档与前端呈现都不一致。站内信规划、Kanban、云端 Job 提案又是另外几套派活叙事，尚未对齐。

问题不是「两个工具能不能共存」，而是：在「用户只有一个主窗口」的前提下，主智能体如何一边把活派出去，一边继续接用户指令，让用户感觉可以同时派多件事。

## 现状要点

### 主要聊天

- 指针落盘为 `chat-primary.json`；`PUT /api/chats/primary` 设置；忙时切换返回 `primary_chat_busy`。
- 执行层没有「主聊天专用」的并发或队列规则，仍是「一聊天一 Run」。
- 主要模式下，`chat_start` 派出去的会话通常归入历史/非主导航，用户不易发现，子会话里的审批也难从主窗口处理。

### agent_invoke

- 适合短、要立刻用结果的内联子任务。
- 会占用主聊天的 Run 整段时间；任一子任务等审批，主聊天整条链路卡住。
- 结果进主上下文，长输出会挤压上下文窗口。

### chat_start

- 适合后台派活，主 Run 可以先结束。
- 缺口：发送方 Run 结束后结果难自动回传；固定一层；忙则拒；发起方信息偏内存；与主要聊天导航未打通。

### 相关规划

- `plans/mailbox.md`：会话投递 / 收件箱 / 中途信与最终回信 / 跳数限制。
- activity 事件：过程类展示（非思考全文），可作任务进度来源。
- Kanban、云端 Job：任务表叙事，与「派活记录」可能是同一张表的不同面。

## 需要讲清楚的张力

1. **窗口唯一 vs 执行串行**  
   UI 收成一个主窗口后，若执行仍是「主聊天一 Run」，长任务会把用户堵在插话通道里，无法真正「派很多活」。

2. **同步派活 vs 异步派活**  
   `agent_invoke` 堵主 Run；`chat_start` 不堵，但回传与可见性不足。两套并存时，模型缺少「该用哪个」的清晰边界。

3. **结果放哪**  
   全塞进主聊天上下文会膨胀；全留在子会话则主窗口「看不见进展」；摘要 + 卡片 + 可点进详情是中间形态，落点未定。

4. **一聊天一 Run 是否能动**  
   落盘、历史重建、压缩、前端单流都建立在该假设上。若允许多 Run 同聊天并发，影响面大；若坚持单 Run，则「主聊天当调度中枢」依赖异步派活 + 回调/通知，而不是主聊天自己并行跑多个 Run。

5. **派活方式数量**  
   invoke、chat_start、站内信、Kanban、云端 Job……若不收敛叙事，工具与产品概念会继续分叉。

## 可讨论的形态（不定稿）

以下只列形态，不选定：

**A. 主聊天只做调度**  
派活全部走后台会话；主 Run 很短；结果以回调 Run、通知或任务托盘呈现。

**B. 主聊天自己也可干长活**  
长任务仍占主 Run；派活与长活如何交错（插话、排队、禁止）需另定规则。

**C. 主聊天允许多 Run 或运行中插入新指令**  
打破或软化「一聊天一 Run」；工程与产品成本最高。

**D. 主聊天当总览，每件活是可点进的子会话**  
导航上把派出去的会话挂在主聊天/主 Agent 下；审批与详情在子会话或主窗口内嵌卡片。

**E. 任务托盘**  
主窗口旁（或内）列出排队中 / 运行中 / 等待输入 / 成功 / 失败；进度可接 activity；与 Kanban / Job 是否同一数据源待定。

派活入口如何收敛也待定，例如：

- 异步派活统一走 `chat_start` + 完成回调（站内信收件箱作底座），或单独 `agent_message_send`；
- `agent_invoke` 收窄为短时内联；
- 或最终合成一张运行时任务表，多个入口只是写表的不同 API。

## 待拍板 / 待澄清

1. 主聊天默认只调度，还是也可以自己跑长任务？
2. 派出去的活放在哪：独立可见聊天、隐藏子会话，还是挂在主聊天下？
3. 结果回来时：自动起回调 Run 汇总，只发通知，还是等用户再问？
4. 「派给自己的分身」是否作为默认派活方式？
5. 被派出去的活能否再往下派？最大跳数？与现有「固定一层」如何衔接？
6. `primary_chat_busy` 是否保留？是否支持「设为主聊天」「主要模式下新开」？
7. 审批集中在主聊天处理，还是必须进入子会话？
8. 任务表、Kanban、云端 Job、站内信记录是否合成一套？
9. 主聊天忙时，Automation / 外部渠道指向它：拒绝、排队，还是改投别处？
10. Desktop 与 WebClient 在主要模式下的呈现是否一致？
