# 主要聊天：长上下文、回放上限与聊天文件切换

评估讨论汇集稿（Platform + WebClient 前端结论）。不写工作量。与 [mailbox-next.md](mailbox-next.md) 交叉；本文件只管「主 Chat 永不结束」时的**模型上下文、存储/JSONL、人可读历史上翻**，不替代 mailbox 收件/出队合同。

前端实现由 WebClient 自行推进；本文件记录已对齐的现状、产品意向与待拍板，便于前后端契约一次拍清。

---

## 要解决的问题

1. 主要聊天模式下，主 Chat 逻辑上可长期不结束；模型上下文会爆窗，人侧时间线也会在刷新/回放时被一次拉爆。
2. 今天一 Chat 一 JSONL 无限 append；压缩不删原文，磁盘与全量 replay 仍随时间变重。
3. 用户期望：持续聊下去**无感**；仍能**向上翻**看一些历史；但不能假装无限回放。
4. 需要把「给模型的窗」「给人看的窗」「磁盘上的文件」三层拆开，避免绑成同一个开关。

---

## 现状（已核对）

### Platform

- **Compact 已有较完整合同**（见 docs/API与协议、会话存储与回放）：
  - **L1（`l1_tools`）**：不调模型；原 JSONL 行打 `_compact`，清旧 reasoning/完整工具组；不改原文、不新增 L1 正文行。
  - **L2（`summary`）**：调摘要模型；写独立 `compact.checkpoint`；被覆盖行标出逻辑上下文。
  - **自动**：完整请求约达窗口 90% 先 L1，仍高于约 60% 则同周期升 L2；失败有 `context_compact_failed` / `context_window_uncompactable` 等。
  - 活动 Run 在安全点执行；与 query 有 `compact_in_progress` 冲突语义。
- **存储**：`<chatId>.jsonl` append；逻辑视图（LLM history / 标准 replay）跳过已压段；原文与审计仍在盘上；有 `.compact-backups`。
- **缺口**：没有「主 Chat 滚动切换聊天文件、只迁正文」的一等能力；没有面向 UI 的 **Chat 级事件分页**（`beforeSeq` / `hasMore` 一类）作为稳定产品合同。
- **Mailbox / 主要聊天**（见 mailbox-next）：mail 常开，mail.db 每次启动清空；用户消息在阶段 5 改走 mailbox，主要聊天的出队策略待定。邮箱队列短命，**不解决** JSONL 长历史问题。

### WebClient（WebClient 评估，本地约 `2084eba9` / v0.5.27；远端亦未见事件分页）

- 历史：`GET /api/chat` **一次全量** `events[]` 进内存（persisted stream replay boundary）；JSONL 仅 Debug。
- UI：Virtuoso 虚拟滚**已加载**项 + Chat 切换书签；**无** `startReached` / prepend / 上滚分页；`timelineNodes` 无窗口上限。
- Live：先整段 replay，再按 **run 内** `activeRun.lastSeq` attach；主 Chat **无** seq gap 检测（Preview/Surface 有）；丢游标 → `seq_expired` / `replay_required` **整段重读**。
- 已读水位：`readRunId` / `lastRunId`，不是事件 seq。
- 已有 Primary、mailbox、`context.compact` 系统气泡；压缩不删原文；**无**分段边界 / 「上滚再拉原文」契约。
- 空闲 Chat 的 WS 重连**不**自动 `loadChat`。

**对齐结论：** 现有能力主要防**模型爆窗**；防**无限主 Chat 的回放/前端内存**必须新增 Chat 级窗口 API + 前端上滚分页；切文件是压缩之后的后手。

## 产品意向（Frank 已表达，尚未全部拍板数值）

1. **用户无感持续聊**：输入与续聊不因「文件策略」打断；上翻不是无限假装。
2. **上翻有硬顶**：例如只能翻到约一个月前，或只能向上约 **200 条**（主要聊天 200 条已很多）；具体用条数、轮数还是时间，或两者取紧 → 待拍板。
3. **先压缩，再切文件**：
   - 主聊天文件上下文不够时，**优先走现有/加强的压缩**（L1→L2）。
   - **实在太长**后再做**聊天文件切换**：留下的迁到新聊天文件的主要是**内容（正文）**，**不带工具**；大约把近 **200 条**量级带进新文件继续聊。
4. WebClient 前端刷新/上滚由 WebClient 侧方案自行推进；Platform 需提供可分页、带上限的回放契约，并与压缩/切文件边界对齐。

## 分层（评估用）

| 层 | 含义 | 意向手段 |
|---|---|---|
| 模型上下文 | 每次 Run 送进 LLM 的内容 | 先 L1/L2；主 Chat 低思考、重活进分身，减少主时间线工具垃圾 |
| 人可读历史 | 页面能往上翻的范围 | 首屏尾窗 + 上滚分页 + **硬顶**（条数/时间） |
| 磁盘文件 | JSONL 物理体积与热路径 | 压缩不删原文；过长则**切换聊天文件**（热文件变小）；旧文件只读/归档策略另定 |

上翻硬顶、切文件触发阈值、压缩阈值 **不要默认绑成同一个数**（例如上翻 200 与「迁入新文件的 200」可以碰巧相同，但触发切文件应看窗/体积/逻辑长度）。

## 压缩（先做的一道）

### 已定方向

- 主要聊天文件 **先走压缩**，再考虑切文件。
- 复用现有 L1/L2 合同；主 Chat 因工具少，L1 收益可能弱于 coder 会话，**更依赖 L2 摘要质量**。

### 顾虑

- L2 摘要漂：细节丢失后，仅靠摘要续聊可能不够；切文件前是否强制再 L2，或迁「近窗原文 + 一条总摘要」。
- 压缩不删原文：磁盘仍涨；只解决逻辑上下文与（部分）估窗，不自动解决单文件 MB。
- 前端：已有 compact 气泡；若要「上滚命中压缩区再拉原文」，需额外契约（见待拍板）。

### 与活动 Run

- 现有：压缩与 query 有冲突/安全点语义；切文件更应在 **无活动 Run、无未决 awaiting** 时做（建议写入待拍板默认态度）。

## 上翻上限与分页回放

### 意向

- 支持向上翻页看历史，但有限制（约一个月或约 200 条量级）。
- 到顶应明示，不假无限滚动。
- 刷新/重连后仍应能在窗口内恢复位置并继续上滚（直到硬顶）。

### 现状缺口

- Platform：全量 replay 边界，无 Chat 级 `hasMore` / `before*` 产品分页。
- WebClient：吃的是全量 `events[]`；无 prepend；主 Chat 无 gap 补洞。

### 顾虑

- 「200 条」是 UI 节点、JSONL 行，还是 user/assistant **可见轮**？工具行多时「200 行」可能只有很少轮对话；主要聊天更宜按**可见正文轮/气泡**计数（待拍板）。
- 硬顶以外的旧约定：靠摘要、记忆、旧文件只读入口，而不是无限时间线。
- 新旧前端兼容：分页响应必须带 `hasMore`（或等价），避免旧前端把「最近一页」当成全量历史。

## 聊天文件切换（压缩之后的后手）

### 意向

- 当主聊天文件上下文仍然不够（或文件过长）时，切换到新的聊天文件继续。
- 迁入新文件的主要是 **内容**，**没有工具**；量级上可把近约 200 条带进新文件。
- 用户仍应感觉在「同一个主要聊天」里续聊（指针切换 ideally 无感或轻提示）。

### 评估要点 / 顾虑

1. **触发条件**未定：估窗 token、文件 MB、逻辑消息数、连续 L2 后仍紧张，或组合。
2. **「只带 content」定义**：是否只保留 user/assistant 对用户可见正文；tool 调用与 result 整段丢弃；是否带上有效 L2 摘要行。
3. **「200」定义**：与上翻硬顶是否同一计量；建议迁移用「可见轮」，存储行另计。
4. **身份与指针**：
   - **新 `chatId` + 主 Chat 指针原子挪过去**：产品上像换文件；但 mail 的地址在发信时确定且不再改变，分身的回信、即时消息、请示和已排队的 mail 都会落回旧 chatId（旧会话仍活着时在那里开 Run，归档旧会话则这些 mail 失败）。按现行 mailbox 合同不可行。
   - **同 `chatId` 物理多卷**：地址更稳，实现像切卷；与「聊天文件」话术略有差别。
5. **进行中状态**：有 ActiveRun / awaiting / 未出队 mail 时禁止切或先排空（待拍板）。
6. **旧文件**：只读上翻（仍受硬顶）、History 入口、保留多久、是否冷压。
7. **与 mailbox**：队列短命；切的是历史热文件，不是邮箱本身；切换瞬间收件目标必须是新热 Chat。

---

## 与主要聊天模式的关系

- 主 Chat：最强模型 + 低思考；分身高思考；上下文由主 Chat 主动给出（见既有主聊合同）。
- 长上下文策略服务「前台永不结束」；**不**要求分身 Chat 使用同一套上翻硬顶（分身可短命）。
- 双强度、mailbox 出队策略不在本文件展开。

## 待拍板

### 上翻与分页契约（Platform ↔ WebClient）

| # | 问题 | 选项 / 说明 |
|---|---|---|
| U1 | 上翻硬顶计量 | 可见气泡/轮约 200；JSONL/事件约 200；约一个月；两者取紧 |
| U2 | Chat 级分页游标 | 事件 `seq`；`runId + runSeq`；其他 |
| U3 | 首屏窗口 | 最近 N 事件；最近 K 个 run；最近 N 可见气泡 |
| U4 | 空闲主 Chat WS 重连 | 按 Chat 级水位补洞；仍不自动 load；仅 mailbox 唤醒时再拉 |
| U5 | 压缩原文在人侧 | 同流保留（受 U1 限制）可上滚看到；摘要气泡 + 按需再拉（segmentId / replacedFrom–To / originalAvailable，或扩展 compact） |
| U6 | 新旧兼容 | 分页必带 `hasMore`（或等价）；旧客户端行为 |

## 验收方向（行为，非工作量；拍板后再生效）

1. 主 Chat 长聊：模型侧优先靠压缩续跑，不以全量历史进窗。
2. 人侧：首屏非整库；上滚可加载更早一页，直到硬顶；到顶可感知。
3. 刷新/重连：窗口内位置可恢复；补洞策略符合 U4。
4. 压缩后：逻辑上下文变小；原文盘上策略符合 U5。
5. 切文件后：热路径为新文件 + 正文近窗；工具未迁入；mailbox/主指针不丢信；用户仍在主聊续聊。
