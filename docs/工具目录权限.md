# 工具目录权限

## 当前状态

工具目录权限统一由 `configs/tools.yml` 中的 `access-policy` 管理。`bash` host shell 与 `file_read`、`file_glob`、`file_grep`、`file_write`、`file_edit` 都读取同一套 `AccessPolicy`，避免 bash 拥有比结构化文件工具更宽的 host path 权限。

`configs/tools.yml` 同时包含 `bash` shell、命令白名单与超时配置，以及 `file-tools` 大小限制、写前读、写审批与 hook 等工具行为配置。旧拆分文件不再读取。

Desktop / 本机服务包会在根目录 `bin/` 内置 `rg`、`dbx`、`httpx`，并仅为 agent-platform 进程及其 Host 子进程前置该目录到 `PATH`。`file_grep`、`file_glob` 使用稳定 JSON schema 并直接调用内置 rg；dbx/httpx 首版通过 JSON `bash` tool 调用，仍受 Bash 命令白名单、bashsec 和 access policy 约束。该 PATH 不会注入 Container Hub sandbox。

## 核心流程

```text
请求 accessLevel
  -> 选择 AccessPolicy level
  -> 展开 @root / @runtime / @workspace / @chat / @agent / @skills / @skills-center / @owner / @temp
  -> canonicalize 目标并执行 temp escape 等 hard block
  -> 写操作先匹配 level readonly + trusted run readonly roots
  -> 写入 Git 可执行配置（.git/hooks、.git/config）按 executable-config 审批
  -> 写入 Workspace 只由本 run 的 editing 能力决定（editing=false 硬拒绝）
  -> 追加 agent runtimeConfig.hostAccess readRoots/writeRoots
  -> 读取时追加 trusted run read roots
  -> file tools 精确校验目标路径
  -> bash 先跑 bashsec，再按命令语义校验 cwd、文件名操作数、redirect
  -> 越权按 policy allow / hitl / auto / block 执行
```

### Effective roots 分层

| 来源 | 生命周期 | 目录与权限语义 |
|---|---|---|
| `access-policy.levels` | 进程配置 | 提供基础 read/write/readonly roots；当前 level 的 readonly 在 writeRoots、hostAccess 和 HITL 之前硬阻断 |
| `@root` | Platform 当前驱动器 | Unix/macOS 为 `/`，Windows 为当前驱动器根目录；full_access 默认读写根，不代表所有盘符 |
| `@runtime` | 进程配置 | 仅用于路径解析，指向 runtime 根目录；本身不授予任何读写权限，解析后的真实路径仍按其余根、readonly、StateDir 保护和 HITL 判定，不能用于 `runtimeConfig.hostAccess` |
| `@workspace` / `@chat` | 单次 run | 绑定 Agent Workspace 与当前 Chat；Workspace 写入由 editing 能力决定（CODER、GENERAL 默认可编辑，KBASE 默认只读），不受 write-roots、审批或 full_access 影响；Chat 默认可读写 |
| `@agent` / `@skills` | Agent runtime | 绑定 `ru-agents/<agentKey>/<revision>` 及其 Skills；shipped default 可读且 readonly |
| `@skills-center` | 按需暴露 | 额外 must-use Skill 或显式 sandbox mount 时绑定共享中心；暴露别名不等于开放整个中心 |
| `@owner` | Agent 配置 | 只有 access-policy 或 `runtimeConfig.hostAccess` 显式引用时授权 |
| `@temp` | 进程启动冻结 | 非 `full_access` effective level 强制加入 read/write roots |
| `runtimeConfig.hostAccess` | Agent 配置、run 冻结 | 为单个 Agent 的 Host Bash/FileTools 追加 read/write roots，不影响 Container mounts |
| `RunAccessRoots` | 单次 run、Platform trusted | `mustUseSkills` 为每个选中 Skill canonical 目录追加 read + readonly；请求不能伪造，未选中兄弟目录不继承 |
| `/api/access-level` | run 运行中 | 切换整套 level，不直接添加目录；trusted run readonly 不随 level 提升消失 |
| exact/rule approval | 当前 run | 临时批准精确目标或同一规则，不修改根列表，也不能放宽 readonly/hard block |

RuntimeContext 中的 Root、Pan、Memory、registries、Teams、Automations 等路径以及 Container mounts 只描述上下文或可见性，不自动成为 AccessPolicy roots。references、run env、`platform_control` 也不追加目录。editing 是解析后的 run 能力（`QuerySession.WorkspaceReadOnly`，KBASE 由 `editingMode` 解析），editing=false 时 Workspace 的任何写入硬拒绝，工作目录或参数落在 Workspace 内、效果无法分析的程序（不透明程序、连接器 CLI、复杂 Shell）也拒绝执行，Bash 默认工作目录改为 `@chat`。

默认 `readonly-roots` 仅包含 `@agent`、`@skills`，不对整个 `@skills-center` 设置只读限制；`auto_approve` 继承该规则。共享技能中心的写入按 Workspace、write roots、hostAccess 和常规审批判定，因此 Workspace 覆盖共享技能中心的 Host Agent 可以创建或维护技能。`mustUseSkills` 选中目录的 run readonly、管理员显式配置的 readonly 及 Container 只读挂载仍生效。已有部署若在 `configs/tools.yml` 显式保留 `@skills-center` readonly，需修改配置并重启；代码默认值不会覆盖显式配置。

FileTools 还维护 run-scoped 读写闭环：已有文件写入或编辑前，默认要求同一 run 内先用 `file_read` 完整读取（fully read），防止模型在没有读取最新内容时覆盖用户改动。

不存在 `WorkingDirectory` 或工具级默认目录。相对路径、Bash 未传 `cwd`（editing=false 时为 `@chat`）、以及 `file_glob/file_grep` 省略 path 时一律从 Workspace 解析；`@chat/...` 才访问当前 Chat，`@temp/...` 才访问主临时根。没有 Workspace 时相对路径与 `@workspace` 返回 `workspace_unavailable`，绝不回退 Chat 或进程 cwd。Bash 的单次 `cwd` 可显式使用 `@chat/...` 或 `@temp/...`，并继续服从 AccessPolicy/HITL。

模型可见的工具 schema 会按 session 生成并深拷贝。无 Workspace 时，`bash.cwd` 与 `file_glob/file_grep.path` 会被动态标为必填，文件路径参数会明确要求 `@chat`、`@agent`、`@skills`、`@owner`、`@temp` 等语义根或允许的绝对路径；这只收紧模型契约，不改变 AccessPolicy、路径分类或实际调用时的 `workspace_unavailable` 安全检查。Skill catalog 同时提供精确的 `path: @skills/<skillId>/SKILL.md`，命中后应直接用 `file_read` 读取，不应通过 Bash 或目录扫描寻找 Skill。

`mustUseSkills` 是唯一由 query admission 建立的 trusted 目录授权。每个请求选中的已配置或额外 Skill 都先解析为其最终 canonical 目录，再同时进入本 run 的 read 与 readonly roots；因此完整 `SKILL.md`、scripts、references 和 assets 的结构化读取不触发路径 HITL，symlink/junction 逃逸按最终目标重新分类。读取授权与执行授权分开判定；已配置或本次选中的普通 Skill，其脚本入口按下述本 run 技能凭据匹配，Bash security 与其他 opaque/complex command 审批保持独立。

`@temp` 在进程启动时 canonicalize、去重并冻结；修改 `TMPDIR`、`TMP` 或 `TEMP` 后必须重启。Unix/macOS 同时纳入 `os.TempDir()` 与 canonical `/tmp`，因此 macOS 的 `/tmp`、`/private/tmp` 等价，且 `/var/folders/.../T` 形式的进程 Temp 也有效；Windows 只纳入 `os.TempDir()`，不额外放行 `C:\Windows\Temp`。`@temp/path` 指向主根 `os.TempDir()`，实际 Host 绝对路径可命中任一冻结根。

effective `default.read-roots/write-roots` 即使在旧或自定义 `tools.yml` 中未声明，也会无条件追加 `@temp`。临时根内 FileTools 读、创建、覆盖和编辑不触发路径、LLM 预审批或 `require-write-approval` 审批；写前读、SHA/mtime/size 并发检查、大小上限、编码和 history 仍执行。Bash 的 `mkdir/touch/cp/mv/rm/chmod` 等可静态识别文件操作不会仅因临时路径触发 HITL。管理员 readonly、KBASE mutation gate 与 hard block 仍优先。

脚本建议先用 `file_write` 完整写入 `@chat/...`，再发起独立 Bash 调用。本 Run 通过受管文件工具写入当前 Chat 目录、由系统解释器（或其 shebang）执行且内容未被外部改动的脚本，三档都免执行审批；本 Run 再用 `file_write/file_edit` 修改后证明随之更新，不重新询问。公共临时目录、Workspace 中的项目脚本、上传/下载/复制来的脚本不享受该豁免，按普通未知程序处理。豁免只消除执行审批，同一调用中的越界参数、重定向和业务规则照常检查；脚本内部的动态访问不受约束（信任临时代码）。每 Run 私有临时目录接入后再纳入豁免。

### 技能脚本入口执行凭据

Agent YAML 已配置的普通 Skill 使用 该 Agent 版本绑定的 `ru-skills/<digest>`，本次 `mustUseSkills` 额外选中的 Skill 使用已解析的技能中心目录；两者合并去重。Run 准入在内存中记录各技能 `scripts/**` 下现存普通文件的 canonical 路径与实际字节 SHA-256，执行时复用通用解释器及脚本入口识别。未配置且未选中的技能、目录外文件、运行中新加入的文件，以及无法确定脚本入口的命令不获得这项豁免。连接器技能沿用连接器 CLI 授权。

凭据绑定 Agent、Run、执行环境，与自写证明分开保存；不写文件或数据库，不复制技能，不生成 run-runtime。同 Run 工具调用与上下文压缩保留内存凭据，不跨 Run 或子调用继承；恢复同一 Run 时不从历史或恢复时的新内容重建凭据，新 Run 独立建立自己的凭据。目录、scripts 根和入口严格解析现存 canonical 路径，symlink/junction 不能借此逃逸；无法验证时走原策略。Host 启动前重验内容，Container 按本 Run 选中技能的 Host–guest 映射在实际容器解析入口并核对字节摘要，不能用 Host 同名文件代替。观察到内容不匹配时撤销该入口凭据，不自动更新摘要。

命中记录 `decision:allow`、`ruleKey:bash-access:skill-script`，仅取消对应入口 opaque 审批，不授予解释器整轮批准。其他命令、重定向、环境赋值、bashsec hard block、readonly 和 KBASE mutation gate 保持独立。入口摘要不锁定脚本加载的完整依赖图；Host Bash 仍在当前进程权限和环境下执行，不隔离脚本内部文件访问，也不消除校验到执行间的全部文件竞态。Container 继续使用既有只读挂载。

### 通用脚本入口与本 run 自写证明

所有 Agent（包括 bootstrap）统一处理 `bash task.sh`、`sh task.sh`、`./task.sh` 和绝对路径执行。opaque 表示执行入口可能在内部访问文件、无法仅凭命令行确定全部行为；它不是错误，也不等于恶意。无扩展名脚本、自定义二进制同样被识别，本地同名程序不能凭 `ls`/`node` 等 basename 获得系统命令待遇。已知 wrapper 会解析内部入口、环境及 cwd，未知语义进入 complex；不改写解释器、参数或退出码。

| 执行入口 | default | auto_approve | full_access |
| --- | --- | --- | --- |
| 当前 Agent 已挂载且入口匹配的连接器 CLI | allow | allow | allow |
| 本 run 写入当前 Chat 目录的自写脚本（证明仍匹配） | allow | allow | allow |
| 已配置或 mustUseSkills 选中技能的 scripts 入口，且本 run 凭据仍匹配 | allow | allow | allow |
| 其他位置的自写脚本、临时目录脚本 | 按调用与内容版本 HITL | auto_approved 并审计 | allow |
| 其他脚本/自定义程序 | HITL | auto_approved 并审计 | allow |

连接器 CLI 的挂载授权覆盖该 CLI 的全部参数、cwd 和内部访问，优先于针对该入口的 opaque/路径审批配置，不产生自动批准审计；它不授予外围 Shell 命令、重定向或环境赋值权限。连接器入口按实际执行环境解析，需匹配 catalog 冻结的 canonical 路径及 SHA-256；连接器业务 hook 仍须独立满足。Host 对无 Shell 包装的单条连接器命令直接启动已验证入口，凭据只进入该子进程；需要凭据的复合命令、包装命令和重定向返回 `connector_requires_direct_invocation`，需拆分调用。分析投影永不执行。规则详见 [连接器](连接器.md)。

下述自写脚本和临时脚本机制中，管理员显式 block 和其他路径限制仍优先。自写证明绑定 Agent、Run、执行环境、canonical 路径、实际编码字节 SHA-256 和 revision；`file_write` 成功创建/完整覆盖后建立。`file_edit` 仅在原证明存在且编辑前字节匹配时更新；读取、上传、下载、复制、外来脚本局部编辑、Bash 写文件、编译产物不建立证明。执行前重新校验，发现变化撤销证明。记录线程安全、不落盘、不从 Chat 历史恢复、不跨 run/子 Agent/Team 成员继承，同 run 上下文压缩保留。写入与执行同一工具批次时，按原顺序等写入完成后再审批执行。

自写证明只在当前 Chat 目录内取消执行审批。其他脚本的批准绑定命令、canonical cwd、入口内容 SHA-256、环境和 access level；同一 Run 中内容或调用上下文变化，旧批准不能复用。普通越界路径的规则范围为精确目标，不再扩大到最近存在的父目录。复杂 Shell 和远端 mutation 只允许单次批准；破坏性操作的本轮批准只复用完全相同的命令与工作目录。

Bash 审批 `description` 保留模型原始补充描述；`policy` 与 `requirements` 独立列出系统判定原因、目标、内容摘要和范围。Host 的单次授权继续绑定 toolID，不能交给兄弟调用。未展示的次级要求不能通过主规则的本轮批准放宽。

Host Bash 的 builtin 人工审批后可恢复并发：审批准备只登记和校验授权，命令由调度器统一启动。仅本次批准绑定当前调用的 `toolID` 和展示时冻结的 access/security 指纹，在通过预算检查后只交给该调用的执行上下文，由 Executor 启动前最终核验并消费；不把整份一次性授权表复制给并发调用，拒绝、取消、失败或未启动调用的授权不能转给其他调用。本轮批准保存在当前 Run 的规则集合中，调度器串行登记后供各调用读取。批准不会放宽 hard block、readonly、新增执行要求或写入/环境修改屏障。

Host 同一 Bash 的 access/security 与 builtin 技能 hook 在首次确认时合并冻结，公开主规则保持原检查优先级与 timeout。本次许可绑定 toolID；本轮批准仅登记公开主规则，其余检查不得顺带进入本轮白名单。opaque 规则按调用、入口内容版本、环境和完整 canonical cwd 精确匹配，不授权删除目标目录，也不涵盖 cwd 子目录。当前批准调用严格复检完整参数与 access 指纹；新增未授权 hook 同样按要求变化收口，不生成同 ID 的第二个等待。详见 [HITL协议](HITL协议.md)。

Host 的 LLM 预审和 Executor 共用分析，启动前用实际子进程环境再次核对。Sandbox 的 cwd、入口解析和摘要探测发生在实际容器，依赖容器内 `/usr/bin/readlink`、`sha256sum`、`head`；不可解析的目标保守进入 opaque/complex，容器 `/tmp` 符号链接逃逸直接 block。容器 Workspace/Chat 映射文件还需匹配容器字节摘要；不把 Host `/tmp` 的文件身份当成容器 `/tmp` 身份。临时目录不再提供执行入口豁免。条件分支合流不会沿用可能失效的环境变量；循环内变量或 cwd 变化导致后续入口不确定时进入 complex，不使用首轮脚本的自写证明放行后续入口。

脚本来源证明不再授权执行；bashsec hard block、canonical/symlink 逃逸、readonly、KBASE mutation gate 和外部写入规则始终独立。Host Bash 是执行前策略检查，不隔离脚本内部每次文件访问，也不保证消除其他进程改文件的全部竞态。无数据迁移，历史审计保持原样。

临时权限按最终 canonical 目标判断。词法上位于冻结临时根、但通过 symlink/junction 跳出的路径会直接 block，不能用 HITL 放行；`artifact_publish` 和 `/api/resource` 复用相同解析器。

Workspace 与 Chat 按 canonical 语义分类，不要求普通 Workspace 与 ChatsRoot 物理互斥。分类优先级是当前 Chat、其他 Chat、Workspace（排除整个 ChatsRoot）、external；因此 Workspace 为 `/` 时 Chat 仍不会获得 Workspace 权限或触发 Git/LSP/file-change hook。相对路径或 `@workspace/...` 解析后进入 ChatsRoot 会返回 `path_crosses_chat_root`，当前 Chat 必须改用 `@chat/...`；绝对路径则按最终分类应用 current-chat、other-chat、workspace 或 external 策略。

专用 `mode: KBASE` 无论是否开启 `editingMode` 都使用 `agent.yml` 声明的同一组工具，且 Workspace 始终是最终 `runtimeConfig.workspaceRoot`；当前 Chat 目录是独立的 `ChatDir`。KBASE Workspace、当前 Chat 目录、其他 chatId 和 external 都先经过普通 `AccessPolicy`。run-scoped `ScopedFilePolicy` 不覆盖 AccessPlan，只负责固定工具准入、Workspace canonical 路径识别和 Workspace mutation gate：未开启 editing 时 Workspace 可读但 write/edit 返回 `kbase_editing_mode_required`，不会产生无法生效的 HITL；开启后才应用 Workspace 已有文件强制先读后写和新文件父目录已存在。当前 Chat 目录在两种模式下都按 `@chat` 可读写，external 和其他 chatId 继续按实际 policy 得到 allow、auto、HITL 或 block。`full_access`、hostAccess、writeRoots 和 approval 可以放宽 external，但不能替代 KBASE Workspace 的 `editingMode:true`；管理员显式 block 仍优先。

### 平台私有目录与参数语义

有效 StateDir（包括自定义 `AP_RUNTIME_STATE_DIR`，其中含连接器凭据与默认身份文件）和单独配置的 identity 文件在三档下都拒绝普通工具读写。Workspace、临时根、hostAccess、普通单次/本轮批准及 full_access 均不能覆盖；Platform 内部身份服务、连接器认证和 Run 持久化继续正常使用这些目录。`registries/providers` 不在保护范围内，`file_read` 读取时继续脱敏密钥字段。普通 `.env`、私钥等敏感文件不单独设限，按所在目录的普通规则处理。

`cat plain.txt`、`cat ./plain.txt` 与重定向 `< plain.txt` 均检查最终物理目标。路径在解析 symlink（Windows 含 junction）后再处理 `..`。命令语义由 `internal/shellanalysis` 的命令说明表统一描述：长短选项与参数个数、源读/目标写、递归、删除、远端修改。未知选项标记为分析不完整，可见文件操作数升级为写入，但不再视为执行未知代码；未登记的程序才是 opaque。`curl file://...`、`-d @file`、`-F f=@file`、`-T` 也检查本地文件。`bash -c`、`sh -c` 的字面量脚本和 `env -S` 递归分析，包装命令不能隐藏远端修改、文件效果或业务规则。

Git 按子命令分类：`status/diff/log/show/branch` 等只读命令在生效配置（仓库、全局、include）未定义 fsmonitor、外部 diff、textconv、filter、签名显示等执行扩展时直接放行；`add/commit/checkout/reset` 等本地写入另要求没有生效的 hook、编辑器和签名程序，并按 editing 判定仓库写入；`fetch/pull/push` 另要求标准凭据助手。`-c`/`--config-env` 注入配置、`--ext-diff`、`--show-signature` 视为执行代码。`reset --hard`、`clean -f`、`checkout -- <路径>`、`restore`、`stash drop`、`branch -D` 为破坏性操作，`push` 为远端修改。配置扫描调用系统 `git config --list`，结果按配置文件元数据缓存 30 秒。sed、awk 只放行可验证的安全子集（无 `e/w/r` 命令与 `s///e`、无 `system/getline/管道/输出重定向`），`jq`、`tar`、`diff` 按真实参数语义分析。

破坏性操作的第一版定义：递归删除（`rm -r`、`find -delete`、`tar --remove-files`）与丢弃未提交改动的 Git 命令；单文件 `rm/mv`、覆盖和 `>` 重定向属于普通修改。Bash 的修改不进入 file-history。

Host 文件操作数 glob 最多审核 512 个目标、4096 个目录项，父目录穿越或超限拒绝；Container 的 glob 尚未实现 guest 展开，需传明确路径。已识别的递归操作检查目标下的只读/私有根，不能靠操作父目录绕过。`file_grep/file_glob` 在用户 include glob 之后添加保护排除，父目录扫描不进入私有目录和 ChatsRoot；grep 内容输出按路径排序以稳定分页。

图片 `referenceName` 与 `filePath` 使用相同 canonical 策略，Desktop CDP 参数文件和产物发布也执行私有目录保护。

普通 Host 工具只继承 `bash.inherit-env` 名单中的变量（支持 `PREFIX*`）；未配置时使用内置名单，覆盖系统路径、用户目录、临时目录、locale、`XDG_*`、代理、证书与常见工具链目录。动态加载器、解释器预加载与 Git 执行配置类变量即使列入名单也不继承。`SSH_AUTH_SOCK` 视为凭据，只传给分析确认的 Git 网络操作。Platform 从桌面会话启动时 PATH 往往不完整，平台在 macOS 按 `/etc/paths`、`/etc/paths.d` 和 Homebrew 标准前缀补齐缺失目录，Linux 补齐标准系统目录，不执行任何 profile。

技能 `.runtime-env.json` 的 `PATH` 只填写额外目录（相对路径按技能目录解析），平台按技能配置顺序去重后追加到 PATH 末尾，不覆盖、不前置；目录须位于该技能自身的 canonical 目录内，或位于 `bash.path-append-roots` 管理员名单内，其他目录忽略并记录警告。审批检查与实际执行使用同一份合并后的环境。Agent、Skill、调用和 run.env 共用危险覆盖检查，包括动态加载器、解释器预加载、Git 执行配置、IFS 与 Shell 启动变量。默认 Bash 使用 `--noprofile --norc -o pipefail -c`。管理员自定义 Shell/参数仍是部署信任边界。

权限矩阵及实现边界见 [AccessPolicy 与 HITL 边界](AccessPolicy与HITL改造.md)。

## 配置与接口

- 工具运行时配置：`configs/tools.yml`，模板为 `configs/tools.example.yml`。
- `access-policy`：目录权限配置。
- `bash`：host shell、命令白名单与超时配置。
- Unix/macOS 默认 host Bash 以 `bash --noprofile --norc -o pipefail -c` 执行，管道中任一上游命令非零退出时，整条管道返回最右侧的非零退出码；Windows 与显式配置的非 Bash shell 不注入该选项。
- `bash.shell-args` 是高级完整覆盖：一旦显式配置，平台不再补充默认参数。需要保留默认语义时，应包含 `--noprofile`、`--norc`、`-o`、`pipefail`、`-c` 与 `{{command}}`。
- `bash.inherit-env`、`bash.path-append-roots`：见上文环境与 PATH 说明。
- 默认 Bash 命令白名单包含 `rg`、`dbx`、`httpx`；builtins 版本和来源由发布锁文件管理，不由 tools 配置管理。
- `sandbox-bash`：已移除。输出重定向在所有运行时都作为文件写入由 AccessPolicy 判定，不再产生 bashsec 审批；保留该节只会在启动时记录警告。
- `file-tools`：结构化文件工具行为配置。
- `default`：chat、temp 写免审，Workspace 写入由 editing 决定；workspace、chat、agent、当前 agent skills、temp 读免审；其他路径、破坏性操作、可执行配置写入、远端修改触发 HITL。
- `auto_approve`：沿用 `default` 边界；越界读、复杂 bash、不透明命令与 bashsec 软审批自动批准，越界写、破坏性操作、可执行配置写入、远端修改仍触发 HITL，bashsec hard block 仍然阻断。
- `full_access`：访问范围扩到 `@root`，除硬约束外全部放行；`approvals.destructive/executable-config/remote-mutation` 可改为 `hitl` 继续确认。bashsec hard block、平台私有目录、editing=false、Platform trusted run readonly（must-use Skill 目录、连接器运行包）与业务 Hook（除非规则声明 `autoApprove: [full_access]`）仍然生效。
- `approvals.destructive`、`approvals.executable-config`、`approvals.remote-mutation`：新增审批项；旧 `tools.yml` 未声明时按同档位的内置默认值补齐，`inherit` 档位从父档位继承。
- `runtimeConfig.hostAccess.readRoots/writeRoots` 可为单个 agent 追加 host-side `bash/file_*` 读写根，支持 `@temp`；该配置不影响 Container Hub / sandbox，sandbox 挂载使用 `runtimeConfig.sandboxMounts`。
- 请求字段 `accessLevel` 可取 `default`、`auto_approve`、`full_access`；缺省为 `default`。
- `/api/access-level` 可在 native run 运行中动态更新当前 run 的 `accessLevel`；该更新不写回 agent 配置，也不会影响下一次 run。
- 动态更新从下一次工具权限判断开始生效，已经开始执行的 host bash / file tool 不会被中断；若当前正等待 access-policy approval，更新后会重新评估，满足新权限时自动继续。
- PROXY / ACP CODER run 暂不支持动态更新，接口返回 `status=unsupported`。
- `auto_approve` 的自动批准会作为 `messages[]` 内联 `role=user` 审计消息写入当前 `chatId.jsonl`，消息内的 `approval.decisions[].decision` 为 `auto_approved`；`full_access` 因为路径根已扩为 `/`，不产生越界审批记录。
- `require-write-approval` 控制写入是否默认需要审批。
- `require-read-before-write` 控制写前是否必须先被文件工具完整读取（fully read）。
- `read-before-write-scope` 控制观察范围，默认 `chat`：`run` 仅限当前 run；`chat` 会在 `<chatId>/.tools/state/file-versions.json` 保存文件版本证明，允许同 Chat 后续 Run 复用，不跨 Chat 共享。
- `read-before-write-max-age` 设置版本证明有效期，默认 `60m`，接受带单位的正时长（至少 `1ms`）。内存与持久化记录均检查有效期；恰好到期仍有效，超过有效期或观察时间缺失、位于未来时返回 `file_edit_cache_expired` / `file_write_cache_expired`，提示“文件缓存过期”，附带 `observedAtUnixMs/ageMs/maxAgeMs`（异常时间的 ageMs 为 0）。
- 修改已有文件依次校验记录存在、完整读取、有效期、当前 SHA-256；即使 mtime/size 不变也重新计算 SHA。成功完整读取或成功写入、编辑更新版本与观察时间，仅校验通过或返回 `unchanged` 不续期。过期后 `file_read` 返回实际内容并刷新记录；未过期的 `unchanged` 也需 SHA 一致。部分读取、截断仍不允许修改。

`file_glob` 用于按文件名/路径 glob 查找文件，`file_grep` 用于按内容正则搜索。`file_glob.pattern` 和 `file_grep.glob` 都是相对于 `path` 的匹配规则：`*.yml`、`**/agent.yml`、`internal/**/*.go` 合法；绝对路径、`~/...`、`@workspace/...`、`file://...` 等搜索根必须放进 `path`，误放在 glob 字段会在启动 rg 前返回可操作的参数错误。`file_grep.pattern` 始终是内容正则，不参与该路径形态检查。

两种搜索都禁止最终 canonical `path` 为 Host 文件系统、Windows volume 或 UNC share 的精确根。该 hard block 同时覆盖缺省 Workspace、显式绝对路径、裸 `@workspace` 和解析到根的 symlink/junction，不可由 accessLevel、hostAccess 或 HITL 放宽；Workspace 为根时，session-local 工具 Schema 会要求显式传入更窄的 `path`。普通绝对目录、语义根子目录和相对 Workspace 子目录保持原有 AccessPolicy 行为。

rg exit code `0` 表示成功，`1` 表示无匹配并正常返回 `matchCount: 0`、`results: []`，`2+` 表示扫描失败。Platform 不再隐藏 rg stderr；失败结果保留限长后的 `stderr`、`rgExitCode`，已经产生 stdout 时还会返回按默认页大小封顶的 `partialResults`、`partialMatchCount` 和 `partialTruncated`，但整体仍是失败，调用方不得把部分结果当成完整搜索。

## 约束与注意事项

- `access-policy.working-directory`、`bash.working-directory`、`file-tools.working-directory` 已删除，出现即启动失败。旧 YAML 路径策略字段 `bash.allowed-paths`、`bash.path-checked-commands`、`bash.path-check-bypass-commands`、`file-tools.allowed-read-paths`、`file-tools.allowed-write-paths` 同样硬失败。
- 工具权限与服务鉴权不是同一层；JWT、resource ticket、CORS 见 [鉴权与安全边界](鉴权与安全边界.md)。
- `approve_rule_run` 只在当前 run 内批准同一规则，不是永久配置，也不能放宽 readonly 或其他 hard block。
- 文件工具写入会进入 file-history 并建立自写证明；Bash 重定向写入同样按路径规则判定，但不进入 file-history。
- KBASE Workspace 内的 `file_write` 不会隐式创建目录；开启 editing 后，任何通用文本新文件都只能写入已存在目录，已有 Workspace 文件必须完整读后再写。当前 Chat 目录和获批外部目录沿用普通 FileTools 规则；写入继续执行 SHA/mtime/size 并发校验、原子替换和 run-scoped history。
- `pipefail` 不等于 `set -e`：它只改变单条管道的退出码，不会阻止 `; true`、`|| true` 或后续成功命令覆盖整个 shell 的最终状态。平台默认不启用 `set -e`，普通 Bash 非零退出仍作为可恢复的工具失败交给 Agent 处理。
- `pipefail` 会暴露原先被隐藏的状态，例如 `rg pattern file | wc -l` 在无匹配时返回非零；`yes | head -n 1` 的上游也可能因预期的 SIGPIPE 返回非零。确属预期结果时，应在命令中显式处理。
- sandbox bash 使用同一 AccessPolicy/HITL 评估 cwd 与可静态识别的路径；`/workspace`、`/chat` 会映射回冻结的 Host 双根，sandbox `/tmp` 会映射到冻结的 Host `@temp` 语义根进行判定，实际可见目录仍由 sandbox mounts 控制。
- Container Hub 当前仍以 `/bin/sh -lc` 执行，不注入非 POSIX 的 `pipefail`；只有在 sandbox 镜像统一保证 `/bin/bash` 后才可采用相同默认值。

## 通用智能体根目录与项目目录

`runtimeConfig.workspaceRoot: "@root"` 显式表示通用根目录智能体。Catalog 保留该意图，同时把运行时 Workspace 解析为本机绝对根目录：macOS/Linux 为 `/`，Windows 为 Platform 当前驱动器根目录。工具相对路径、`@workspace`、运行上下文和目录权限使用解析后的真实路径；该值不增加跨盘权限，不绕过 readonly、审批、KBASE 根目录限制或根目录扫描禁令。

公共 HTTP/WebSocket `/api/agents`（包括 includeTeam）与 Admin 摘要的 `workspaceDir` 只表达项目目录：`@root` 省略该字段，普通绝对目录（包括显式 `/`）继续返回解析后的目录，未配置时也省略。Admin 原始 definition 保存 `"@root"`，编辑、导入、重载不得把它改写为实际根路径。Desktop 据 `workspaceDir` 是否非空区分 Projects，不按 mode 或路径形状猜测通用身份。现有通用智能体的 `/` 配置需显式改为 `"@root"`；不自动迁移所有根路径，以免改变显式项目配置的语义。

工具权限 `read-roots/write-roots/readonly-roots` 与工具路径参数支持 `@root`（路径参数也可用 `@root/...`），不改变 Workspace，也不绕过 readonly、KBASE mutation gate 或根目录扫描禁令。Windows 其他盘符仍按既有越权策略处理。

所有平台发布包直接使用 `configs/tools.example.yml`，不维护 Windows 副本。未配置 `bash.allowed-commands` 时，Windows 默认 `*`，Unix/macOS 使用 Go 内置命令列表；显式配置优先。Shell 未配置时按平台选择，Windows 默认 PowerShell，Unix/macOS 默认 Bash；内置 Git Bash 仍由已有开关控制。已有部署的 `configs/tools.yml` 不会因此自动重写。

图片工具的参考图与 mask 使用相同路径策略，并将多个越界输入合并审批。`referenceName` 解析后也检查 canonical 路径，不能经符号链接读取私有状态。一次性批准绑定 toolID，不授予其他调用读取权。
