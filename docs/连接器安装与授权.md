# 连接器安装与授权

## 认证类型

`connector.json.auth_mode` 区分凭据来源和认证流程，与 `type=cli/mcp/view` 独立。普通凭据由 Platform/Agent 一侧持有，保存到部署级 `.state/connectors/<id>`；账号按 Platform subject 隔离尚未实现。

| auth_mode | 凭据来源与获取方式 | 当前行为 |
| --- | --- | --- |
| `token` | 用户在第三方后台生成并手工填写 | 按 token_schema 校验、保存、查询状态与清除；注入 MCP headers、stdio env 或 HTTP query |
| `oneid-token` | Desktop 企业 SSO 自动提供 | 按调用即时提供 AP_ACCESS_TOKEN；Host CLI/stdio MCP 通过环境变量使用，HTTP MCP 生成 Bearer Header，不保存连接器凭据 |
| `oauth` | 用户通过浏览器完成 OAuth 2.0 授权码流程 | 使用预注册 public client 和显式授权/Token endpoint，PKCE、loopback 回调与刷新 |
| `mcp` | 用户通过浏览器完成 MCP OAuth 2.1 认证 | 发现资源和授权服务器元数据，使用预注册 public client 或动态注册，再执行 PKCE 与刷新 |
| `null` | 由 connector Skill / CLI / SDK 决定 | 不推断无需认证，不阻挡 MCP 初始化；仅显式声明受管 CLI 生命周期时提供管理端登录助手 |

`null` 是 JSON 空值，也可省略 auth_mode；字符串 `"null"` 和空字符串非法。读取旧包时，`none`、`cli` 归一为 `null`，旧 `oauth` + `oauth.discovery=true` 归一为 `mcp`；原包文件不自动改写，目录/API 元数据返回新值。builtin.dbx 和 builtin.httpx 的认证委托给各自 CLI/Skill，清单使用 `null`，随包不可修改或删除。

`oneid-token` 复用 Desktop SSO：Desktop 原子写入 `<Desktop dataRoot>/state/desktop/sso-access-token.txt`，启动参数 `--identity-file` 将该文件路径交给 Platform。普通 Agent Host Bash 与 oneid-token 的 stdio MCP 在创建进程时即时读取，注入保留环境变量 `AP_ACCESS_TOKEN`；不修改 Platform 进程环境。HTTP MCP 无子进程环境，使用同一身份环境生成 `Authorization: Bearer ...`，每次请求重新读取，并严格绑定 HTTPS（默认端口 443）的完整 MCP endpoint。Token 不复制进连接器包、Agent 运行包或 `.state/connectors`。

## ZIP 导入

`POST /api/admin/connectors/import` 使用现有 Platform 鉴权和 `{code,msg,data}` 包裹。multipart 表单只接受一个 `file`，可选 `overwrite=true`。

ZIP 支持根目录直接放 `connector.json`，或一层与 id 同名的包装目录。清单决定安装目录；文件名不决定 id。单包上传最多 64 MiB、8192 个条目、解压合计 256 MiB、单文件 128 MiB；拒绝路径穿越、符号链接、特殊文件、大小写路径冲突、Windows 保留文件名及 `builtin.*`。可执行权限保留为 0755，普通文件为 0644。

完整包和 MCP key 冲突先校验，之后替换来源并本地 reload。同名包默认返回 409，显式覆盖替换整个目录。本地 reload 失败恢复旧来源；远端服务连接失败只报告不可用，不回滚合法包。当前过程处理普通运行错误，不承诺断电时目录替换的跨步骤事务。

不启动完整服务也可以管理包：

```bash
agent-platform connector-manage import --runtime-dir /absolute/runtime /path/to/tmeet.zip
agent-platform connector-manage status --runtime-dir /absolute/runtime --id tmeet
agent-platform connector-manage login --runtime-dir /absolute/runtime --id tmeet
agent-platform connector-manage logout --runtime-dir /absolute/runtime --id tmeet
agent-platform connector-manage set-token --runtime-dir /absolute/runtime --id example-api --credentials-file /absolute/token-values.json
```

`--runtime-dir` 选择需要管理的部署，原包固定使用该根下的 `connectors-center`，旧迁移来源固定为 `connectors` 和 `connector-state`。状态根只读取环境变量 `AP_RUNTIME_STATE_DIR`，未设置或为空时使用 `<runtime-dir>/.state`；连接器固定使用其 `connectors/<id>` 子目录。独立 CLI 不自动读取 `.env`，应由调用方注入与 Platform 相同的环境；相对状态路径按命令当前工作目录解析。`--state-dir`、`--connectors-center-dir`、`--connectors-dir` 和 `--connector-state-dir` 已移除，传入会报错。CLI 登录输出状态和授权链接，保持前台等待；Ctrl+C 取消。登录、保存 Token 或退出完成后原子重写内容不变的 connector.json，唤醒标准来源 watcher。已运行的旧版本 Platform 需要重启到支持授权的新版本。此功能不提供独立授权界面，Platform 现有客户端通过下述 API 发起授权和显示状态。

## 登录 API

| 方法 | 地址 | 行为 |
| --- | --- | --- |
| POST | `/api/admin/connectors/auth?id=<id>` | 异步开始登录，相同连接器的活动登录幂等复用 |
| GET | 同上 | 查询状态及等待中的授权链接，不回显 CLI 原始输出或 Token |
| PUT | 同上 | token 模式接受 `{ "credentials": { "API_KEY": "用户填写值" } }`，完整替换凭据并 reload |
| DELETE | 同上 | 清除 token/OAuth 本地凭据，或执行受管 CLI 退出；不清除 Desktop SSO 或任意 CLI 自管状态 |
| POST | `/api/admin/connectors/auth/cancel?id=<id>` | 只取消登录会话和进程树 |

响应字段为 `connectorId/sessionId/status/authorizationUrl/message/expiresAt`。状态包含 `delegated`、`setup_required`、`unauthorized`、`preparing`、`pending`、`authorized`、`failed`、`canceled`。管理端轮询 GET，当状态为 pending 时打开 authorizationUrl。登录 session 上限 15 分钟，CLI 上游自身的更短超时仍生效；进程重启不恢复等待会话，需重新发起。

## 企业 SSO / oneid-token

清单只声明 `"auth_mode": "oneid-token"`，不声明 token_schema 或 oauth。Host CLI 直接读取 `AP_ACCESS_TOKEN`。stdio MCP 自动获得同名变量；若 SDK 需要其他变量名，可在 mcp.json 使用 `"env": {"SERVICE_TOKEN":"${AP_ACCESS_TOKEN}"}`。这是受管身份来源替换，不读取任意进程环境；`AP_ACCESS_TOKEN` 本身仍不能被 Agent/Skill/连接器配置覆盖。普通 MCP 子进程会清除继承的同名变量，不获得 SSO。

HTTP MCP 默认发送 Bearer Header，也可在动态 headers 中引用 `${AP_ACCESS_TOKEN}`；Authorization 若显式声明，仅接受 `Bearer ${AP_ACCESS_TOKEN}`。禁止在 URL、静态字段或其他占位符中使用 SSO。旧包所有 HTTP MCP 组件均使用 platform.authSource=identity-file 时，加载元数据自动归为 oneid-token，原文件不改写；离线迁移也会生成 oneid-token。

授权状态只表示当前 Desktop Token 是否可用，不验证上游权限。GET 返回 authorized/unauthorized；缺失、为空或非法时提示登录 Desktop，不阻止 Platform 启动。此模式不支持连接器的手工 Token 写入、交互登录或退出；SSO 登录/退出由 Desktop 管理。Token 更新后，HTTP 下次请求读取新值；stdio 下次调用检测身份变化并关闭旧 session、以新环境创建进程。Desktop 删除 Token 后，新的 MCP 调用拒绝执行，旧 stdio session 回收；已启动的普通 CLI 进程保持其启动时环境。

独立 `connector-manage status` 默认读取 `<runtime-dir>/identity/access-token`；使用 Desktop 管理的部署时，传入与 Platform 启动参数相同的 `--identity-file /absolute/path/sso-access-token.txt`。管理命令只读取这个文件，不复制、不刷新、不删除它。Terminal、Container、Proxy、ACP、LSP 与 sidecar 不通过此链路获得 Token。

## 静态 Token

`token_schema.fields` 定义 key、label、type（text/password）、required，可带 placeholder、description，text 可带公开 defaultValue；password 禁止默认值。兼容旧字段 name 作为 key；key 必须是唯一的大写字母、数字、下划线标识，以字母开头。保存接口只接受声明字段，检查必填、单行和每字段 64 KiB 上限，不验证第三方业务权限。PUT 请求上限 1 MiB，拒绝重复字段、未知请求属性与尾随 JSON。CLI 的 credentials-file 使用字段值对象 `{ "API_KEY": "用户填写值" }`，不使用内联命令参数传 Secret。

凭据原子写入 `.state/connectors/<id>/credentials.json`（0600），GET 只返回是否配置。HTTP MCP 的动态 headers/query 每次请求读取当前文件；query 只允许值中出现 `${KEY}`，替换后逐项 URL 编码，不允许凭据决定 host/path/query 参数名。源码 URL、catalog、SDK 原请求和错误保留模板，退出后旧 HTTP session 不能继续使用已删除的 Token。stdio env 按实例配置解析，凭据变更由 reload 重建实例。通用独立 CLI 的 token/OAuth env 注入适配尚未实现；自带认证的 CLI 使用 null。

## CLI 准备与隔离

宿主需要预装 Node.js/npm；tmeet 要求 Node >=14，wecom 要求 Node >=18。Platform 只安装 `cli.json.platform` 明确声明的 npm 包与固定版本，使用独立 prefix/cache，关闭 lifecycle scripts，不执行原 WorkBuddy 的全局 `init` shell 命令。`auth/status/unAuth` 只接受同一受管 CLI 的单条命令，不接受复合命令、重定向、变量展开或命令替换。

`null` 不要求任何 CLI 登录声明。仅 `cli.json.platform.npmPackage` 明确启用受管适配时，认证执行由配置声明，不按连接器 id 硬编码：`runtime` 检查 Node 主版本，`versionCheck.command/minVersion/versionPattern` 检查 CLI，`auth` 启动登录，`authUrlDomain` 限定返回链接，`status/statusMatch` 判定真实登录状态，`unAuth` 或 `platform.logoutMode` 退出。版本命令省略时使用 `--version`；`versionPattern` 若提供，第一捕获组必须是版本。WorkBuddy 的 `authQrModal` 只作为来源 UI 元信息，Platform 返回授权链接；登录始终等待命令退出并检查 status。

例如 tmeet 的 `cli.json.platform`：

```json
{"npmPackage":"@tencentcloud/tmeet","npmVersion":"1.0.16","entry":"scripts/tmeet.js","command":"tmeet","configEnv":"TMEET_CLI_CONFIG_DIR"}
```

各 Agent 运行包中的 `.platform-runtime.json` 只保存实际 stateDir 路径，不保存凭据；由 Platform 组装时生成，并适配已知旧版启动器。包内 `bin` 启动器用于 Host Bash/Terminal，自动设置 `TMEET_CLI_CONFIG_DIR` 或 `WECOM_CLI_CONFIG_DIR`，调用安装后的 CLI。目录布局：

```text
connectors-center/                 # 导入的外部原包
├── tmeet/
└── wecom/
ru-agents/<agentKey>/connectors/    # Platform 为当前 Agent 生成
├── tmeet/                         # 已挂载的清单、bin 启动器、skills
└── wecom/                         # 仅挂载时生成
.state/                            # Platform 通用持久化运行状态
└── connectors/                    # 不随运行包重建
    ├── tmeet/
    │   ├── npm/                   # 固定版本 CLI
    │   ├── npm-cache/
    │   └── config/                # 腾讯会议独立凭据
    └── wecom/
        ├── npm/
        ├── npm-cache/
        └── config/                # 企业微信独立加密凭据
```

企业微信没有正式 logout 子命令；包声明 `platform.logoutMode=delete-config`，只删除 `.state/connectors/wecom/config`。不删除用户默认的 `~/.config/wecom`。CLI 原始输出只在有界内存中检查，返回的登录 URL 必须属于包声明的 authUrlDomain。登录命令退出后再次执行 status，只有通过状态检查才返回 authorized。

Agent 挂载连接器即授权其运行包 CLI 执行。`wecom-cli auth show --status`、`message aibot sessions list` 和 `message aibot send` 等全部子命令，在 `default/auto_approve/full_access` 下都无需 Platform HITL 或自动审批审计；消息 JSON 和文件参数也不会再被当作普通脚本或目录访问单独审批。实际入口由运行包路径及内容摘要确认，原始命令和参数直接交给 CLI。登录未完成、目标不在企微允许的会话范围等业务错误仍按 CLI 实际返回处理。完整边界见 [连接器](连接器.md)。

这两个受管 CLI 的安装和凭据目前面向 Native Host。Container 不挂载 `.state`，因此不能直接复用 Host 登录或 npm 依赖。连接器目录 PATH 本身仍沿用现有容器挂载规则。

企业微信跨技能引用使用同包共享技能路径 `@connectors/wecom/skills/<name>/SKILL.md`。文档生成脚本在无 WorkBuddy 路径变量时使用 Platform 的 `AP_CHAT_DIR/AP_WORKSPACE_DIR`，读临时输入可使用系统 temp；该文档生成能力另需 Python 和 `python-docx`。

## 普通 OAuth 与 MCP OAuth

`auth_mode=oauth` 使用显式 `oauth.client_id`、`authorization_endpoint`、`token_endpoint`、`resource` 和可选 scopes。client_id 是预注册的公开客户端标识；不接受包内 client_secret。此流程直接打开授权端点，不探测 MCP 元数据、不动态注册，也不强制发送 MCP 的 resource 请求参数。当前支持 public client + PKCE；机密客户端、按 issuer 自动发现普通 OAuth 端点、服务端公共回调与上游 revocation 尚未实现。

```json
{
  "auth_mode": "oauth",
  "oauth": {
    "client_id": "public-client-id",
    "authorization_endpoint": "https://accounts.example.com/authorize",
    "token_endpoint": "https://accounts.example.com/token",
    "resource": "https://api.example.com",
    "scopes": ["documents.read"]
  }
}
```

`auth_mode=mcp` 通过官方 Go MCP SDK 校验资源/授权服务器元数据，并要求服务声明 PKCE S256。oauth 配置块可省略；可带 `resourceMetadataUrl`、`scopes`、`client_id` 和 `resource`，旧 discovery=true 兼容保留。不指定 client_id 时要求服务支持动态客户端注册；指定后跳过注册。未提供元数据地址时探测 MCP `WWW-Authenticate`，再尝试 endpoint 对应的 well-known 地址。暂未支持 client metadata documents 和完整发现回退策略。

OAuth resource 是授权 audience，默认使用 MCP URL；允许显式声明其他 HTTPS 资源标识，例如 QQ 邮箱 resource 为 `https://api.mail.qq.com`、MCP endpoint 为 `https://api.mail.qq.com/mcp`。元数据必须匹配声明的 resource，实际 Token 发送目的地仍严格绑定 MCP endpoint 的 scheme/host/path/query，不能借 resource 扩大范围。两个模式均不能混用 mcp.json 的 Authorization header 或 platform.authSource。

两个流程都使用随机 state、PKCE S256 和本机 loopback callback，浏览器必须能够访问 Platform 所在机器。默认监听临时 `127.0.0.1` 端口；预注册客户端如需固定回调，可提供 `oauth.redirect_uri`，仅接受 `http://127.0.0.1:<port>/<path>`。授权配置、Token、resource 与请求目的地以 0600 原子持久化至 `.state/connectors/<id>/oauth.json`，父目录 0700；已有单一资源的旧凭据兼容读取。每次 MCP 请求读取当前凭据，过期时跨进程加锁刷新并持久化 refresh token；本地 catalog 不等待网络或刷新锁。退出删除本地凭据，取消只影响当前管理进程的待完成登录。

认证按部署共享，未实现不同 Platform subject 的独立账号绑定。登录成功表示 CLI 或 OAuth 凭据获取成功；MCP 后台 tools/list 的服务可用性、SDK 支持的协商版本和业务侧权限仍需单独检查，不把登录成功等同于所有工具均可调用。Platform 优先请求 `2025-11-25`，也接受 `2025-06-18`、`2025-03-26` 和 `2024-11-05`，因此腾讯文档返回 `2025-03-26` 本身不会使同步失败；上游 HTTP 429 限流仍会独立报告。
