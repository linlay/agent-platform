# 配置化说明

Go runtime 的配置事实源分三层：

```text
代码默认值 < configs/*.yml < .env allowlist / 启动参数
```

`.env` 现在只作为启动/部署注入层。除本文列出的 allowlist 外，旧环境变量不再作为 runtime 配置入口；高级和低频配置统一写入 `configs/*.yml`，修改后需要重启服务。现场排障只保留明确列出的 debug allowlist。

## `.env` Allowlist

根 `.env.example` 只展示以下 key，也只有这些 key 会作为 `.env` 正式入口：

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `SERVER_PORT` | `11949` | 本地 `make run` 与 compose 外部入口端口；`--port` 启动参数优先级更高 |
| `AP_RUNTIME_DIR` | `runtime` | runtime 总目录 |
| `AP_RUNTIME_REGISTRIES_DIR` | `${AP_RUNTIME_DIR}/registries` | provider / model registry 根目录 |
| `AP_RUNTIME_CHATS_DIR` | `${AP_RUNTIME_DIR}/chats` | chat 落盘目录 |
| `AP_RUNTIME_MEMORY_DIR` | `${AP_RUNTIME_DIR}/memory` | memory 落盘目录 |
| `AP_RUNTIME_KBASE_DIR` | `${AP_RUNTIME_DIR}/kbase` | KBASE runtime 索引目录 |
| `AP_RUNTIME_PAN_DIR` | `${AP_RUNTIME_DIR}/pan` | pan 目录映射 |
| `AP_CONTAINER_HUB_BASE_URL` | 空 | Container Hub 服务地址；非空即启用 Container Hub |
| `AP_CHAT_RESOURCE_TICKET_SECRET` | 空 | resource ticket 签名密钥；设置后启用 `/api/resource` ticket 校验 |
| `AP_DEBUG_LLM_CONSOLE` | `request,usage` | 可选 LLM console 日志分类，逗号分隔 |
| `AP_DEBUG_LLM_CHAT_RECORD` | `false` | 是否记录 LLM chat completion JSON trace 并发送 `debug.llmChat` 事件 |

Windows release 包按 UTF-8 读取 `.env`。因此 `AP_RUNTIME_DIR` 及其目录覆盖项可以包含中文或其他非 ASCII 字符，不依赖 Windows PowerShell 5.1 的本地代码页。

不在 allowlist 里的旧环境变量会被忽略。resource ticket TTL 也不再有环境变量入口，请使用 `configs/runtime.yml -> resource.ticket-ttl-seconds`。

Platform 默认使用 `<AP_RUNTIME_DIR>/identity/access-token` 作为 identity 文件；`AP_RUNTIME_DIR` 未设置时根目录为 `<config-root>/runtime`，`~/...` 会展开到当前 Platform 进程用户的 home，相对路径按 canonical `--config-dir` 解析，最终 identity 路径固定为绝对路径。`--identity-file <absolute-path>` 是可选的最高优先级启动覆盖，不属于 `.env` 或 YAML 配置，Desktop 可继续用它传入 canonical access-token 文件路径。启动时不要求文件或父目录存在，也不读取、创建或缓存 token；文件可以在 Platform 启动后创建、替换或删除。Platform 每次新建普通 Agent Host Bash 时重新读取，成功时注入 `AP_ACCESS_TOKEN`，其他执行面不自动注入。

运行形态只由启动参数 `--runtime-mode=standalone|desktop` 决定，默认 `standalone`，非法值会使启动失败。Platform 不从端口、父进程、WebSocket `source`、环境变量或 YAML 推断运行形态；Desktop 启动内置 Platform 时固定传入 `--runtime-mode=desktop`。

## Server

本地运行约定：

- `make run` 会先加载根目录 `.env`
- `make run` 会先构建 `release-local/backend/agent-platform`，再从该二进制启动；KBASE PDF 使用 `build/builtins/<os>-<arch>/bin/pdftotext`，无需放置 plugin。
- `make run` 的端口链路为 `SERVER_PORT -> 11949`
- 直接执行 `go run ./cmd/agent-platform` 不会自动加载 `.env`
- 直接 `go run` 时，未设置 `SERVER_PORT` 或 `--port` 则代码默认监听 `8080`
- 服务端口不从 `configs/runtime.yml` 读取，最终优先级是代码默认 `8080` -> `SERVER_PORT` -> `--port`

## Runtime YAML

`configs/runtime.yml` 是运行时主配置入口，模板见 `configs/runtime.example.yml`。当前支持的顶层配置包括：

| YAML 节 | 说明 |
|---|---|
| `paths` | runtime 目录，例如 `tools-dir`、`owner-dir`、`agents-dir`、`ru-agents-dir`、`teams-dir`、`root-dir`、`automations-dir`、`kbase-dir`、`skills-center-dir`；高频目录仍可由 `.env` allowlist 覆盖 |
| `skills` | skills prompt 拼接限制，例如 `max-prompt-chars` |
| `query` | query 消息构造策略，例如 `advanced-user-prompt` |
| `auth` | `/api/**` JWT 鉴权开关、JWKS 地址、issuer 和 JWKS cache |
| `resource` | resource ticket TTL 等非敏感运行策略 |
| `budget` | run、model、tool、HITL/awaiting 超时和调用上限 |
| `automation` | automation orchestrator 开关、默认时区和 dispatch 并发 |
| `memory` | memory store 文件名、召回条数、上下文字符上限、搜索默认 limit 和混合检索权重 |
| `container-hub` | Container Hub URL、token、默认 environment、请求超时、sandbox 级别和回收策略 |
| `cors` | `/api/**` CORS 策略 |
| `billing` | 计费展示货币 |

`desktop_action`、`desktop_cdp` 和旧扁平 WebClient Action 均使用当前 run 的通用 `budget.tool.timeout`，不再有独立 `desktop:` YAML 配置。反向请求不生成 HTTP Bridge URL，也不存在 HTTP fallback。

### Query

`query.advanced-user-prompt` 默认关闭。开启后，native Go LLM 请求会把 provider-side user message 包装为 `advanced_user_prompt`，其中 `run_context` 只包含 runId、requestId、agentKey、teamId、role、当前时间、时区和 scene 摘要；真实用户请求位于 `user_message`。该开关不修改 `/api/query` 的原始 `message`，也不改变 PROXY / ACP CODER 的上游转发 payload。

### Auth / Ticket

Auth 默认开启，默认使用 `configs/local-public-key.pem` 本地公钥。需要 JWKS 时写入：

```yaml
auth:
  enabled: true
  jwks-uri: https://example.com/.well-known/jwks.json
  issuer: example-issuer
  jwks-cache-seconds: 60
```

本地公钥规则：

- 本地公钥文件固定为 `configs/local-public-key.pem`
- 该路径和文件名不是配置项
- 配置了 `auth.jwks-uri` 时走 JWKS 模式，不读取本地公钥文件
- `AP_CHAT_RESOURCE_TICKET_SECRET` 只负责 ticket 签名密钥
- ticket TTL 写在 `resource.ticket-ttl-seconds`

### Paths

默认目录来自 `AP_RUNTIME_DIR`。只在目录需要脱离 runtime 根目录时，才在 `configs/runtime.yml` 写 `paths`：

```yaml
paths:
  tools-dir: /data/agent-platform/tools
  owner-dir: /data/agent-platform/owner
  agents-dir: /data/agent-platform/agents
  ru-agents-dir: /data/agent-platform/ru-agents
  teams-dir: /data/agent-platform/teams
  root-dir: /data/agent-platform/root
  automations-dir: /data/agent-platform/automations
  kbase-dir: /data/agent-platform/kbase
  skills-center-dir: /data/agent-platform/skills-center
```

`ru-agents-dir` 默认是 `<AP_RUNTIME_DIR>/ru-agents`，会解析为绝对安全目录，并拒绝与其它 runtime 根目录相同或互相包含。它没有独立环境变量。`AP_RUNTIME_REGISTRIES_DIR`、`AP_RUNTIME_CHATS_DIR`、`AP_RUNTIME_MEMORY_DIR`、`AP_RUNTIME_KBASE_DIR`、`AP_RUNTIME_PAN_DIR` 仍保留在 `.env` allowlist；其它低频 runtime 子目录请写入 `paths.*`，旧目录环境变量不再生效。

共享 Skill 只接受 `paths.skills-center-dir`，默认值为 `<AP_RUNTIME_DIR>/skills-center`，没有独立环境变量。Platform 会在创建新目录和加载 Catalog 前检查已移除的旧 Skill 目录；一旦存在就终止启动，即使新目录也已存在。该检查不会移动、复制、合并或删除任何数据。

### MCP Registry

MCP server 不是 `configs/runtime.yml` 的内联配置，而是放在 `${AP_RUNTIME_REGISTRIES_DIR}/mcp-servers/*.yml`。runtime 使用官方 Go MCP SDK v1.6.1；`streamable-http` 与 `stdio` 都只接受协商版本 `2025-11-25`。

`transport` 缺省为 `streamable-http`。HTTP 配置必须有 `baseUrl`，可选 `endpointPath/authToken/headers/connect-timeout/read-timeout/retry`，不得出现 stdio 字段。stdio 配置必须有 `command`，可选 `args/env/workingDirectory/startup-timeout/read-timeout/retry`，不得出现 HTTP 字段。相对 `command` 和 `workingDirectory` 以当前 registry YAML 的目录为基准；子进程继承 Host runtime 环境和 builtin PATH。

```yaml
serverKey: qiuerscript
name: Qiuerscript
transport: stdio
command: ../../tools/qiuerscript/qiuerscript-tool
args: [serve, --datasource, dev]
env: {}
workingDirectory: ../..
startup-timeout: 5
read-timeout: 30
```

registry 加载和热重载采用原子替换。非法 transport、缺少必填字段或 HTTP/stdio 字段混用会硬失败，旧 snapshot 和现有 session 保持不变；合法变更生效时才关闭被删除或连接字段变化的 session/stdio 子进程。旧 tools-dir 私有 external stdio 配置已删除：`service.yml`、`type: external`、`external:` 与 `kind: external-service` 均为带迁移提示的硬错误。

### Container Hub

`container-hub.base-url` 默认使用 allowlist 中的 `AP_CONTAINER_HUB_BASE_URL`：

```yaml
container-hub:
  base-url: ${AP_CONTAINER_HUB_BASE_URL:http://host.docker.internal:11960}
  auth-token:
  default-environment-id:
  request-timeout: 300
  default-sandbox-level: run
  agent-idle-timeout: 600
  destroy-queue-delay: 5
```

除 `AP_CONTAINER_HUB_BASE_URL` 外，旧 Container Hub 环境变量和高级 Container Hub 环境变量不再覆盖 runtime 配置。token、environment id、超时和 sandbox 策略请直接写入 YAML，或由部署系统在启动前渲染 YAML。

Container Hub 默认基础挂载最多为：

- `/workspace` -> 当前 Agent 的 canonical Workspace（`rw`）
- `/chat` -> `AP_RUNTIME_CHATS_DIR/<chatId>`（`rw`）
- `/root` -> `paths.root-dir`（`rw`）
- `/skills` -> `paths.ru-agents-dir/<agentKey>/skills`（仅 `run/agent`，`global` 默认不挂载，`ro`）
- `/pan` -> `AP_RUNTIME_PAN_DIR`（`rw`）
- `/agent` -> `paths.ru-agents-dir/<agentKey>`（`ro`，必挂载；缺失时 fail-fast）
- `/owner` -> `paths.owner-dir`（`ro`，缺失时自动创建）
- `/memory` -> `AP_RUNTIME_MEMORY_DIR/<agentKey>`（`ro`，缺失时自动创建）

`runtimeConfig.sandboxMounts` 会真实影响 Container Hub session payload：

- `platform + mode`：按需平台挂载；`agent` / `owner` / `memory` 只覆盖默认挂载模式；`skills-center` 显式挂到 `/skills-center`
- `destination + mode`：覆盖非保留的默认基础挂载模式；`/workspace`、`/chat` 及其子路径不能覆盖
- `source + destination + mode`：新增非默认目标路径挂载

### Budget

通用预算写在 `configs/runtime.yml`：

```yaml
budget:
  timeout: 3600
  max-steps: 100
  model:
    max-calls: 100
    timeout: 180
    retry-count: 5
  tool:
    max-calls: 100
    timeout: 600
    retry-count: 0
  hitl:
    timeout: 600
    question:
      timeout: 600
    approval:
      timeout: 600
    form:
      timeout: 600
```

配置项中的 HITL timeout `0` 表示未配置；事件协议中非 planning confirmation 的 `awaiting.ask.timeout=0` 表示该等待项无限等待、不自动超时。`awaiting.ask.timeout>0` 由后端按真实时间独立计时，前端 observer / attach / detach 状态不会暂停或延长后端超时。CODER `finalize_planning` 产生的 planning confirmation 永久等待：它不读取 `budget.hitl.plan`，且 `awaiting.ask(mode:"planning")` 不发送 `timeout` 字段；遗留 `budget.hitl.plan` 会被静默忽略。CODER 的阶段配置使用 `stageSettings.planning` 与 `budget.stages.planning`；`defaults.coder-planning.max-steps` 是其专属默认值。

Anthropic 请求的 `max_tokens` 默认值是源码内部常量 `4096`；stage 级 `maxOutputTokens` 仍可显式覆盖。

### Memory / Chat Storage

runtime memory 行为写入 `memory` 节：

```yaml
memory:
  enabled: true
  db-file-name: memory.db
  context-top-n: 5
  context-max-chars: 4000
  search-default-limit: 10
  hybrid-vector-weight: 0.7
  hybrid-fts-weight: 0.3
  dual-write-markdown: true
```

agent definition 侧另有 `memoryConfig`，用于决定某个 agent 是否注入 `memory_write`、`memory_read`、`memory_search` 以及管理类 memory tools。`memory/memory.md` 属于 agent 静态背景提示，不等同于 runtime memory store。chat 回放窗口固定为最近 20 个 run，SQLite 索引文件固定为 `chats.db`，不提供 runtime YAML 配置。

### KBASE

KBASE 是独立于 memory 的文本知识库公共能力。`configs/kbase-settings.yml` 负责新建专用 KBASE Agent 的默认回答模型、全局 embedding modelKey、Lance 索引/维护策略、refresh 调度和文档抽取；默认索引目录来自 `paths.kbase-dir`。include/exclude、chunk 与 retrieval 参数写在 Agent 的 `kbaseConfig` 中；所有 enabled KBASE 都必须通过 `runtimeConfig.workspaceRoot` 提供唯一内容根。`mode: KBASE` 自动启用，`REACT`、`PLAN-EXECUTE` 与原生非 ACP `CODER` 附加能力时必须显式配置 `enabled: true`。

对专用 `mode: KBASE`，最终 canonical `runtimeConfig.workspaceRoot` 是 main/editing 两种 run 的唯一 Workspace。旧 `kbaseConfig.source` 会硬失败。当前 Chat 目录始终独立保存在 `ChatDir`。专用 KBASE 两种 stage 都提供相同的五个文件工具，`editingMode:true` 只允许 KBASE Workspace mutation；普通 Agent 附加 KBASE capability 复用其既有 Workspace，不改变原有文件工具或 Memory 配置。

```yaml
paths:
  kbase-dir: ./runtime/kbase
```

`configs/kbase-settings.yml`：

```yaml
default-agent:
  modelKey: deepseek-v4-pro
  reasoningEffort: MEDIUM
embedding:
  modelKey: babelark-text-embedding-v4
index:
  fts:
    base-tokenizer: icu
  vector:
    ann-min-rows: 50000
maintenance:
  optimize-change-threshold: 1000
  optimize-interval: 24h
  version-retention: 168h
refresh:
  debounce: 2s
  reconcile-interval: 10m
```

旧示例中位于 `runtime.yml -> kbase` 的同名配置不再读取。

KBASE 固定使用 LanceDB。全局 `storage` 与整个 `migration` 配置段均已废弃，出现任一键会使启动配置加载失败；`control.db` 仍使用 SQLite，但只记录 generation、文件状态、refresh run 和恢复日志，并且仅接受当前 schema。启动期可认领完整匹配的 `0/0` 无标记库；其他旧 `kbase.db`、旧 generation 或结构不匹配的 `control.db` 不会被改写。专用 KBASE mode 会隔离对应 Agent，普通 Agent 的 optional capability 则保留 Agent 并报告 degraded。`ann-min-rows` 不得小于 1000；低于门槛时使用 cosine flat search，达到门槛时尝试 `IVF_HNSW_SQ`，recall@10 低于 0.95 会删除 ANN 索引并保持 flat。`optimize-change-threshold` 控制累计新增/修改 chunk 触发 delta index refresh 的门槛；`optimize-interval` 控制完整 compact/index merge/prune，watcher 单文件变化不会同步执行完整 optimize。

`default-agent.modelKey` 与 `default-agent.reasoningEffort` 只在通过 `/api/admin/agents/create` 创建专用 KBASE Agent 且请求未显式传 `modelConfig.modelKey` / `modelConfig.reasoning.effort` 时写入 Agent 配置；手写 Agent 文件仍必须包含最终的 `modelConfig`。`embedding.modelKey` 会在新建 KBASE 且请求缺少 embedding modelKey 时写入 Agent 配置，并在运行时解析到 `models/*.yml` 中 `type: embedding` 的 provider、真实 `modelId`、dimension、timeout 与 endpoint。`kbaseConfig.tags` 是公开调度元数据，只接受字符串列表，不参与索引 hash 或检索，也不进入 Channel Agent v1 注册。`kbaseConfig.embedding` 只接受 `modelKey`，旧式 `providerKey/model/dimension/timeout` 不再读取。`kbaseConfig.embedding.modelKey` 只用于知识库索引和检索，不控制回答模型或思考程度。`kbaseConfig.chunk` 是 Agent 级配置；未配置时默认使用 `unit: estimatedTokens`、`maxTokens: 1000`、`overlapTokens: 100`。字符切块必须显式写 `unit: chars`，再使用 camelCase 的 `maxChars` / `overlapChars`；未写 unit 的字符字段、kebab-case retrieval 键和 unit 别名会被拒绝。只接受 canonical retrieval 键 `topK`、`rrfK`、`vectorWeight`、`ftsWeight`、`candidateFloor`、`candidateMultiplier`、`candidateMax`。`estimatedTokens` 是 runtime 本地启发式估算，不是 provider 或 embedding 模型 tokenizer 的精确 token。默认 storageDir 为 `${paths.kbase-dir}/${agentKey}/`；Agent 也可通过 `kbaseConfig.storage.location: workspace` 改用 `${runtimeConfig.workspaceRoot}/.kbase/`。一个 canonical storageDir 只能由一个 Agent 占用，共用会在启动校验时失败。所有 enabled capability 的 canonical Workspace 必须与 `${paths.chats-dir}` 完全分离，且不能是文件系统根；相等、互为父子或 symlink 实际重叠时仅隔离对应 Agent。KBASE capability 不读取 memory embedding 配置。

agent 级 retrieval 默认为：

```yaml
kbaseConfig:
  tags: [docs, knowledge-base]
  retrieval:
    topK: 8
    fusion: rrf
    rrfK: 60
    vectorWeight: 0.7
    ftsWeight: 0.3
    candidateFloor: 30
    candidateMultiplier: 4
    candidateMax: 500
```

`topK` 为 1–50；两个 weight 必须非负且不能同时为 0；`rrfK` 为 1–1000；`candidateFloor >= topK`，`candidateMax >= candidateFloor` 且不超过 2000。retrieval 调整只改变 `queryHash`，不重建索引；embedding/chunk/include/exclude/extraction/FTS tokenizer/schema 等改变 `indexHash` 的配置才创建新 generation。

详细的目录、迁移、恢复和分发边界见 [KBASE LanceDB 迁移](KBASE-LanceDB迁移.md)。

### Automation

Automation 策略写入 YAML：

```yaml
automation:
  enabled: true
  default-zone-id: Asia/Shanghai
  pool-size: 4
```

未在单个 automation YAML 中写 `environment.zoneId` 时，cron 会跟随这里的 `automation.default-zone-id`；该值无效或未配置时回退进程 `time.Local`。只有跨时区任务或必须锁定不同业务时区的任务，才需要在 automation YAML 中显式写 `environment.zoneId`。

Logging 默认值已经源码化，不提供 runtime YAML 入口：request/auth/exception/tool/action/viewport/memory/LLM interaction 默认开启，SSE 默认关闭；LLM console 默认分类为 `request,usage`，mask 默认关闭，record 默认关闭。`AP_DEBUG_LLM_CONSOLE` 和 `AP_DEBUG_LLM_CHAT_RECORD` 是保留给现场排障的 allowlist 覆盖。

run lifecycle、WebSocket、H2A render、默认 locale、chat history 窗口和 logging 默认值都是内部常量，不提供 runtime YAML 配置入口。WebSocket 不读取 SSE heartbeat 配置；Ping、Pong timeout、应用 heartbeat 和客户端静默阈值分别由独立的 WebSocket 配置字段持有，默认 30/60/30/100 秒。默认 locale 固定为英语 `en`，请求可通过 query/header/Accept-Language 显式覆盖。

## Tools / AI Tools / Prompts / Channels

工具运行时配置已合并到：

- `configs/tools.yml`：access policy、Bash、FileTools、sandbox bash，以及 `platform-control` 的全局开关、追加 denylist 和 run-env 限额；effective default read/write roots 总会追加进程启动时冻结的 `@temp`。写操作先匹配当前 level readonly 与 Platform trusted run readonly，命中后不会进入 hostAccess 或 HITL；`mustUseSkills` 的 selected-only run roots 不写入该配置
- `configs/ai-tools.yml`：`vision_recognize`、`web_fetch`、`image_generate` 等模型能力工具
- `configs/prompts.yml`：全局、plan-execute、BTW 与 memory prompt 文案；`btw.user-prompt-template` 用于隐藏“顺便问”的冻结快照边界，`btw.final-answer-prompt` 用于读工具额度耗尽后的收尾回答。该文案只在 user message 中生效，不替代后端 read-only 工具策略。
- `configs/coder-prompts.yml`：CODER 专属 prompt 文案
- `configs/kbase-prompts.yml`：KBASE 专属 prompt 文案
- `configs/channels.yml`：channel 连接配置。只接受 `mode`、`transport`、`protocol`、`endpoint`、`auth`、`heartbeat`、`reconnect`；`mode: client` 表示 platform 主动连外部，`mode: server` 表示开放 `/ws/channel` 等待外部连接；`transport` 默认 `websocket`，`protocol` 默认 `platform-ws`。`type`、`default-agent`、`agents`、`gateway` 已移除，出现即加载失败。Agent 的外部接入/本地接出关系不写在 channel 中，分别由 `mode: CHANNEL + remoteAgentKey` 和普通 Agent 的 `channelConfig.exports` 表达；两种建连方向都支持接出注册 v1。
- `configs/coder-settings.yml`：CODER 专属运行策略、ACP `acp-bridges`（`timeout-ms` 默认 `300000`），以及新建 CODER agent 时写入的 `default-agent` 默认值；该文件仅在启动时读取，修改后需要重启 runtime
- `configs/kbase-settings.yml`：KBASE 默认 agent、embedding、refresh 与文档抽取策略

旧拆分文件 `access-policy.yml`、`bash.yml`、`file-tools.yml`、`memory-prompts.yml`、`vision-recognize.yml`、`container-hub.yml`、`desktop.yml`、`cors.yml` 不再读取。

`vision_recognize` 的 `images` 固定为非空数组，单张图片也不接受单对象或字符串简写。当前 Chat 附件优先使用 `reference_name`，显式本地路径使用经权限校验的 `file_path`：

```json
{"images":[{"reference_name":"image.png"}],"prompt":"识别全部内容"}
```

```json
{"images":[{"file_path":"@chat/image.png"}],"prompt":"识别全部内容"}
```

Agent 必须在 `toolConfig.tools` 显式配置 `platform_control`，挂载后即可调用全部注册 operation。所有 Agent 看到相同固定 Schema；Skill、`mustUseSkills` 与 Skill 热重载不能替 Agent 挂载 Tool。run env 无需预声明 key，仅当前普通 native root run 可调用 `run.env.set/unset`；动态值只存在于当前 Platform 进程内，重启后的续接 run 使用空动态层。遗留 `runtimeConfig.runEnv` 静默忽略。`platform-control` 配置节是可选的，省略时使用代码默认限额；只有需要调整单值/总量/key 数限制或追加 deny key 时才需声明。旧 `platform-control.profiles` 与 `platform-control.bindings` 已移除，出现时启动硬失败。修改 denylist 或限额后需要重启。

### 已移除配置的迁移对照

不提供自动迁移。请在部署前手工完成以下替换；旧输入会在加载或写入时明确失败。

| 已移除输入 | 必须使用的当前配置 |
|---|---|
| `runtime/teams/<teamId>.yml|yaml`、`defaultAgentKey` | `runtime/teams/<teamId>/team.yml`，配置 `orchestrator`；Team 请求与 automation 只传 `teamId` |
| channel 的 `type`、`default-agent`、`agents`、`gateway` | canonical channel 的 `mode/transport/protocol/endpoint/auth/heartbeat/reconnect`；agent 导入/导出写入 `channelConfig` |
| `ACP-PROXY`、`ACP_PROXY` | `PROXY` |
| `PLAN_EXECUTE` | `PLAN-EXECUTE` |
| `ONESHOT` | `REACT`；ONESHOT 仅为 compact 进程内模式 |
| 未写 `unit` 的 `maxChars/overlapChars`、kebab-case retrieval 键、unit 别名 | 显式 `chunk.unit: chars` + camelCase 字段，或使用默认 `estimatedTokens` |

## Provider / Model Registry

provider 和 model registry 位于 `AP_RUNTIME_REGISTRIES_DIR/providers` 与 `AP_RUNTIME_REGISTRIES_DIR/models`。model registry 通过 `type` 区分调用契约，未写 `type` 时等价于 `type: chat`：

- provider `apiKey` 按明文字符串读取；未配置时保留为空值
- runtime 不再支持 provider `apiKey` 加密或解密
- provider `baseUrl` 只从 provider YAML 读取；provider 动态 base URL 环境变量不再覆盖
- 除 PROXY 与 ACP CODER 外，agent 最终必须配置 `modelConfig.modelKey`；运行时不会再通过 provider `defaultModel` 为 agent 隐式选择回答模型，管理接口新建 CODER / KBASE 时可分别用专用 settings 的 `default-agent.modelKey` 和 `default-agent.reasoningEffort` 代填模型配置。CODER 的 `default-agent.budget` 也只在创建时写入 agent.yml，不作为运行时动态覆盖。PROXY 的请求级 `model` 字段由上游代理服务解释，不要求存在于本地 model registry。
- KBASE embedding 解析优先级为 agent `kbaseConfig.embedding.modelKey` > `configs/kbase-settings.yml -> embedding.modelKey`；旧式 `providerKey/model/dimension/timeout` 不再读取。
- model 输入上下文字段为 `maxInputTokens`
- `name` 是模型显示名；可选 `icon` 是返回给前端的模型家族图标标识，例如 `glm`、`kimi`、`chatgpt`、`gemini`、`claude`、`qwen`、`minimax`、`mimo`、`deepseek`，未配置时接口省略该字段
- `type: vl` 是视觉语言模型的专用类型，只能由 `vision_recognize` 的 profile 引用，不可作为 agent 回答模型或聊天输入区模型选项；配置该工具的模型时不再使用 `isVision: true` 作为类型判断。
- chat model 顶层 `timeout` 可选，单位秒；配置后会覆盖 `budget.model.timeout`，作为该模型的流式 idle timeout。适合 MiniMax / transit-hub 等首包或中途思考可能超过默认 180 秒的模型。
- native `type: chat`、`protocol: OPENAI` 模型可选配完整的 `reasoningEffortMapping`，将平台统一逻辑档位 `LOW/MEDIUM/HIGH/XHIGH/MAX` 翻译为 provider 实际档位。映射必须完整覆盖五档，键和值只能使用这五个大写值；允许多个逻辑档位映射到同一实际档位，禁止 `NONE`。`NONE` 始终关闭 reasoning 并省略 provider 的 `reasoning_effort`。未配置映射时保持原有请求，不自动添加该字段。ACP passthrough、非 OPENAI 或非 chat 模型声明该字段会加载失败。
- stage 输出上限字段为 `maxOutputTokens`
- 旧 `contextWindow` 与 `maxTokens` 配置字段不再读取

Chat model 示例：

```yaml
key: th-minimax-m3
name: MiniMax M3 via Transit Hub
icon: minimax
provider: transit-hub
type: chat
protocol: OPENAI
modelId: minimax-m3
maxInputTokens: 200000
timeout: 300
```

DeepSeek Flash 映射示例：

```yaml
key: deepseek-v4-flash
provider: deepseek
type: chat
protocol: OPENAI
modelId: deepseek-v4-flash
isReasoner: true
reasoningEffortMapping:
  LOW: LOW
  MEDIUM: HIGH
  HIGH: HIGH
  XHIGH: HIGH
  MAX: MAX
```

映射只在构造 OpenAI-compatible provider 请求时生效，并以小写写入顶层 `reasoning_effort`；Agent YAML、API、事件和 usage 始终保留大写逻辑值。管理端 registry YAML 校验与 runtime 启动加载使用相同的映射约束，映射内容不通过 catalog API 回显。

Image generation model 示例：

```yaml
key: babelark-gpt-image-2
name: GPT Image 2
provider: babelark
type: image-generation
protocol: OPENAI
modelId: gpt-image-2
image:
  timeout: 180
  defaultSize: 1024x1024
  responseFormats:
    - b64_json
    - url
  generation:
    endpointPath: /v1/images/generations
    requestFormat: openai-images-json
  edit:
    endpointPath: /v1/images/edits
    requestFormat: openai-images-multipart
    maskProtocol: openai-alpha
```

`image_generate` 对 Agent 始终暴露同一套参数。没有 `images` 时按 `image.generation` 文生图；传入 `images` 时，`images[0]` 是编辑主体，其余最多三张是参考图，并按 `image.edit` 适配请求。路由不识别模型名或 provider，只读取模型 YAML：

- generation 的 `openai-images-json`：向 `image.generation.endpointPath` 发送 `model/prompt/size/response_format/n` JSON。
- edit 的 `openai-images-multipart`：向 `image.edit.endpointPath` 发送重复的 `image[]` multipart part；`maskProtocol: openai-alpha` 时还允许发送归一化后的 `mask`。
- generation/edit 的 `openai-chat-completions`：把 prompt 和可选输入图组装为 OpenAI chat content blocks，并发送图像输出 modalities；edit 只允许 `maskProtocol: none`。

`image.generation` 必须同时配置 `endpointPath` 和合法 `requestFormat`；缺失、未知格式或旧的顶层 `image.endpointPath` 都会使启动失败。`image.edit` 可省略，但一旦出现也必须完整配置。`maskProtocol` 只接受 `none` 或 `openai-alpha`，后者只能与 `openai-images-multipart` 组合；启动加载和管理端 registry 校验都会拒绝非法组合。未声明 `image.edit` 的模型仍可文生图，但图生图返回 `image_generate_edit_unsupported`；mask 能力为 `none` 时返回 `image_generate_mask_unsupported`，不会自动换模型或退化为提示词近似编辑。

`configs/ai-tools.yml -> image-generate.profiles.*` 只选择 `model-key` 和工具级限制，不再允许 `endpoint-path` 覆盖；旧字段会使启动失败。`max-images` 默认 `4`，`max-image-bytes` 默认 `20971520`，同时约束输入图和 mask 的单文件大小。`profile` 的工具 schema 在启动时注入已配置 profile 的排序 enum，省略时使用 `default-profile`。

图片与 mask 来源统一使用 `{source_type, value}`。`source_type` 只接受 `reference_name`（当前 Chat 附件文件名）或 `file_path`（经 AccessPolicy/HITL 检查的本地路径），`value` 必须是非空字符串。例如：

```json
{"prompt":"remove the watermark","images":[{"source_type":"reference_name","value":"image.png"}],"mask":{"source_type":"file_path","value":"@chat/mask.png","mode":"white_edit"}}
```

这是不兼容迁移：字符串数组以及旧的 `reference_name`、`file_path` 属性均不再接受；`vision_recognize` 的入参不受影响。HTTP URL 仍不可作为图片来源，也不会隐式读取全部附件。

name: Qwen VL Max
provider: qwen

### OpenAI compatible `compat`

OpenAI-compatible provider 可在 `protocols.OPENAI.compat` 配置默认请求兼容项；chat model 可在顶层 `compat` 配置单模型覆盖项。两层按对象深度合并，优先级为 model > provider。例如，适用于 provider 全部模型的默认值可放在 provider：

```yaml
protocols:
  OPENAI:
    compat:
      messages:
        preserveReasoningContent: true
      request:
        whenReasoningEnabled:
          chat_template_kwargs:
            thinking: true
            return_reasoning: true
```

仅某个模型支持的参数应放在 model，避免误传给同一 provider 的其他模型：

```yaml
key: our-deepseek-v4
provider: our-deepseek
protocol: OPENAI
modelId: DeepSeek-v4
compat:
  request:
    whenReasoningEnabled:
      chat_template_kwargs:
        thinking: true
        return_reasoning: true
```

`whenReasoningEnabled` 仅在 agent 的 `modelConfig.reasoning.enabled: true` 时写入模型请求。流式响应中的 `delta.reasoning_content` 与 `delta.reasoning` 都会被 runtime 归一化为既有的 `reasoning_content` 语义，供 SSE、会话持久化和后续模型调用使用；同一 delta 同时存在两者时优先 `reasoning_content`。

## Compose 目录映射

`compose.yml` 会把宿主机 runtime 根目录映射到容器内固定路径，并允许四个高频子目录单独覆盖：

| 宿主机来源 | 容器内路径 |
|---|---|
| `${AP_RUNTIME_DIR:-./runtime}` | `/opt/runtime` |
| `${AP_RUNTIME_REGISTRIES_DIR:-${AP_RUNTIME_DIR:-./runtime}/registries}` | `/opt/runtime/registries` |
| `${AP_RUNTIME_CHATS_DIR:-${AP_RUNTIME_DIR:-./runtime}/chats}` | `/opt/runtime/chats` |
| `${AP_RUNTIME_MEMORY_DIR:-${AP_RUNTIME_DIR:-./runtime}/memory}` | `/opt/runtime/memory` |
| `${AP_RUNTIME_PAN_DIR:-${AP_RUNTIME_DIR:-./runtime}/pan}` | `/opt/runtime/pan` |

容器内应用会设置 `AP_RUNTIME_DIR=/opt/runtime`，并把 runtime 子目录同步为对应 `/opt/runtime/*` 路径；容器内应用监听端口固定为 `8080`。
