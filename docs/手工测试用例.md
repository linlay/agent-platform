Identity 文件动态注入 Host Bash：

1. 不传 `--identity-file` 启动 Platform，令 `<AP_RUNTIME_DIR>/identity/access-token` 先保持不存在，通过 `test -z "${AP_ACCESS_TOKEN+x}"` 确认普通 Agent Bash 中没有该变量。
2. 不重启 Platform，写入合法单行 token，通过只检查存在性或预期哈希确认下一次 Bash 获得新值；原子替换文件后下一次 Bash 使用替换值，删除文件后下一次 Bash 不再包含该变量。测试输出不得打印 token 原文。
3. 另建 token 文件并使用 `--identity-file <absolute-path>` 启动，确认显式文件覆盖 `<AP_RUNTIME_DIR>/identity/access-token`。
4. 设置父进程或 Agent runtime env 的同名变量，确认不能绕过有效 identity 文件；Agent/Skill/调用级声明应以保留变量错误拒绝。
5. 确认 Workspace Terminal、`file_grep/file_glob`、Container、Proxy、ACP、MCP、LSP 与 sidecar 未自动获得 `AP_ACCESS_TOKEN`，已有 Bash 不因文件变化被中断。

### `platform_control` 与 run-local env

准备两个显式挂载 `platform_control` 的普通 native Agent：`online-office` 与 `zenmi`。Agent YAML 不声明 `runEnv`，也不要修改 `POST /api/query` 请求结构。

1. 分别让两个 Agent 调用 `capabilities.list`，确认 run env 只暴露 `run.env.set/unset`，且结果不含 `profiles`。移除 Agent 的显式 tool 后不得看到或调用工具；临时加入任意 Skill 或 `mustUseSkills` 也不能替 Agent 挂载该工具。
2. 两个 Agent 调用 `runtime.status` / `catalog.validate` 均应成功；planning/read-only stage 仍不得调用 mutation，Team/子 Agent 仍不得修改 run env。
3. 先由 httpx create/upload 取得 UUID，再调用 `run.env.set`。同值不提升 revision；相同 idempotencyKey 重试返回原成功结果。再次 set 不同 UUID 应覆盖并提升 revision。
4. 调用旧 bind/get/list/bulk，确认均返回 `platform_control_invalid_operation`。检查 SSE、attach backlog、Chat JSONL、raw messages、LLM trace、archive、export 与 search，set value 应原样存在且不得出现 `[REDACTED]`/`valueBytes`，idempotency key 仍不得出现；成功结果只含 key/changed/idempotent/revision。
5. 验证 set → Bash/PowerShell/httpx/dbx/Node/Python/rg 读取 → unset。只有当前 run 已 set 的 key 才能 unset；未 set、重复 unset、其他 run set 的同名 key均返回 `run_env_key_not_set`。若 Host/Agent/Skill 有同名值，unset 后新子进程回退该低层值。Platform 自身 `os.Getenv` 必须始终不变。
6. 单次 assistant 回复按 `[run.env.set, bash]` 顺序调用时 Bash 读取新值；逆序时 Bash 只看到旧 revision。空字符串和多行值应成功，NUL、非法 UTF-8、denylist、单值/总量/key 数超限应失败；请求中的 value 仍按普通 Tool 参数可观测。
7. 使用错误 expectedRevision 应返回 `run_env_revision_conflict`；并发首次 set 只能形成一个线性 revision，set/snapshot 只能观察完整旧 revision 或完整新 revision。两个并行 root run 不得串值，`run_query` 新 root 不继承。
8. Container 复用同一 session 连续执行 command：新 command 看到新动态值，unset 后回退静态值；session reuse key 不因 revision 改变。已启动的后台进程保持旧环境。
9. 子 Agent即使复用 root RunID 也不得取得 scope；Team、Workspace Terminal、MCP stdio/HTTP、ACP、Proxy、Channel、LSP、KBASE sidecar 与长期服务不得获得动态值。
10. 在独立临时 runtime 根执行 set/unset，确认不会创建任何 run-env 状态文件。Platform 重启后，question/planning 仍按原协议恢复，但动态 Scope 必须为空且 revision 为 0；不得从 Chat 中的历史 set/unset 重放。
11. 正常完成、失败、interrupt 与 budget stop 后，确认旧 Scope 已关闭且无法再次访问；新 run 和重启恢复的 run 均不得继承旧动态值。

Windows 还需在真实 Windows CI/主机分别覆盖 PowerShell、`CreateProcess`、直接 `.exe`、环境变量名大小写冲突和 `%SystemRoot%` 等 hard deny；不能只依赖交叉编译。

online-office 端到端用例固定为 capabilities.list → create/upload → `platform_control run.env.set` → session/edit/commit/download。同一 run 切换文档时再次 set，并重新建立、验证对应 session/lease。检查 Skill 不含 `/bin/sh` 或内联 `KEY=value httpx`。

### `mustUseSkills` selected-only 目录授权

准备一个挂载 `file_read/file_write/file_edit` 的普通 Agent、一个已配置 Skill `configured-skill`，以及技能中心的 `selected-extra` 和 `unselected-extra`：

1. 使用 `mustUseSkills:["configured-skill","selected-extra"]` 发起 default access run，确认读取两个 Skill 的 `SKILL.md`、scripts、references 和 assets 都不产生 `awaiting.ask`。
2. 同一 run 读取 `@skills-center/unselected-extra/SKILL.md`，确认仍进入 `file_read` AccessPolicy HITL；选择一个 Skill 不得开放整个技能中心。

4. 在选中 Skill 内建立指向目录外的 symlink/junction（平台允许测试环境建立时），确认按最终 canonical 目标重新判权，不继承选中目录 grant。结束 run 后重新发起未带 `mustUseSkills` 的请求，确认 grant 不继承。

### Agent ZIP 导入

准备一个根目录包含 `agent.yml` 的完整 Agent ZIP；也应接受只多一层包装目录且使用 `agent.yaml` 的 ZIP：

```bash
curl -sS -X POST "$BASE_URL/api/admin/agents/import" \
  -F 'file=@./portable-agent.zip;type=application/zip'
```

成功响应应返回导入 Agent 的 admin detail，且 prompt、`skills/`、`.config/`、知识文件和其他普通资源均完整保留。Agent Key 必须来自 YAML，接口不接收 Key 表单字段。再次导入相同 Key 应返回 409，且 `data.error.overwriteRequired=true`；确认后用同一文件重试：

```bash
curl -sS -X POST "$BASE_URL/api/admin/agents/import" \
  -F 'overwrite=true' \
  -F 'file=@./portable-agent.zip;type=application/zip'
```

旧目录中的 `.config`、专属 Skills 和资源应被完整替换而不是合并；覆盖平铺 YAML 来源后，应只保留规范目录型来源。导入一个语法和公共 mode 合法、但引用本机不存在 Workspace、模型、工具、KBASE 或 Skill 的 Agent 时，应以 200 返回 `status="invalid"` 与 diagnostics，并保留磁盘来源。缺失或同时包含 `agent.yml` / `agent.yaml`、包含 `../`、反斜杠、symlink、大小写冲突、重复路径或文件/目录冲突的 ZIP 应返回 422；非 ZIP 返回 415；超过 32 MiB 上传/单文件、256 MiB 解压总量或 4096 entry 返回 413。可通过制造 catalog 硬重载失败验证 staging/backup 回滚：新 Key 不留半成品，覆盖旧 Key 后旧来源恢复。

导入一个根目录包含 `SKILL.md` 的完整 ZIP；也应接受只有一层包装目录的 ZIP：

```bash
curl -sS -X POST "$BASE_URL/api/admin/skills/import" \
  -F 'key=imported-skill' \
  -F 'file=@./imported-skill.zip;type=application/zip'
```

成功响应应返回 `data.skill.key="imported-skill"` 和 `data.openedFile.path="SKILL.md"`。再次使用相同 Key 应返回 409；缺少 `SKILL.md` 或包含 `../`、symlink、无效 `.runtime-env.json` 的 ZIP 应返回 422 和 `data.error.diagnostics[]`，且 `skills-center/imported-skill` 不得留下半成品。非 ZIP 返回 415，超过压缩、单文件、总解压量或 4096 entry 限制返回 413。

### 分层上下文压缩

1. 先备份真实 Chat 的 JSONL、资源目录、SQLite Chat/Run 元数据与 SHA256；不直接修改原 Chat，使用 `/api/chat/derive` 创建 L1 历史、L2 历史、活动 Run 和自动压缩副本。
2. 对含已完成大工具结果的副本发送 `level:"l1_tools"`。确认普通 user/assistant 内容逐字不变，白名单工具组替换为带 tool/toolCallId/status/path/SHA/头尾片段的结构化记录，不调用模型；单个大工具组也允许压缩。再对只有一个已结束大 Run 的副本发送：

```bash
curl -sS -X POST "$BASE_URL/api/compact" \
  -H "Content-Type: application/json" \
  -d '{"requestId":"compact-history-1","chatId":"replace-derived-chat","trigger":"manual","level":"summary"}'
```

确认 `accepted:true/status:"completed"/scope:"history"`，单 Run 整体进入摘要；两个 Run 时只保留最后一个，三个及以上默认保留最后两个。只有已压缩历史或没有终态 Run 时才返回 `skipped/no_compactable_history`。

3. 用小 Context Window fake provider 运行普通 Agent，分别对 L1/L2 在模型流、工具执行、question/approval/form 等待、最终 Turn 边界发送请求。请求在安全点之前必须保持阻塞；流/Tool 自然结束后依次看到 `context.compact.start`、`context.compact.complete`，再看到下一次 `llm.request` 或 `run.complete`。工具只执行一次，HITL 保留同一 `awaitingId`。
4. 检查 `<chatId>.jsonl` 追加 `_type:"compact.run.checkpoint"`；其 `messages` 只在 raw JSONL 审计中可见，`GET /api/chat`/SSE/WS 不得回显。连续执行 L1/L2 后刷新只按各 `compactId` 回放一次完成事件，后续 Query 使用最新 checkpoint 与它之后的 step。
5. 以相同 `requestId` 并发重试，确认共享同一 `compactId` 和结果；用不同 request 重复提交时返回 `busy/compact_in_progress`。中断 HTTP/WS 客户端后任务仍完成并可回放；Interrupt 则返回 `failed/run_interrupted`。
6. 在历史压缩 lease 持有期间发新 Query，确认以可重试 `409 compact_in_progress` 拒绝且未注册 Run。ACP/PROXY/CHANNEL/BTW 活动 Run 返回 `unsupported_active_run`；普通 Agent/Team 协调器活动 Run 的 L1/L2 都可执行。
7. 注入摘要空响应、模型错误或单次输入预算不足，确认分别返回 `summary_empty`、`summary_model_failed`、`summary_input_too_large`，上下文不变、无 checkpoint、无规则兜底；注入 checkpoint 写入失败，确认不发布 compact complete，而是发布 `context.compact.failed(detail:"compact_persist_failed")` 和 `run.error`，且没有后续模型调用。Provider 连续两次 context-length 溢出时，第一次按 L1→必要时 L2 压缩后重试，第二次以 `context_window_uncompactable` 终止。
8. 将完整请求推高到自动阈值，确认事件顺序先为 L1 start/complete；若 L1 后低于 60% 则不调用摘要模型，仍高于 60% 才追加一次 L2 start/complete。L2 失败时不得开始下一次模型调用。

### Chat 自动审批与 Temp 临时脚本免审批

选择同时启用 `file_write` 与 Bash 的普通 Agent，使用 `auto_approve` 要求它先以结构化文件工具写入脚本，再用独立 Bash 调用执行：

```bash

  -H "Content-Type: application/json" \
  -d '{"chatId":"auto-script-chat","agentKey":"default_agent","accessLevel":"auto_approve","message":"严格执行两步：先用 file_write 把只输出 OK 的 Python 脚本写到 @chat/auto-script.py；再单独调用 bash，cwd 设为 @chat，command 设为 python3 auto-script.py。不要使用 heredoc、重定向或复合命令。"}'
```

确认 `file_write` 后紧接 Bash 工具结果，流中不出现 `awaiting.ask`；读取带 raw messages 的 Chat 详情，确认只有一次自动审批审计，`decision=auto_approved`、`reason=accessLevel=auto_approve` 且 `ruleKey` 以 `bash-access:opaque:` 开头。

再以 `accessLevel=default` 要求 Agent 用 `file_write` 写入 `@temp/auto-script.js`，然后用独立 Bash 在 `cwd=@temp` 执行 `node auto-script.js`。确认写入和执行都不出现 `awaiting.ask`，并且没有为这两个普通 allow 决策生成 `auto_approved` 审计。Host 绝对 `/tmp/...` 在 macOS canonicalize 为 `/private/tmp/...` 时结果应相同。

继续覆盖以下边界：

- 对 `@chat` 脚本把 `accessLevel` 改为 `default`，相同的独立解释器命令应进入 opaque approval；等待期间通过 `/api/access-level` 切换为 `auto_approve` 后，原等待项自动回答并继续执行，不要求重新发起 Bash。`@temp` 直接脚本在 `default` 下仍应普通放行。
- 对 Host 与 Container Hub Sandbox 各执行一次；Sandbox 内 `/chat`、`/tmp` 必须分别映射回 Host 当前 Chat 和冻结临时根，并得到相同决定。
- 同一模型响应中并列返回两个无依赖的 Host Bash 调用（分别执行 Chat Python 与 Temp JavaScript），两者都执行且整批只形成一条包含 Chat decision 的自动审批审计；Temp 普通 allow 不写入该审计。
- 改用危险的内联脚本，例如 `node -e 'require("child_process")'`，确认 bashsec hard block 直接拒绝且不进入 approval；symlink 逃逸、readonly 和 KBASE 非 editing gate 同样不得被 `auto_approve` 放宽。
- heredoc、输出重定向以及“写入并执行”的复合 Bash 不属于该快捷流程，继续按 Bash security 规则产生自动批准、HITL 或 block。

### Model turn 提交、丢弃与恢复

使用可控制 stream 帧的 mock provider，并把测试 Agent 的 `budget.model.retryCount` 设为至少 `1`。每个场景同时检查 live SSE、`GET /api/chat`、run summary 和磁盘 `<chatId>.jsonl`：

1. 正常结束但不返回 usage/context window：应正常 commit 并只写一条 `react`。
2. 先返回 usage，再返回缺 id、非法类型或缺函数名的 tool call：不得 commit；usage 不能使该 turn 落盘。
3. 分别在 content、reasoning 和 tool arguments 中途断流：第一次 attempt 应收到 `run.activity.status:"retrying"` 与 `recovery.action:"discard_incomplete_model_turn"`；recovery 中对应 id 必须覆盖已展示的半截块。
4. 重试成功：JSONL 和 run summary 只包含成功 attempt，`react.seq` 连续且没有空洞；非流式 `content/fullText` 也不得拼入第一次 attempt。
5. 重试耗尽：只出现终止 `run.error`，JSONL 中没有未完成 `react`。
6. 完整 tool call commit 后让工具返回失败：原 assistant turn 与同 `seq` 的失败 tool result 都应保留，不出现 model turn recovery。
7. 工具执行期间中断或制造可能有副作用的失败：不得自动回滚重试该 model turn，避免工具重复执行。
8. 对 OpenAI、Anthropic、HITL awaiting、planning、orchestrated Team 和并行工具分别重复正常/断流用例；成员 task 的 recovery id 与根 task 不得串 scope。

旧历史回归准备两个失败 run fixture：

- 末尾 `file_write` arguments 截断且无 tool result：`/api/chat`、raw messages、search、compact、derive 和后续 LLM history 应忽略整个末尾 group；原始 JSONL 审计内容仍保留该文本。
- 末尾 tool call 结构完整但无结果：继续 query 应在本地返回 HTTP `409` 与 `data.error.code:"chat_history_incomplete"`，并确认 mock provider 没有收到请求。

### 工具预算耗尽终态

把测试 Agent 的 `budget.tool.maxCalls` 设为 `1`（等价生产回归可设为 `60`），让 mock provider 连续返回两次合法工具调用。第二次对应第一个越限尝试。分别用默认 SSE 和 `stream:false` 执行，并检查：

1. ToolRouter 只收到第一次调用；第二次不执行，且不存在第三次模型请求。
2. SSE 顺序为一次失败 `tool.result(error:"tool_calls_exceeded")`、一次 `run.error(error.code:"tool_calls_exceeded")`、`[DONE]`；之后没有 `run.complete` 或 `run.cancel`。
3. `run.error.error.diagnostics` 包含 `toolCalls:2`、`limitValue:1`、`limitName:"budget.tool.maxCalls"` 和实际 `toolName`。
4. 并行批次中预算内 sibling 正常收尾，所有越限 sibling 均不执行；客户端只收到一次越限 `tool.result` 和一次终止 `run.error`。
5. `GET /api/attach` 和 WebSocket run stream 可回放同一完整错误；`run_status` 返回 `status:"failed"` 与相同 `error.code`。
6. run summary 的 `finishReason` 为 `error`；`<chatId>.jsonl` 含 `_type:"event"` 的完整 `run.error`；刷新 `GET /api/chat` 后只出现一个 `run.error`，不出现 `run.complete/run.cancel`。
7. 在服务端确认预算错误后调用 `/api/interrupt`，响应必须为 `accepted:false, status:"unmatched"`，数据库、`run_status` 和回放仍保持 error。
8. `stream:false` 返回错误 envelope，但其数据库、RunControl、事件总线和 Chat 回放结果与 SSE 路径一致。
9. 让同一模型响应返回至少三个不可并行的 `plan_update_task`，并使预算在批次中途耗尽：客户端仍只收到一次越限 `tool.result` 和一次 `run.error`；JSONL 中每个 `tool_call_id` 都有结果，首个越限调用之后的 sibling 结果带 `_internalOnly:true`，其内容含 `executed:false`。
10. 在上述失败 run 后对同一 Chat 发起新 query，确认历史加载成功、请求到达 provider 且不返回 `409 chat_history_incomplete`；人工构造的未知执行状态缺失结果历史仍必须返回 409。

## 时间契约回归

完成一次 query 后，确认 chat detail 直接提供顶层时间，且所有结构化时间都是 JSON number（不是字符串、`0` 或 `null`）：

```bash
curl -sS "$BASE_URL/api/chat?chatId=replace-me" | jq '
  .data |
  {createdAt, updatedAt, runTimes: [.runs[]? | {startedAt, completedAt}], eventTimes: [.events[]? | .timestamp]}
'
```

`createdAt`、`updatedAt`、每个 run 的 `startedAt` / `completedAt` 与每个 event 的 `timestamp` 必须位于 `1000000000000..9007199254740991`。可选字段（例如 `readAt`、`expiresAt`、KBASE `lastIndexedAt`）未发生时必须不存在，不能以 `0` 或 `null` 表示。

使用旧 JSONL、archive 或 trace 夹具时，故意保留字符串、秒级、浮点、`0` 或缺失的必填时间，确认 `/api/chat`、`/api/chat/jsonl`、archive replay、search 与 `/api/chat/llm-trace` 返回 `422 time_contract_violation`，且文件没有被重写。

对 GPT Image 2 追加与第一张图同尺寸的新格式 mask，依次验证 `alpha`、`white_edit`、`black_edit`，结果应为 `operation: inpainting`。尺寸不一致、alpha 模式使用非透明 PNG、mask 不带 images 都必须在 provider 调用前失败。对两个 Gemini profile 传 mask，确认返回 `image_generate_mask_unsupported`，且不会改用 GPT Image 2 或发送提示词近似请求。再以 `{"source_type":"file_path","value":"<越权路径>"}` 验证会生成 AccessPolicy HITL，拒绝后不得读取文件；HTTP URL source type、空 value、字符串元素以及旧的 `reference_name/file_path` 属性必须在 provider 调用前拒绝，并返回图片索引和新格式示例。

在 SSE 中确认成功发布必有 `artifact.publish`，其顶层 `timestamp` 是 epoch milliseconds，`toolId` 与触发发布的 `tool.result.toolId` 相同；每个 artifact 都有 `artifactId/name/mimeType/sizeBytes/sha256/url`，Team 子任务还应带正确的 `taskId`。检查 `<chatId>/.tools/artifacts.json`：其中的 `chatId`、artifact 元数据、`runId` 与 `publishedAt` 都存在。

检查 JSONL：只有包含该 `tool.result` 的 `_type:"react-tool"` 行携带 `artifacts.items[]`，且项目仅描述本次批量发布；后续 `react-tool` 行不得复制累计 artifact 快照。再调用 `/api/chat`，确认 `data.artifact.items[]` 来自 manifest。将 chat 归档/恢复并派生到已完成 run，确认归档恢复仍能返回 artifact，而派生 chat 的 manifest 只保留该 run 的项目且 resource URL 指向新 chat。

分别发布前 512 字节恰好截在 3 字节中文字符和 4 字节 UTF-8 字符中间的 `.md` 文件，并覆盖边界外分别剩余 1、2、3 字节的组合；分别对其执行 `GET` 与 `HEAD /api/resource`，两者都必须返回 `X-Document-Kind: document-markdown` 与非空 `X-Document-Revision`，并保持 `Content-Type: text/markdown; charset=utf-8`。再验证跨边界续字节非法、样本中间含非法 UTF-8、完整文件末尾是不完整字符或样本中含 NUL 的同扩展名文件仍返回 binary。

使用 `POST /api/document/commit` 对 Workspace File、Artifact 和 Reference 分别验证文本与 PNG/JPEG/WebP payload：Workspace 只能带 expected revision 原位覆盖；Artifact 默认另存并可明确覆盖；Reference 只能另存新 Artifact。覆盖后确认原身份不变、revision 与 manifest SHA/MIME/size 更新；先外部修改再用旧 revision 覆盖必须返回 409 `revision_conflict` 且不改写外部版本。验证错误 MIME/签名、绝对路径、错误前缀、`..`、单/双重编码 traversal、其他 Chat/Agent、symlink、ChatsRoot 越界和超限 payload 均失败。再用旧 `/api/resource/image/commit` 运行一次相同图片用例，确认兼容适配保持响应并委托同一提交逻辑。

验证缺 sidecar 时，只在隔离的 release 副本中移除 `bin/kbase-lance-engine[.exe]`；不要操作生产安装目录。存在 `docs_kbase` 这类 required capability 时，KBASE 应返回 unavailable 且 `/healthz` 返回 `503`。只保留 `zenmi` 这类 optional capability 后重启，`/healthz` 应返回 `200` 并携带 `degraded/error`，Zenmi 的普通工具仍可用，而五个 KBASE 工具返回 `kbase_unavailable` 与 `stale=true`。两种情况都不能读取或回退 SQLite 检索库。

SQLite 认领回归（仅在隔离 runtime 执行）：先用当前版本创建 `chats.db`、`archive.db`、`memory.db` 或 KBASE `control.db`，将两个 PRAGMA 都设为 `0`。重启时，结构完全相同的库应被补写当前 `application_id` / `user_version`；将任一库加入额外列、表、索引、触发器或 FTS 对象后，标记必须仍为 `0/0` 且数据库不被修复。chat/archive/memory 的不匹配应阻止启动；required KBASE 不匹配应把对应 Agent 显示为 `invalid_kbase_storage`，引用该成员的 Team 不可运行；optional KBASE 不匹配应保留普通 Agent，status 为 degraded/stale，修复目录并成功 refresh 后降级状态消失。进程启动完成后再把一份匹配库改回 `0/0` 并触发热重载、KBASE status/search/refresh 或只读打开，标记不得被重新写入。

### Desktop runtime resource 迁移

准备包含 Agent、Skill、Tool、Team、Registry、根 `VERSION` 和启用的 `provider-register.json` 的 env.zip，在已有 runtime 执行 `agent-platform runtime-resource-sync` 并传入 `--desktop-device-id`。确认 `.include.json` 不需要进入 zip，Platform 只以包内实际资源为权威清单；四类一级资源同名项被发行版本整项覆盖，目标中的本地修改和额外文件被删除，文件/目录类型可互换，新项正常加入，包外未知项保留；发行 Registry 同路径覆盖、包外文件保留。确认 `provider-register.json` 按新版 endpoint/JWT/providers 重新申请新 key，覆盖后的空 `apiKey` 被新值填充且旧 key 不复用，一次性注册定义不落到 runtime；可信历史包中已管理而新版移除的项删除，未知项保留。macOS/Linux 确认覆盖后的 `.sh` 为 `0755`，包外脚本权限不变。

在包外未知 Agent 中写入无效 YAML 或已移除的 Tool 声明，确认 catalog 记录 invalid 诊断并隔离该 Agent，但资源同步仍发布候选、提交新 state 并返回成功；其他有效 Agent 和 Platform 启动不受影响。

覆盖前在 runtime 写入旧 `VERSION` 和四类资源的旧内容，成功后确认 `.agent-platform/resource-backups/<from>-to-<to>-<timestamp>-<transaction>/` 保留五类完整快照和旧 `VERSION`。注入中途发布失败，确认旧内容、旧目录额外文件和原权限均由快照与 journal 恢复，且 state 不提交。

同一目标 Desktop 版本替换不同 SHA 的包，以 `version-change` 再次执行，确认不读取包、不申请 key 且 `changed=false`；以 `manual-import` 执行则允许同步并重新申请。分别构造注册 HTTP 失败、响应缺 key、缺少设备标识、旧 `image.endpointPath`、路径逃逸、符号链接、损坏 ZIP、VERSION 不符、文件/目录冲突和中途发布失败，确认实际 loader/安全校验拒绝候选，state 不提交，备份恢复；模拟恢复失败时 journal 保留。Unix 与 Windows deploy 测试必须确认参数完整转发到同一子命令，且子命令非零会让 deploy 非零。

## Submit / Steer / Interrupt

`/api/submit` 当前使用统一 HITL 协议：

- 顶层固定是公开 owner + `runId + awaitingId + params`；普通 Agent 使用 `agentKey`，Team 使用 `teamId`
- `params` 永远是数组
- 不在 submit 里再传 `mode`
- 后端按 `awaitingId` 反查当前是 `question / approval / form`
- `params[i]` 固定对应 `awaiting.ask` 下发数组的第 `i` 项；`id` 可省略，即使携带也只作审计用途

question:

```bash
curl -X POST "$BASE_URL/api/submit" \
  -H "Content-Type: application/json" \
  -d '{"agentKey":"default_agent","runId":"replace-me","awaitingId":"tool_question","params":[{"id":"q1","answer":"Weekend"},{"id":"q2","answers":["产品更新","使用教程"]}]}'
```

也可以省略 `id`，只要顺序与 `awaiting.ask.questions` 一致：

```bash
curl -X POST "$BASE_URL/api/submit" \
  -H "Content-Type: application/json" \
  -d '{"agentKey":"default_agent","runId":"replace-me","awaitingId":"tool_question","params":[{"answer":"Weekend"},{"answers":["产品更新","使用教程"]}]}'
```

question 的每个答案必须与同索引问题的题型匹配：`multi-select` 使用非空 `answers`，其他题型使用 `answer`，不能同时传两者。题目数量、数值类型、文本非空以及未开启自由输入时的选项值也会校验；`id` 可省略，携带时只用于审计，仍按顺序配对。

```bash
curl -sS "$BASE_URL/api/project/diff?agentKey=replace-agent&chatId=replace-chat&runId=replace-run&path=internal%2Fserver%2Fproject.go"
```

用错误 Agent/Chat/Run 组合测试 owner 边界；二进制历史应返回 415，任一侧超过 `file-tools.max-read-bytes` 应返回 413。通过 Bash 或外部程序修改但未经过 `file_write/file_edit` 的文件只能在 `/api/file` 看见实时内容，changes/diff 不应伪造记录。

## Upload / Resource

```bash
curl -X POST "$BASE_URL/api/upload" \
  -F "requestId=upload_01" \
  -F "chatId=replace-me" \
  -F "file=@./README.md"
```

上传成功后，`data.upload.path` 是智能体可读的执行路径；使用响应中的 `data.upload.url` 访问平台资源：

```bash
curl -X GET "$BASE_URL/api/resource?file=replace-me%2FREADME.md"
```

如果部署开启了 resource ticket，需要把 chat 详情或其他接口返回的 ticket 透传到 `t` 参数：

```bash
curl -X GET "$BASE_URL/api/resource?file=replace-me%2FREADME.md&t=replace-me-ticket"
```

说明：

- `/api/file` 面向 agent workspace 文件预览；`/api/resource` 面向 chat 资源
- chat 上传资源的浏览器/普通客户端文件字节走 `POST /api/upload` 与 `GET /api/resource`；上传结果保持在 Chat 根目录 `<name>`
- 新生成/发布结果中的 `url` 是 `<chatId>/<relativePath>` 逻辑引用，客户端把它放入 `file` query；历史正文中的 `/api/resource?file=...` 仍应原样可读
- 用中文、空格、`#`、`%` 文件名重复测试，必须由标准 URL API 编码后读取，不手写 `%xx`；图片响应应保持原始字节、准确 MIME 和 `Content-Disposition: inline`
- 带合法 Bearer 和 `access_token` Cookie 分别读取当前用户资源；其他用户、错误 chatId、绝对路径、`..`、编码后的 traversal 和 symlink escape 必须失败
- `artifact_publish.path` 可使用当前 Workspace/Chat 内的相对路径、语义路径或 Host 绝对路径；受控根之外、其他 chat、`file://`、HTTP(S)、UNC 或当前主机不支持的 Windows 绝对路径必须失败
- WebSocket `/api/upload` 仅用于网关中转 `url + metadata`，由 platform 自己下载文件，不支持直接在 WS payload 中放 base64/二进制内容

## Platform WebSocket v2 存活与握手

1. 连接普通 `/ws` 后读取首帧，确认只能先收到 `push.connected`，其中协议版本为 2、物理 `sessionId` 非空、`serverTime` 为 epoch milliseconds，并协商 30 秒 heartbeat 与 100 秒 silence timeout。每次新物理连接的 `sessionId` 必须不同。
2. 连续读取 heartbeat，确认携带同一 `sessionId`、严格单调递增 sequence 和合法 timestamp；监控连接快照更新 `lastHeartbeatAt`，消息列表不逐条记录 heartbeat payload。
3. 保持连接 120 秒且不发送业务请求，确认 heartbeat 持续、连接不关闭。随后连续发送业务请求并暂时不依赖 heartbeat，确认任意合法入站帧同样维持客户端存活。
4. 模拟不返回 Pong，确认服务端按独立 Pong timeout 清理物理连接；修改 SSE heartbeat 配置不得改变普通 WebSocket 的 Ping、heartbeat 或协商静默参数。
5. 客户端分别注入首帧非 connected、协议版本错误、字段缺失、heartbeat 周期越界、silence timeout 小于下限或超过 10 分钟，确认立即以协议错误关闭，不进入业务状态，也不回退旧协议。
6. 在监控页核对 protocolVersion、sessionId、关闭原因、lastInbound/Ping/Pong/Heartbeat 时间；token、Authorization、用户请求正文与 heartbeat payload 不得出现在消息预览或日志。
7. 用同一 app-scope 用户和 deviceId 同时连接 `source=desktop-main` 与 `source=desktop-btw`，确认两条连接同时存活；再各自建立第二条同 lane 连接，确认只替换本 lane，另一 lane 不断开。
8. 在 Primary 并发两个 `/api/query`，在 BTW 并发两个 `/api/btw`，确认四个 Run stream 独立且物理连接仍为两条。BTW lane 发送 `/api/query`、Primary 发送 `/api/btw` 都应得到稳定的 lane 错误。
9. 对 BTW Run 在同一 BTW 连接执行 attach、detach、submit/steer/interrupt；detach 后后台 Run 继续，按 lastSeq attach 可恢复。父 Chat、不同 BTW 分支和普通 Run 可以并发。
10. 触发 catalog/chat/run 全局 Push 与 Desktop Action/CDP，确认只有 Primary 收到；BTW 只收到 connected、heartbeat 及本连接请求的 response/error/stream。断开 BTW 不改变 Desktop Main target，断开 Primary 不替换或关闭 BTW。
