# 手工测试用例

## 环境变量

```bash
# 本地 make run 与 Docker Compose 默认都走 SERVER_PORT=11949
BASE_URL="http://localhost:11949"
# 若你改了 SERVER_PORT，同步调整 BASE_URL
```

Identity 文件与 oneid-token 连接器凭据注入（使用隔离部署和测试凭据）：

1. 不传 `--identity-file` 启动 Platform，令 `<有效 StateDir>/identity/access-token` 先保持不存在，通过 `test -z "${AP_ACCESS_TOKEN+x}"` 确认普通 Agent Bash 中没有该变量。
2. 不重启 Platform，写入、原子替换或删除合法单行 token，确认普通 Agent Bash 始终没有 `AP_ACCESS_TOKEN`。挂载用于验收的 oneid-token CLI 连接器，以经验证的单条直接命令调用，仅检查存在性或预期哈希：有效文件的新值应在下一次连接器子进程中生效，删除后不得复用旧值或继承父进程 token。不得打印 token 原文，也不得用 Shell 包装或管道读取凭据。
3. 另建 token 文件并使用 `--identity-file <absolute-path>` 启动，通过上述连接器调用确认显式文件覆盖 `<有效 StateDir>/identity/access-token`；普通 Shell 仍不注入。
4. 设置父进程或 Agent runtime env 的同名变量，确认不能绕过有效 identity 文件；Agent/Skill/调用级声明应以保留变量错误拒绝。
5. 确认 Workspace Terminal、`file_grep/file_glob`、Container、Proxy、ACP、非 oneid-token MCP、LSP 与 sidecar 未自动获得 `AP_ACCESS_TOKEN`，已有 Bash 不因文件变化被中断。
6. 挂载 oneid-token stdio MCP，检查 AP_ACCESS_TOKEN 注入和同一身份下的 session 复用；轮换文件后下次调用重建进程，删除文件后拒绝新调用并回收旧 session。HTTP MCP 只向配置的完整 HTTPS endpoint 发送最新 Bearer Token；`.state/connectors` 不产生 SSO 凭据副本。

### `run_env` 动态环境

准备两个有效挂载 run_env 的普通 native Agent；Agent YAML 不声明动态 key，query 不传环境参数。

1. list 确认动态层为空；explain 检查 key 规则与继承通道，不出现 Host/静态环境值。
2. set、unset、update 验证同值无变化、整批失败回滚、最终状态限额及规范化重复键拒绝。
3. 原请求携带 expectedRevision 成功后，原样重试返回原 revision；同幂等键改变 expectedRevision 返回冲突。
4. 检查 SSE、attach、JSONL、历史、trace、导出，value 与 idempotencyKey 均可见。
5. [bash,set,bash] 顺序调用及审批恢复保持环境版本；子任务/Team 看不到 run_env 且强制调用被拒绝。
6. 空 Scope、set 后全部 unset 的 wait 可以重启恢复为空 Scope（revision=0）；非空 Scope 的 wait 重启沿用失败终态；空白 steer 仍可唤醒。
7. platform_control 的所有旧 run.env 操作拒绝；关闭 platform-control 不影响 run_env；旧环境限额配置明确报错。

在线文档流程：create/upload → run_env set DOCUMENT_HUB_DOCUMENT_ID → session/edit/commit/download。切换文档须重新验证 session/lease。

Windows 仍需在真实主机验证 PowerShell、CreateProcess、直接 exe、大小写冲突及 SystemRoot 等保护，不以交叉编译替代。

### `mustUseSkills` selected-only 目录授权

准备一个挂载 `file_read/file_write/file_edit` 的普通 Agent、一个已配置 Skill `configured-skill`，以及技能中心的 `selected-extra` 和 `unselected-extra`：

1. 使用 `mustUseSkills:["configured-skill","selected-extra"]` 发起 default access run，确认读取两个 Skill 的 `SKILL.md`、scripts、references 和 assets 都不产生 `awaiting.ask`。
2. 同一 run 读取 `@skills-center/unselected-extra/SKILL.md`，确认仍进入 `file_read` AccessPolicy HITL；选择一个 Skill 不得开放整个技能中心。
3. 对两个选中 Skill 分别调用 `file_write/file_edit`，确认直接返回 `file_*_path_blocked` 且不生成 approval；切换 `auto_approve`、`full_access`，或预先配置 hostAccess/writeRoots 后结果仍相同。
4. 在选中 Skill 内建立指向目录外的 symlink/junction（平台允许测试环境建立时），确认按最终 canonical 目标重新判权，不继承选中目录 grant。结束 run 后重新发起未带 `mustUseSkills` 的请求，确认 grant 不继承。

### Agent ZIP 导入

准备一个根目录包含 `agent.yml` 的完整 Agent ZIP；也应接受只多一层包装目录且使用 `agent.yaml` 的 ZIP：

```bash
curl -sS -X POST "$BASE_URL/api/admin/agents/import" \
  -F 'file=@./portable-agent.zip;type=application/zip'
```

成功响应应返回导入 Agent 的 admin detail，且 prompt、`skills/`、`.config/`、知识文件和其他普通资源均完整保留。Agent ID 必须来自 YAML，接口不接收 ID 表单字段。再次导入相同 ID 应返回 409，且 `data.error.overwriteRequired=true`；确认后用同一文件重试：

```bash
curl -sS -X POST "$BASE_URL/api/admin/agents/import" \
  -F 'overwrite=true' \
  -F 'file=@./portable-agent.zip;type=application/zip'
```

旧目录中的 `.config`、专属 Skills 和资源应被完整替换而不是合并；覆盖平铺 YAML 来源后，应只保留规范目录型来源。导入一个语法和公共 mode 合法、但引用本机不存在 Workspace、模型、工具、KBASE 或 Skill 的 Agent 时，应以 200 返回 `status="invalid"` 与 diagnostics，并保留磁盘来源。缺失或同时包含 `agent.yml` / `agent.yaml`、包含 `../`、反斜杠、symlink、大小写冲突、重复路径或文件/目录冲突的 ZIP 应返回 422；非 ZIP 返回 415；超过 32 MiB 上传/单文件、256 MiB 解压总量或 4096 entry 返回 413。可通过制造 catalog 硬重载失败验证 staging/backup 回滚：新 ID 不留半成品，覆盖旧 ID 后旧来源恢复。

导入一个根目录包含 `SKILL.md` 的完整 ZIP；也应接受只有一层包装目录的 ZIP：

```bash
curl -sS -X POST "$BASE_URL/api/admin/skills/import" \
  -F 'id=imported-skill' \
  -F 'file=@./imported-skill.zip;type=application/zip'
```

成功响应应返回 `data.skill.id="imported-skill"` 和 `data.openedFile.path="SKILL.md"`。再次使用相同 ID 应返回 409；缺少 `SKILL.md` 或包含 `../`、symlink、无效 `.runtime-env.json` 的 ZIP 应返回 422 和 `data.error.diagnostics[]`，且 `skills-center/imported-skill` 不得留下半成品。非 ZIP 返回 415，超过压缩、单文件、总解压量或 4096 entry 限制返回 413。

### Agent 专属 Skill 导入

在 `/agents` 编辑一个已保存的目录型 Agent，在“技能”区域点击“导入专属技能”并上传包含 `SKILL.md` 的 ZIP。系统应从 frontmatter 的 `id`（没有则 `name`）自动识别新 ID。成功后：该 ID 自动选中，`GET /api/admin/agents/detail?agentKey=<id>` 的 `privateSkills[]` 包含它，磁盘只出现 `agents/<agentKey>/skills/<skillId>/`，而 `/api/admin/skills` 不应出现该 ID。下拉标签按“名称 · 专属”显示；专属管理行按“[专属] 名称”显示，右侧“删除”会二次确认并删除本地目录及 YAML 引用。下拉标签的移除仅解除启用，不删除本地目录。

使用已存在于技能中心的 ID 时，导入应直接成功，不查询或要求确认技能中心版本；仅当前 Agent 显示并使用“名称 · 专属”，不追加覆盖说明。此时删除该技能中心 Skill 不应被该 Agent 阻塞，且不会删除其本地覆盖版本。

## MCP 版本协商与工具同步

Platform 默认请求 `2025-11-25`，服务端分别返回 `2025-11-25`、`2025-06-18`、`2025-03-26` 或 `2024-11-05` 时，应完成初始化通知、工具同步和调用；HTTP 后续请求携带实际协商版本，初始化日志也记录该版本。服务端返回缺失、无效或未知版本时仍应关闭连接并报告 unavailable。服务端返回 HTTP 429 时应报告限流失败。

查看 registry summary。HTTP 项应有 `transport:"streamable-http"` 和 `baseUrl`；stdio 项应有 `transport:"stdio"`，且不得出现 `command`、`args`、`env` 或无意义的 `baseUrl`：

```bash
curl -sS "$BASE_URL/api/admin/registries"
```

Qiuerscript 迁移后，六个工具应由 MCP catalog 发现，来源固定为 `sourceType/sourceCategory:"mcp"` 且 `serverKey:"qiuerscript"`：

```bash
curl -sS "$BASE_URL/api/admin/tools"
```

在已配置 qiuerscript `dev` datasource 的机器上，可直接验证标准 MCP stdio 初始化、`initialized`、`tools/list` 与 stdin EOF 退出：

```bash
printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{},"clientInfo":{"name":"manual-test","version":"1"}}}' \
  '{"jsonrpc":"2.0","method":"notifications/initialized","params":{}}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}' \
  | qiuerscript-tool serve --datasource dev
```

`tools/list` 应返回 `qs_read/qs_glob/qs_grep/qs_write/qs_edit/qs_delete`；管道结束后进程应正常退出。这里直接测试的是 qiuerscript server，其接受版本由该二进制实现决定；Platform client 接受 SDK 支持的服务端协商版本，不要求所有 server 只返回 `2025-11-25`。

旧配置硬失败回归：在隔离 runtime 的 `tools-dir` 分别放入 `service.yml`、`type: external`、`external: {}` 或 `kind: external-service` 后启动/触发 tools 热重载，操作应失败并提示迁移到 `runtime/connectors-center` 的 `mcp.json`（`type: stdio`）；不要在共享运行目录执行此用例。

### 分层上下文压缩

使用隔离测试 Chat 或派生副本，规则见 [会话存储与回放](会话存储与回放.md) 和 [API与协议](API与协议.md)。

1. 手动 `level:"l1_tools"` 不调用模型，只给原 JSONL 行增加 `_compact:{level,id,keep?}`；不改原文、不新增 L1 行。检查 reasoning 与完整工具组的清理，正文、引用、附件和未完成交互保留。

3. 自动阈值验证：89.99% 不触发，90% 触发 L1；L1 后低于 90% 不执行 L2，仍达到 90% 才执行一次 L2。60% 仅为 L2 选材目标。

5. 活动 Run 在模型／工具批次结束或 HITL 安全点处理压缩；工具不重复执行，等待项保持同一 `awaitingId`。持久化失败返回 `compact_persist_failed`，不得继续调用模型。
6. 相同 `requestId` 并发重试共享结果，不同请求并发返回 `busy/compact_in_progress`；历史维护期间新 Query 返回可重试 409。验证客户端断开、Run 中断及不支持的后端处理。
7. 自动 L1/L2 共享 `cycleId`；需要 L2 时 L1 的 `cycleComplete:false` 不结束 UI 等待。压缩后验证刷新回放与下一次 Query 的有效上下文。

### 自写和临时脚本的版本审批

选择同时启用 `file_write` 与 Bash 的普通 Agent，要求先用结构化文件工具写入只输出 `OK` 的脚本，再用独立 Bash 调用执行。分别使用 `@chat/auto-script.py` 和 `@temp/auto-script.js`，覆盖 Python 与 Node。

- `default`：文件写入遵守既有路径与写审批配置；脚本执行进入审批，卡片 `policy` 展示内容哈希、调用范围与理由。选择本 Run 批准后，同一路径、相同内容和调用上下文可复用；修改脚本内容后重新审批，兄弟调用不得消费一次性授权。
- `auto_approve`：没有其他硬限制时脚本自动审批并产生审计，执行指纹的 `ruleKey` 以 `bash-access:execution:` 开头。临时脚本不再特殊免审。
- 等待 default 审批时，通过切档入口改为 `auto_approve`，验证原等待项重新评估后继续；带额外业务 Hook 的命令仍遵守 Hook 的 `autoApprove` 声明。
- `node -e 'require("child_process")'` 归为未知代码执行：default 审批、auto 自动审计。私有根、readonly、KBASE 非 editing gate 和可见越界写不得因内联代码而失效。
- Host 路径经 symlink 解析后获得相同决定；`cat plain.txt` 和 `cat ./plain.txt` 在两者均指向外部文件时不得有策略差异。Container 显式路径按 guest/host 映射检查，glob 暂不支持。
- 并列返回两个无依赖的 Host Bash 调用，确认批量卡片包含两者的全部理由，批准后并发恢复；拒绝、中断、超时不能留下可被其他 toolID 消费的批准。

参见 [AccessPolicy 与 HITL 边界](AccessPolicy与HITL改造.md) 中的当前实现边界；任意获准 Host 程序的内部文件访问尚无操作系统隔离。

### Model turn 提交、丢弃与恢复

使用可控制 stream 帧的 mock provider，并把测试 Agent 的 `budget.model.retryCount` 设为至少 `1`。每个场景同时检查 live SSE、`GET /api/chat`、run summary 和磁盘 `<chatId>.jsonl`：

1. 正常结束但不返回 usage/context window：应正常 commit 并只写一条 `react`。
2. 先返回 usage，再返回缺 id、非法类型或缺函数名的 tool call：不得 commit；usage 不能使该 turn 落盘。
3. 分别在 content、reasoning 和 tool arguments 中途断流：第一次 attempt 应收到 `run.activity.status:"retrying"` 与 `recovery.action:"discard_incomplete_model_turn"`；recovery 中对应 id 必须覆盖已展示的半截块。
4. 重试成功：JSONL 和 run summary 只包含成功 attempt，`react.seq` 连续且没有空洞；非流式 `content/fullText` 也不得拼入第一次 attempt。
5. 重试耗尽：只出现终止 `run.error`，JSONL 中没有未完成 `react`。
6. 完整 tool call commit 后让工具返回失败：原 assistant turn 与同 `seq` 的失败 tool result 都应保留，不出现 model turn recovery。
7. 工具执行期间中断或制造可能有副作用的失败：不得自动回滚重试该 model turn，避免工具重复执行。
8. 对 OpenAI、Anthropic、HITL awaiting、planning、orchestrated Team 和并行工具分别重复正常/断流用例；成员 task 的 recovery id 与根 task 不得串 scope。

旧历史回归准备两个失败 run fixture：

- 末尾 `file_write` arguments 截断且无 tool result：`/api/chat`、raw messages、search、compact、derive 和后续 LLM history 应忽略整个末尾 group；原始 JSONL 审计内容仍保留该文本。
- 末尾 tool call 结构完整但无结果：继续 query 应在本地返回 HTTP `409` 与 `data.error.code:"chat_history_incomplete"`，并确认 mock provider 没有收到请求。

### 工具预算耗尽终态

把测试 Agent 的 `budget.tool.maxCalls` 设为 `1`（等价生产回归可设为 `60`），让 mock provider 连续返回两次合法工具调用。第二次对应第一个越限尝试。分别用默认 SSE 和 `stream:false` 执行，并检查：

1. ToolRouter 只收到第一次调用；第二次不执行，且不存在第三次模型请求。
2. SSE 顺序为一次失败 `tool.result(error:"tool_calls_exceeded")`、一次 `run.error(error.code:"tool_calls_exceeded")`、`[DONE]`；之后没有 `run.complete` 或 `run.cancel`。
3. `run.error.error.diagnostics` 包含 `toolCalls:2`、`limitValue:1`、`limitName:"budget.tool.maxCalls"` 和实际 `toolName`。
4. 并行批次中预算内 sibling 正常收尾，所有越限 sibling 均不执行；客户端只收到一次越限 `tool.result` 和一次终止 `run.error`。
5. `GET /api/attach` 和 WebSocket run stream 可回放同一完整错误；`chat_get_status` 返回 `status:"failed"` 与相同 `error.code`。
6. run summary 的 `finishReason` 为 `error`；`<chatId>.jsonl` 含 `_type:"event"` 的完整 `run.error`；刷新 `GET /api/chat` 后只出现一个 `run.error`，不出现 `run.complete/run.cancel`。
7. 在服务端确认预算错误后调用 `/api/interrupt`，响应必须为 `accepted:false, status:"unmatched"`，数据库、`chat_get_status` 和回放仍保持 error。
8. `stream:false` 返回错误 envelope，但其数据库、RunControl、事件总线和 Chat 回放结果与 SSE 路径一致。
9. 让同一模型响应返回至少三个不可并行的 `plan_update_task`，并使预算在批次中途耗尽：客户端仍只收到一次越限 `tool.result` 和一次 `run.error`；JSONL 中每个 `tool_call_id` 都有结果，首个越限调用之后的 sibling 结果带 `_internalOnly:true`，其内容含 `executed:false`。
10. 在上述失败 run 后对同一 Chat 发起新 query，确认历史加载成功、请求到达 provider 且不返回 `409 chat_history_incomplete`；人工构造的未知执行状态缺失结果历史仍必须返回 409。

## 时间契约回归

完成一次 query 后，确认 chat detail 直接提供顶层时间，且所有结构化时间都是 JSON number（不是字符串、`0` 或 `null`）：

```bash
curl -sS "$BASE_URL/api/chat?chatId=replace-me" | jq '
  .data |
  {createdAt, updatedAt, runTimes: [.runs[]? | {startedAt, completedAt}], eventTimes: [.events[]? | .timestamp]}

```

`createdAt`、`updatedAt`、每个 run 的 `startedAt` / `completedAt` 与每个 event 的 `timestamp` 必须位于 `1000000000000..9007199254740991`。可选字段（例如 `readAt`、`expiresAt`、KBASE `lastIndexedAt`）未发生时必须不存在，不能以 `0` 或 `null` 表示。

使用旧 JSONL、archive 或 trace 夹具时，故意保留字符串、秒级、浮点、`0` 或缺失的必填时间，确认 `/api/chat`、`/api/chat/jsonl`、archive replay、search 与 `/api/chat/llm-trace` 返回 `422 time_contract_violation`，且文件没有被重写。

在 Darwin ARM64，确认 cache 的 `bin/` 包含 `rg`、`kbx`、`memx` 与 `pdftotext`，以及 connectors/builtin.dbx 和 connectors/builtin.httpx 完整包，且存在 `libexec/poppler-pdftotext/darwin-arm64/`。本地 clean checkout 的 `VERSION` 严格高于组件目标时必须询问；输入 `yes` 后只允许更新组件目标与 `darwin-arm64` 的 target release/path/SHA，并先在相邻项目稳定 `dist/<version>/` 固化同 SHA archive，所有 Windows/Linux target 必须逐字节不变。输入其他内容或非交互 leader 均不得修改正式 lock。随后在 Windows AMD64 checkout 到目标 VERSION/commit 并同步，应不询问而自动只更新 `windows-amd64` target；checkout/commit 不匹配则只更新 cache。rollout 未完成时再发布更高版本，应允许新 leader 经 `yes` 抢占，落后平台随后直接跟随最新目标。同版本不同 commit/path/SHA、dirty、降级、artifact 目标冲突、校验失败或 lock 并发变化均不得覆盖正式记录。`--all` 不得为未在 lock 中声明的 Poppler target 尝试构建，也不得写交叉 target。故意令任一构建 archive、归档许可证、Poppler runtime manifest 或 payload 缺失时必须失败，且不得替换既有 `build/builtins/<target>`。同步脚本不操作 `release-local/bin`。目标平台 build/start/search smoke、签名与 notarization 在对应 release runner 执行，不得因为本地同步脚本存在就记录为已验证。

正式 Desktop builtin 发布只消费已校验的 build cache。在 Darwin ARM64 release runner 上，先确保相邻 builtin collection 中的 lock target archive 已发布，再从干净 platform 目录验证装配：

```bash
make test-release-program-clean
```

该命令会删除本仓库 `dist/`，再直接运行 `make release-program`；不要求 Rust、Cargo 或 `protoc`，但要求已校验的 builtin cache 和 Syft 均已就绪。它会检查最终 bundle 的 KBX、Poppler、完整连接器、manifest、许可证及 verify-program-bundle；Desktop 仅调用 Platform 的 make release。

### Desktop runtime resource 迁移

准备包含 Agent、Skill、Tool、Team、Connector、Registry、根 `VERSION` 和启用的 `provider-register.json` 的 env.zip，在已有 runtime 执行 `agent-platform runtime-resource-sync` 并传入 `--desktop-device-id`。确认 `.include.json` 不需要进入 zip，Platform 只以包内实际资源为权威清单；五类一级资源同名项被发行版本整项覆盖，目标中的本地修改和额外文件被删除，文件/目录类型可互换，新项正常加入，包外未知项保留；发行 Registry 同路径覆盖、包外文件保留。确认 `provider-register.json` 按新版 endpoint/JWT/providers 重新申请新 id，覆盖后的空 `apiKey` 被新值填充且旧 id 不复用，一次性注册定义不落到 runtime；可信历史包中已管理而新版移除的项删除，未知项保留。macOS/Linux 确认覆盖后的 `.sh` 为 `0755`，包外脚本权限不变。

在包外未知 Agent 中写入无效 YAML 或已移除的 Tool 声明，确认 catalog 记录 invalid 诊断并隔离该 Agent，但资源同步仍发布候选、提交新 state 并返回成功；其他有效 Agent 和 Platform 启动不受影响。

覆盖前在 runtime 写入旧 `VERSION` 和五类资源的旧内容，成功后确认 `.agent-platform/resource-backups/<from>-to-<to>-<timestamp>-<transaction>/` 保留六类完整快照和旧 `VERSION`。注入中途发布失败，确认旧内容、旧目录额外文件和原权限均由快照与 journal 恢复，且 state 不提交。

同一目标 Desktop 版本替换不同 SHA 的包，以 `version-change` 再次执行，确认不读取包、不申请 key 且 `changed=false`；以 `manual-import` 执行则允许同步并重新申请。分别构造注册 HTTP 失败、响应缺 key、缺少设备标识、旧 `image.endpointPath`、路径逃逸、符号链接、损坏 ZIP、VERSION 不符、文件/目录冲突和中途发布失败，确认实际 loader/安全校验拒绝候选，state 不提交，备份恢复；模拟恢复失败时 journal 保留。Unix 与 Windows deploy 测试必须确认参数完整转发到同一子命令，且子命令非零会让 deploy 非零。

## Submit / Steer / Interrupt

`/api/submit` 当前使用统一 HITL 协议：

- 顶层固定是公开 owner + `runId + awaitingId + params`；普通 Agent 使用 `agentKey`，Team 使用 `teamId`
- `params` 永远是数组
- 不在 submit 里再传 `mode`
- 后端按 `awaitingId` 反查当前是 `question / approval / form`
- `params[i]` 固定对应 `awaiting.ask` 下发数组的第 `i` 项；`id` 可省略，即使携带也只作审计用途

question:

```bash
curl -X POST "$BASE_URL/api/submit" \
  -H "Content-Type: application/json" \
  -d '{"agentKey":"default_agent","runId":"replace-me","awaitingId":"tool_question","params":[{"id":"q1","answer":"Weekend"},{"id":"q2","answers":["产品更新","使用教程"]}]}'
```

也可以省略 `id`，只要顺序与 `awaiting.ask.questions` 一致：

```bash
curl -X POST "$BASE_URL/api/submit" \
  -H "Content-Type: application/json" \
  -d '{"agentKey":"default_agent","runId":"replace-me","awaitingId":"tool_question","params":[{"answer":"Weekend"},{"answers":["产品更新","使用教程"]}]}'
```

## Upload / Resource

```bash
curl -X POST "$BASE_URL/api/upload" \
  -F "requestId=upload_01" \
  -F "chatId=replace-me" \
  -F "file=@./README.md"
```

上传成功后，`data.upload.path` 是智能体可读的执行路径；`data.upload.url` 是不含 `chatId` 的 Chat 相对 URI。Markdown 原样使用该 `url`；HTTP 读取由客户端 adapter 加入响应中的 `chatId` 后进行 query 编码。以下示例假定响应的 `chatId` 为 `replace-me`、`url` 为 `README.md`：

```bash
curl -X GET "$BASE_URL/api/resource?file=replace-me%2FREADME.md"
```

如果部署开启了 resource ticket，需要把 chat 详情或其他接口返回的 ticket 透传到 `t` 参数：

```bash
curl -X GET "$BASE_URL/api/resource?file=replace-me%2FREADME.md&t=replace-me-ticket"
```

说明：

- `/api/file` 面向 agent workspace 文件预览；`/api/resource` 面向 chat 资源
- chat 上传资源的浏览器/普通客户端文件字节走 `POST /api/upload` 与 `GET /api/resource`；上传结果保持在 Chat 根目录 `<name>`
- 上传、生成图片和发布产物的 `url` 是不含 `chatId` 的 `<relativePath>`，Markdown 原样使用；客户端 adapter 加入当前 `chatId` 后转换为 HTTP 数据面请求。发布产物 URL 必须指向发布副本；历史 endpoint Markdown 不迁移且不再预览，HTTP 数据面仍保留
- 用中文、空格、`#`、`%` 文件名重复测试，必须由标准 URL API 编码后读取，不手写 `%xx`；图片响应应保持原始字节、准确 MIME 和 `Content-Disposition: inline`
- 带合法 Bearer 和 `access_token` Cookie 分别读取当前用户资源；其他用户、错误 chatId、`..`、编码后的 traversal 和 symlink escape 必须失败。绝对路径请求须携带 `chatId` 和有效认证：普通 Agent 当前 Workspace／冻结临时根内的文件应可读取；Chat 目录绝对路径、Team、越界路径和无认证请求必须拒绝
- `artifact_publish.path` 可使用当前 Workspace/Chat 内的相对路径、语义路径或 Host 绝对路径；受控根之外、其他 chat、`file://`、HTTP(S)、UNC 或当前主机不支持的 Windows 绝对路径必须失败
- WebSocket `/api/upload` 仅用于网关中转 `url + metadata`，由 platform 自己下载文件，不支持直接在 WS payload 中放 base64/二进制内容

## Platform WebSocket v2 存活与握手

1. 连接普通 `/ws` 后读取首帧，确认只能先收到 `push.connected`，其中协议版本为 2、物理 `sessionId` 非空、`serverTime` 为 epoch milliseconds，并协商 30 秒 heartbeat 与 100 秒 silence timeout。每次新物理连接的 `sessionId` 必须不同。
2. 连续读取 heartbeat，确认携带同一 `sessionId`、严格单调递增 sequence 和合法 timestamp；监控连接快照更新 `lastHeartbeatAt`，消息列表不逐条记录 heartbeat payload。
3. 保持连接 120 秒且不发送业务请求，确认 heartbeat 持续、连接不关闭。随后连续发送业务请求并暂时不依赖 heartbeat，确认任意合法入站帧同样维持客户端存活。
4. 模拟不返回 Pong，确认服务端按独立 Pong timeout 清理物理连接；修改 SSE heartbeat 配置不得改变普通 WebSocket 的 Ping、heartbeat 或协商静默参数。
5. 客户端分别注入首帧非 connected、协议版本错误、字段缺失、heartbeat 周期越界、silence timeout 小于下限或超过 10 分钟，确认立即以协议错误关闭，不进入业务状态，也不回退旧协议。
6. 在监控页核对 protocolVersion、sessionId、关闭原因、lastInbound/Ping/Pong/Heartbeat 时间；token、Authorization、用户请求正文与 heartbeat payload 不得出现在消息预览或日志。
7. 使用相同 app-scope 用户/deviceId 建立 desktop-main、desktop-btw、desktop-explain 三条连接，确认同时存活；每条 lane 新连接仅替换本 lane。错误 app/device 或保留 surface 冒充应拒绝。
8. 在 main、btw、explain 分别并发发送 `/api/query`，确认 Run stream 独立、物理连接仍为三条；旁聊携带 payload lane=main 仍写隐藏分支，主 Chat JSONL/摘要/未读保持不变。所有 lane 使用旧 WS `/api/btw` 均返回未知请求类型。
9. 每条 lane 保持一个 stream，先 detach 再 attach；漏 detach 时第二条 query/attach 明确拒绝且不创建 Chat/Run。detach 后后台 Run 继续，按 lastSeq attach 可恢复；三条 lane 的 stream 可并行。
10. 触发 catalog/chat/run 全局 Push 与 Desktop Action/CDP，确认只有 Primary 收到；BTW 只收到 connected、heartbeat 及本连接请求的 response/error/stream。断开 BTW 不改变 Desktop Main target，断开 Primary 不替换或关闭 BTW。

## VIEW

内置 HTML 和连接器展示统一使用 [VIEW 协议](VIEW连接器.md)。question / approval / planning 为 native，不请求 HTML。

```bash
curl -X GET "$BASE_URL/api/view?source=builtin&key=platform_control_review"
```

确认返回 `data.view.source: builtin` 与内嵌 HTML。缺少 source、未知 key、请求 native key 或传入旧 viewport 字段应失败；旧 `/api/viewport` 应返回 404。连接器来源必须提供 `source=connector`、connectorId、key、chatId 与冻结 hash，并校验 Chat 权限。表单等待项只有单个 `form`，planning 与 form 用 `param` 对象提交；Team 多成员同时等待时应逐个出现，答完一项才出现下一项。

### HTTP Query lane

1. `POST /api/query` 不传 `lane` 或传 `main`，确认普通 Chat 正常更新。
2. 网页 BTW 发往 `/api/query`，body 含 `lane:"btw"`；分别验证 SSE 与 `stream:false`，同一 `btwId` 连续两问使用不同 Run，主 Chat JSONL、摘要不变。
3. HTTP `lane:"explain"` 返回 403，未知 lane 返回 400，均不创建 Chat；旧 `/api/btw` 不再注册，不能启动 Run。

### Platform selection steer 与 transport/lane 隔离

1. 非视觉模型接受 selection steer；选区文本在入队后保持不变，消费一次，JSONL 与回放/续聊保留文本。混合图片继续校验 Chat 资源，非视觉模型保留工具读取引用，错误引用不入队。
2. main/btw/explain 三条连接各启动 Run；对另外两条 lane 的 Run 依次调用 attach/detach/steer/interrupt/access-level，均返回 `run_lane_mismatch` 且 Run 状态不变。Submit 按下一节验证跨设备／通道提交。
3. 除 Submit 外，HTTP Run 使用 HTTP 控制成功，WS 控制返回 `run_transport_mismatch`；反向亦然。不能用 payload lane 覆盖归属。
4. 同 lane detach、断线、关窗重开后重新 attach；新 sessionId 不影响恢复。不同 device 拒绝。进程重启后的等待项 submit 与 planning 执行 Run 继续继承原归属。
5. 除 Submit 外，缺少归属记录的 Run 控制请求明确拒绝；保留归属记录后重启，校验仍生效。


## chat_start 来源与跨设备 HITL 回归

1. 桌面主对话通过 chat_start 新建独立任务，确认新 Run 的 transport/lane 与父 Run 相同，runOrigin 仍保留父级关系。父 Run 结束后独立任务继续运行。
2. 独立任务触发审批，在桌面提交并确认后续工具执行；提交失败时审批卡片显示具体错误，保留选择并可重试。
3. 桌面创建待审批任务，从已认证手机 HTTP 或 WS 提交，确认成功且没有改变 Run 原有连接归属；两端重复审批不会执行两次。
4. 错误 Agent/Team、错误 awaitingId、非法答案仍拒绝；无有效认证时 HTTP 与 WS 仍不能访问。
5. main/btw/explain 的 attach、detach、steer、interrupt 和 access-level 跨通道操作继续按既有规则拒绝。
6. chat_start 的父级来源缺失或无效时明确失败，不创建来源为空的派生 Run；不迁移既有 Run 文件。

## chat_start 可选启动参数与等待摘要

1. 仅传 agentKey/message，确认成功且子 Run 继承父 Run 当前档位；运行中切换父档位后再次调用继承新档位，指定已有 chatId 续聊同样继承。
2. 父 Run 分别为三档时显式请求三档：同级或降级直接启动；高于父档位在父 Chat 弹出 chat_start_review 审阅页，核对目标、权限变化、完整任务内容，等待期间未创建 Chat/Run。批准后只启动一次并核对目标 request.query 的 runOrigin.permission；拒绝、超时（默认 600 秒）、中断均不启动。
3. 审阅页显示期间把父 Run 切到更高档位：审批不会被自动回答；此后批准返回 run_start_review_stale 且未创建 Run，模型重新调用后按新档位直接启动。父 Run 为 auto_approve/full_access、approve_rule_run、错误调用 ID 均不能通过审批。tools.yml 保留 runQuery 时启动失败并提示 config-migrate。
4. 分别关闭目标 interactionConfig.accessLevel/mustUseSkills，非默认档位/非空技能选择返回 interaction_disabled；Team 非空技能列表、连接器技能、未知技能拒绝。空技能数组不强制额外技能。
5. 新建时传 chatName，检查 chat.created、列表与重启后名称一致；续聊不覆盖。chatId/chatName 同传、空名、错误类型、null、未知字段 taskName/model 均明确拒绝；省略三个新增字段仍可用。
6. 同一父 runId/toolId 合法重试只创建一个 Run，不改名、不修改原档位；子 Run 不改变父 Run 权限。
7. 目标等待 question/approval/form/planning 时查询 status：类型、itemCount、awaitingCount 正确；审批最多 3 项，每项字符串最多 200 字符，有裁剪标记，不透传原始工具参数。多等待项返回稳定顺序；淘汰 awaiting.ask 缓存后摘要仍存在。人工解决、取消或计划失效后不再显示旧等待。
8. 运行中调整目标档位后，status 立即反映当前档位，终态保留最终值。父 Agent 告知用户去目标 Chat 审批，不代 submit，不持续轮询。
9. A6/A7 在 default 和 auto_approve 下分别复测：每轮先创建 Workspace 内 disposable 测试目录及无价值测试文件；A6 删除该目录，A7 读取预先准备的 workspace 外测试文件。核对审批决策、auto_approved 审计和实际输出，不能用目标不存在时的 rm 成功替代破坏性操作验收。仅在隔离测试部署使用 full_access，不修改生产权限默认值。
