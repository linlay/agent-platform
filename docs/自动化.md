# 自动化

## 当前状态

Go runtime 已具备 automation registry、orchestrator、dispatcher 与 execution store。automation 定义目录由 `<AP_RUNTIME_DIR>/automations` 控制，调度器随服务进程启动。

当前自动化能力仍是运行时编排的一部分，不等同于完整产品层任务管理；Desktop 侧 automation 操作可通过 desktop action bridge 暴露给模型。

Automation 的 `query.accessLevel` 支持 `default`、`auto_approve`、`full_access`，省略时使用 `default`。定时及手动触发均使用受理时 Definition 中的权限配置，指定已有 `query.chatId` 也不继承该 Chat 上次 Run 的权限。配置修改只作用于之后的触发，运行中通过通用 Run 权限接口调整不会回写任务配置。此字段不受 `runQuery.allowAccessLevelOverride` 限制，仍经过目标 `interactionConfig.accessLevel` 准入及工具硬限制；不满足时明确失败，不静默降级。`query.params.accessLevel` 不是权限配置入口。

## 核心流程

```text
启动加载 automations
  -> registry 注册
  -> orchestrator 计算触发
  -> dispatcher 并发执行
  -> 非阻塞提交 execution 开始快照
  -> Platform Query Runtime 持久化 RunStart / RunCompletion
  -> execution history 后台绑定 run 并记录完整结果
```

手动触发通过 HTTP-only 的 `POST /api/automation/trigger` 进入同一个 orchestrator 和 dispatcher。接口按 Automation ID 读取受理时的完整 Definition，立即生成并提交 `running` Execution 快照，然后返回 `executionId`；Query 注册、模型执行和终态归档在受生命周期管理的后台任务中继续。手动与定时执行共用 `automation.pool-size` 并发池，但手动触发允许执行暂停项，不消耗 `remainingRuns`，也不改变下次定时触发时间。后续编辑或删除 Automation 不影响已经受理的执行快照。

`executions.db` 是旁路历史，不是 Query/Run 的前置依赖。Dispatcher 在调用 Query 前生成 `executionId` 并把 Automation、目标 Agent/Team、有效时区和 `query.message` 快照提交给内存记录器；提交不执行 SQLite I/O。Query 注册后通过只读生命周期 hook 报告 `RunStart`，完成后返回 Chat Store 实际持久化的 `RunCompletion`。History worker 随后异步写入 `chatId`、`runId`、`finishReason`、完整 `AssistantText` 和终态。History 初始化、备份、写入、广播或回写失败只影响历史完整性，不得改变 Query 的启动、结果或错误。

日志统一写入服务进程 stdout。排障时优先查看是否出现 `automation orchestrator started`、`[automation] registered ...`、`[automation] dispatch ...`。

## 配置与接口

- `<AP_RUNTIME_DIR>/automations`：固定的 automation 定义目录。
- `configs/runtime.yml` 的 `automation.enabled`：是否启用 orchestrator。
- `configs/runtime.yml` 的 `automation.default-zone-id`：平台默认时区；未在单个 automation YAML 中写 `environment.zoneId` 时，cron 按这个时区解释。
- `configs/runtime.yml` 的 `automation.pool-size`：dispatch 最大并发。
- `POST /api/automation/trigger`：按 `id`（兼容 `automationId`）异步受理一次原生手动执行；该管理操作只支持 HTTP。
- `desktop_action` 支持 `desktop.automations.*` 一组动作。

默认值见 [配置化说明](配置化说明.md)。

Automation 可以绑定普通 Agent 或目录式 Team：

```yaml
# 普通 Agent
agentKey: reporter
query:
  message: 生成日报
  accessLevel: auto_approve
```

```yaml
# Team：只传 teamId，由隐藏协调器调度
teamId: research
query:
  message: 研究本周行业变化并输出复核后的报告
```

registry 在加载、创建和更新时使用 Team 快照校验身份：Team 同时配置 `agentKey` 会失败，成员为空或存在失效成员也会失败。触发后的 `QueryRequest` 只携带 `teamId`，由隐藏协调器调度。

`query.message` 以 HTTP JSON 解码后的字符串为事实值，创建、更新、YAML 持久化、重载和最终执行均逐字符保留换行、制表符、反斜杠、引号及首尾空白；校验只用裁剪后的结果判断是否为空。例如请求 JSON 中的 `\n` 表示真实换行，返回 JSON 仍编码为单层 `\n`，不会变成字面量反斜杠加 `n`。如果消息本身需要字面量 `\n`，JSON 请求应按标准规则写成 `\\n`，持久化后仍保持字面量。旧 YAML 中 plain 或单引号标量里的 `\n` 不会被自动转换；重新提交 `query.message` 后才会按当前可逆格式保存。

`description`、`environment.zoneId`、`query.role`、`query.hidden` 和 `query.accessLevel` 都可省略。省略 `query.role` 时执行角色为 `automation`；省略 `query.hidden` 时有效值为 `true`，Chat 时间线不显示该 automation query 消息，但仍显示 chat、run 和模型回复。需要显示 query 时可显式配置 `hidden: false`。Registry 保留“未配置”状态，API 详情和结构化持久化不会把这些计算后的默认值重新写入 YAML。

管理 API 创建和更新使用 `query.accessLevel`，详情原样返回已配置档位；省略不写入 YAML。更新不带整个 `query` 时保留原配置；带 `query` 时按现有整体替换语义处理，省略 `accessLevel` 即恢复默认权限。YAML 加载、源码保存与管理 API 持久化均拒绝非法档位，API 对非法值或错误类型返回 400。WebClient 结构化编辑器提供三档选择，创建、编辑和复制任务均保留选值。

`auto_approve` 仍可能要求越界写、破坏性操作等审批，不能保证完全无人值守；`full_access` 更宽，但仍受平台硬限制。

## 约束与注意事项

- 时区优先级为：automation YAML 的 `environment.zoneId`、`configs/runtime.yml` 的 `automation.default-zone-id`、最后才回退到进程 `time.Local`。
- 日常自动化默认省略 `environment.zoneId`，表示跟随 Platform 当前时区（`automation.default-zone-id`，无效或未配置时为进程 `time.Local`）；需要跨时区或不随 Platform 时区变化的任务，再显式写 `environment.zoneId`。
- cron 表达的是对应时区里的本地时间，例如默认时区为 `Asia/Shanghai` 时，`0 9 * * *` 表示北京时间每天 09:00，不是 UTC 09:00。
- API 返回的 `nextFireAt`、`startedAt`、`completedAt` 是 epoch milliseconds，供排序、计算和客户端本地化。`nextFireTime`、`startedTime`、`completedTime` 统一按 Platform `automation.default-zone-id`（无效或未配置时回退进程 `time.Local`）输出 `YYYY-MM-DD HH:mm:ss`，只用于阅读，不携带毫秒或时区。Execution 还返回创建时的有效业务 `zoneId` 快照；该快照不参与三个 `*Time` 字段的展示转换。可选 `nextFireAt` / `completedAt` 缺失时省略，绝不返回 `0` 或 `null`；完整规则与 `422 time_contract_violation` 语义见 [API与协议](API与协议.md#统一时间契约)。
- `executions.db` 当前 schema 为 V2（`PRAGMA user_version=2`）。`AUTOMATION_EXECUTIONS` 在原快照和时间字段之外保存 `QUERY_CONTENT_`、`CHAT_ID_`、`RUN_ID_`、`RUN_STARTED_AT_`、`FINISH_REASON_` 与完整 `RESULT_CONTENT_`；列表查询只读取最多 240 字符的摘要，单条详情才读取完整结果。
- 发现结构精确匹配已知旧版本的数据库时，History worker 先创建并校验 `executions.db.backup-v<version>-<timestamp>.db`，再把 active 数据库原子重建为空 V2；旧行不迁移、不回填，备份暂不自动删除。备份或升级失败时 Platform 与 Automation 继续运行，History 状态明确降级并在后台重试。未知结构不会被猜测升级或覆盖。
- History 状态为 `initializing`、`ready`、`degraded` 或 `unavailable`。Automation 配置列表和编辑始终可用；历史不可读时 execution history/detail 接口返回明确 `503`，不会伪装成空列表。
- History 初始化或不可用不会阻止手动触发；Execution 快照仍按现有旁路机制尽力提交，History 恢复后继续持久化。触发接口的 HTTP 成功只表示已受理，不表示 Query 或模型执行成功。
- Platform 开始停止后不再接受新的手动触发。已受理任务纳入 orchestrator 生命周期：排队任务写为 `canceled`，运行中任务沿 Query context 取消链路结束，避免已返回 `executionId` 的任务静默丢失。
- 重启后遗留的 `running` Execution 会在后台对账：若 `chats.db` 已有对应 Run 终态则回填，否则标记为 Platform 重启期间中断。该恢复不阻塞新 Query。
- automation 首次创建出的 chat 会在 chat 摘要、`/api/chat` 详情和 `chat.created` push 中记录 `source:"automation:<automationId>"`。automation 名称不写入 chat 表；如需展示名称，可用 automationId 查询 automation registry。后续 automation 写入已存在 chat 时不会覆盖原 chat source。
- 本地 `make run` 的 automation 日志在启动服务的终端里，不在 `docker compose logs`。
- automation 配置变更遵循运行时配置规则，通常需要重启或重新装载对应 registry。
- automation 只决定何时启动根 query，不替代 run 内编排；orchestrated Team 触发后仍由 `agent_delegate` 和 plan tools 调度。普通 `agent_invoke` 与 TEAM 调度见 [子智能体调度](子智能体调度.md)。
- Desktop 模式下，automation 根 run 首次调用 `desktop_action` 或网页控制工具时绑定当前 `desktop-main`，不要求可见 WebClient query。该路由不授予 WorkPanel Chat grant；Standalone 行为不变。

## Platform Control 管理工具

受信任 `builtin.platform-control` 挂载新增 `automation_query` 与 `automation_manage`，仅普通 Native 根 Run 可用；planning 只读。工具输入沿用 `{action,args}`，平台字段使用 camelCase，旧参数名不做别名转换。Automation 属于部署级管理资源，不进入 `catalog_manage.apply`。

- `automation_query`：`list/get/executions/execution/validate`。列表使用 limit/offset，get 返回 baseRevision；validate 接受完整创建候选，只校验并预览最多三次计划时间。
- `automation_manage`：`create/update/setEnabled/delete/trigger`。创建接受结构化名称、Cron、zoneId、Agent/Team、query、enabled 与 remainingRuns；update 按字段更新，但 query 整体替换。省略 remainingRuns 保持原值，不支持用 null 清除次数限制。
- 修改、启停、删除、立即执行必须带 get 返回的 baseRevision。执行前重新校验定义，源码编辑与定时次数变动也可能使版本过期。管理写入与调度写入共用 Registry 的来源锁和版本比较，避免用过期定义覆盖新设置。
- 创建、修改、启停使用 `automation_review`；立即执行使用 `automation_trigger_review`；删除使用 `automation_delete_review`。default 展示人工审阅；auto_approve/full_access 自动批准非删除操作并沿用 HITL 审计，删除始终人工确认。工具直接调用 Platform 服务，不经过 Desktop action，不产生 Desktop 第二次确认。
- 页面显示名称、执行者、任务内容、计划、时区、权限、变更对比；自定义 Cron 展示实际计算的未来时间，原始字段折叠。预览不是已执行或已调度的保证。任务权限来自保存的 query.accessLevel，工具创建省略时显式保存 default，不继承当前聊天权限。

`internal/automation.Service` 共用于 HTTP/WS 和 Platform Control；Server 仅保留请求与响应适配。底层仍复用 Registry、Orchestrator、ExecutionHistoryReader。手动 trigger 接受已审阅的定义快照，返回 accepted/executionId，不改变启停状态，也不消耗剩余定时次数。配置更新、暂停、删除会替换或取消定时注册，可能取消在该注册上下文中运行的定时任务；手动触发的执行使用独立上下文，不因此取消。删除保留历史和已有会话。

工具调用收据保存于 `<StateDir>/automation-control/`，绑定 subject、Agent、Run、tool invocation 与参数摘要。执行前写入 intent，完成后记录结果；同次调用重复执行返回先前结果。进程中断遗留的 intent 按 unknown 返回，不擅自重放；必须先检查任务和执行历史。收据不自动清理，本机制不提供多进程分布式事务或系统断电级 exactly-once 保证；外部编辑器直接写盘仍不在管理锁保护范围。
