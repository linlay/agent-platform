# 运行时资源迁移

## 职责边界

Agent Platform owns 已有 runtime 中 `agents`、`skills-center`、`tools`、`teams`、`registries` 的升级语义。Desktop 只定位实际 runtime root、校验发行 env.zip、判断 Desktop `VERSION` 是否变化，并把已验证的包路径作为不透明输入传给 deploy。Desktop 不解析 Registry YAML，也不直接合并 Platform 领域目录。

release manifest 通过以下能力声明该 contract：

```json
{
  "desktop": {
    "runtimeResources": "v1"
  }
}
```

Unix `deploy.sh` 与 Windows `deploy.ps1` 只解析并转发参数，合并算法统一由同一个 Go 子命令实现：

```text
agent-platform runtime-resource-sync
  --ap-runtime-dir <runtime-root>
  --runtime-resource-source <env.zip>
  --runtime-resource-previous-source <old-env.zip，可选>
  --desktop-version-from <version|legacy>
  --desktop-version-to <version>
  --desktop-device-id <stable-device-id>
  --mode <version-change|manual-import>
```

## 输入与合并规则

子命令要求 ZIP 只有一个 `env/` 根，并拒绝路径逃逸、反斜杠路径、符号链接、特殊文件、重复路径、文件/目录冲突、损坏包和 `env/VERSION` 不匹配。它只抽取根 `VERSION`、五个 Platform scope 与可选的一次性 `provider-register.json`，忽略 `desktop-init.json`、Chats、Owner、Profile、Pet、Sites 等 Desktop 或用户数据。`zenmind-env` 的 `.include.json` 只在打包阶段筛选资源，不进入 env.zip，也不由 Platform 解析；包内实际出现的资源就是本次更新的权威清单。

- Agent、Skill、Tool、Team 以一级资源为单位。包内资源无条件整项覆盖或新增：同名目标存在时先完整移除再复制发行版本，不合并本地修改或目标中的额外文件；文件与目录可以互相替换。覆盖和新增项都由包管理。
- Registry 以发行包文件相对路径为单位。同路径无条件覆盖或新增，包外文件保留，不猜测或合并凭据字段。
- Registry 覆盖完成后，如果同一新版 env.zip 声明了 `provider-register.json` 且 `enabled=true`，Platform 必须严格按其中的 `endpoint`、JWT `grant` 与 `providers` 重新申请一枚新 API key，并结合 Desktop 传入的稳定设备标识注入所有目标 Provider。旧 Registry 中的 key、旧 env.zip 和 runtime 中已消费的一次性注册文件都不参与生成；注册定义不发布到 runtime。
- 上一状态清单或可信历史 env.zip 能证明由包管理、而新版已移除的资源才会删除；没有出现在新版包中且无法证明所有权的本机资源继续保留。
- 首次进入本机制且没有状态时，可用 `--runtime-resource-previous-source` 推导旧所有权；历史包不存在、损坏或版本不可靠时从空所有权开始。
- macOS/Linux 包内 `.sh` 发布为 `0755`；被覆盖资源采用发行包权限，包外保留资源的权限不变，事务回滚会恢复覆盖前的权限。Windows 资源发布使用本机文件语义。

Platform 先把当前五类目录复制到 staging，再应用合并规则与新版包注册定义。候选树在新 key 注入后使用实际 Model/Provider、MCP、Viewport、Agent、Team、Skill、Tool loader 校验。Model/Provider、MCP、Viewport、Tool 或 Agent/Team/Skill catalog 根级加载失败会终止迁移；例如旧 `image.endpointPath` 会失败，新 `image.generation.endpointPath` 才可通过。单个 Agent 定义无效时由 catalog 隔离并保留管理诊断，不阻断资源发布、Platform 启动或 Desktop 升级。注册请求、响应解析或目标 Provider 写入失败均使本次迁移失败，既不发布候选，也不提交 state。

## 幂等与事务

`version-change` 只比较 Platform 状态中的目标 Desktop 版本。同版本立即返回，不读取 env.zip，也不比较 SHA；SHA 只用于输入完整性、未完成事务一致性和审计。`manual-import` 是显式操作，可在同版本再次执行。

状态归 Platform 自己维护：

```text
<runtime>/.agent-platform/
├── runtime-resource-state.json
├── runtime-resource-upgrade.json
└── resource-backups/<from>-to-<to>-<timestamp>-<transaction>/
```

发布前完整备份五类 scope 和根 `VERSION`，备份目录名为 `<from>-to-<to>-<timestamp>-<transaction>`，其中 `from` 来自 `--desktop-version-from`，快照中的 `VERSION` 保留实际旧版本。journal 记录事务、源 SHA、目标和原始权限。任一步发布或状态提交失败都会从备份恢复，不写新 state；恢复不完整时保留 journal 并返回非零退出码，下次调用先续跑恢复。成功时先提交 state，再清理 journal；已完成事务的备份继续保留，不进入运行时 catalog。macOS/Linux 的状态/备份目录使用 `0700`、文件使用 `0600`；Windows 使用仅当前用户和 SYSTEM 可访问的 ACL。

## deploy 组合

runtime resource sync 与 Desktop config reset 可在一次 deploy 中完成。deploy 先重建服务配置并渲染模型参数，再把 `--desktop-device-id` 连同资源参数转给子命令，因此新版 `--ai-image-generate-model-key`、Registry schema 与重新生成的 Provider key 在同一部署事务中生效。子命令失败会让 deploy 原样返回非零，Desktop 必须阻止核心服务启动且不得提交自己的完成版本。

独立 Platform 部署未传 runtime resource 参数时保持原行为，不执行迁移。其他内置服务不需要实现本 contract。
