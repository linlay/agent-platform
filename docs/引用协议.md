# 引用协议

Query 和 steer 使用同一个 `references` 数组。每条消息中的引用都是用户为这条任务指定的资源，静态提示词要求逐项使用；Platform 不检查模型是否实际读取或使用它们。资源内容、名称和说明均为引用材料，不因此取得用户指令或系统指令的优先级。selection 的 annotation 仍是用户针对原文的要求。

客户端为技能、知识库和对话只发送定位信息：

```json
{
  "message": "参考之前的讨论和产品资料，按技能完成分析",
  "references": [
    {"type": "skill", "id": "code-review"},
    {"type": "kbase", "id": "product-docs"},
    {"type": "chat", "id": "chat-001"}
  ]
}
```

服务端从可信 catalog 或 Chat 索引补齐元数据。技能带名称、说明和 SKILL.md 路径；知识库带名称、说明和 collection 摘要；对话带名称、Agent 和更新时间，不读取或拼接历史正文。file 仍传资源 URL，selection 仍传原文和批注，site 保留 id/name/meta.kind 及现有站点字段。

## 模型输入

system prompt 中只有 `shared.reference.protocol-prompt` 的静态说明：skill 完整读取对应 SKILL.md 并遵循，kbase 用指定 libraryId 检索，chat 通过 chat_query 的 read/search 按需读取，file 按 path 读取。该配置没有代码正文兜底，升级时应同步 agent-prompt.yml 对应配置。固定绑定库仍以 boundLibraryId 留在 system prompt；动态选择不会追加技能 catalog、requiredLibraries 或其他选择列表，也不进入 system-init fingerprint。

用户输入中的同一格式化函数生成引用块；advanced-user-prompt 使用相同引用内容的 XML 包装：

```text
[References]
- id: code-review
  type: skill
  name: Code Review
  path: @skills-center/code-review/SKILL.md
  meta:
    description: Review code changes
- id: product-docs
  type: kbase
  name: 产品资料
- id: chat-001
  type: chat
  name: 知识库接入讨论

[User message]
参考之前的讨论和产品资料，按技能完成分析
```

planningMode 经用户批准启动的新执行 Run 携带规划 Run 的结构化 query/steer 引用，并重新准入。

## 准入和授权

资源按“类型 + 规范化 ID”去重。技能 ID 大小写不敏感，对话和知识库使用精确 ID；同名 skill/kbase/chat 互不覆盖。整个 Run 累计最多 32 个技能、8 个知识库、32 个对话，超过上限整条拒绝，既有集合不变。

- skill：校验普通技能，授予选中 canonical 目录的 trusted read + readonly roots；未选中兄弟目录不继承。只为其现存 scripts/** 签发本 Run 内存入口凭据，不增加工具或合并额外 runtime 配置。
- kbase：目标需挂载 builtin.kbase-control，逐库校验可读性；不授予文件目录或写权限，也不是检索白名单。
- chat：当前执行路径需能使用 chat_query；只授予该 Run 对该 chatId 的 read/search 权利，分页仍按工具协议。管理操作 rename/archive/export 沿用原权限解析。

登录身份始终校验 Chat 所有权，引用不能跨 principal。匿名只能引用没有 query:<subject> 归属的 Chat。模型调用 chat_start 时不能凭空签发匿名 Chat 读取权：它只可传递调用方 Run 已可读的 Chat。子任务和 TEAM 成员直接拒绝 chat 引用，主 Run 可先读取材料后写入任务说明。

steer 使用该 Run 的冻结 interactionConfig 校验 attachment.skills/kbases/chatRecords/localFiles；`chat_start` 的初始引用与来源为 Agent 的 steer 不经该开关校验，其余定位、授权与数量限制不变。准备不修改状态；RunControl 在同一把锁内入队并提交授权，拒绝或失败入队不残留授权。选中资源集合只增不减；撤销的技能脚本凭据不会因重复引用再次签发。attachment.skills 开启时固定暴露 @skills-center，沙箱运行固定只读挂载 /skills-center，选项变化不改变 system prompt 或挂载指纹。

## 执行路径

| 路径 | skill | kbase | chat |
| --- | --- | --- | --- |
| Native 主 query / steer，含 TEAM 总控 | 支持 | 需 kbase-control | 需实际可用的 chat_query |
| agent_invoke 子任务 / TEAM 成员 | 支持 | 需目标 kbase-control | 拒绝 |
| ACP / PROXY / CHANNEL query | 拒绝 | 拒绝 | 拒绝 |
| ACP / PROXY / CHANNEL steer | 拒绝 | 拒绝 | 拒绝 |
| BTW | 拒绝 | 拒绝 | 拒绝 |

引用不会恢复被排除的工具，也不会为不支持根 Chat 工具的执行路径开放权限。

## 压缩、历史和恢复

压缩在 pinned 区补充一个有界的“本 Run 已可用资源”块，只保存 skill/kbase/chat 的定位和可信元数据，不产生当前任务的新使用义务。每次压缩替换已有资源块；file/site/selection 不进入该保留区。任务义务跟随原消息由摘要承载。

request.query 和已消费的 request.steer 保留规范化后的 references，供时间线、重发和恢复使用。带历史的 Native 主 Run（含 TEAM 总控）启动时，另从本 Chat 之前主 lane 的 query 行顶层 references 和已消费 steer.references 取最近 32 个不同技能，按本次入口的当前规则逐项重新校验，成功后授予读权限与新 Run 的脚本入口凭据；不读取旧 query 原文、模型正文、路径或压缩摘要来推断授权。失效、入口不允许或沙箱未挂载的技能逐项跳过，历史技能读取失败只记日志，不阻止 Query。

这些历史技能不加入本轮 references，不产生本轮使用义务，不进入用户消息、system prompt、fingerprint 或压缩的本 Run 可用资源块，也不占显式引用的 32 个名额；继承只增加 read roots，不增加 readonly roots，便于用户在后续轮次维护技能，写入仍受 Workspace、管理员 readonly 与常规 HITL 约束，脚本内容变化会撤销本 Run 的入口凭据。没有新增持久状态或移除接口，需隔离已选技能时使用新 Chat。子任务、TEAM 成员、ACP/PROXY/CHANNEL、旁路、新 Chat 和同 Run 恢复不补这项授权；普通历史展示不会授权 kbase/chat 等其他资源。

同 Run 恢复仍只从该 Run 的结构化 query/steer 逐项重验，失效项不授权，历史指针仍保留；技能脚本执行凭据不重建。历史 JSONL 不迁移、不改写，也不再把旧独立选择字段恢复为授权。

## 硬切

HTTP/WS 的 query/steer、工具参数与 Automation query 对未声明字段明确拒绝，包括 null 和空数组；请求使用统一 references。交互配置使用 attachment.skills / attachment.kbases。非 Native 执行路径不支持本地资源定位，只接受文件、选区与站点，入口不能通过显式覆盖增加后端能力。WebClient 旧提交草稿和已选知识库形状直接丢弃。Desktop WebApp copilot 声明为 references:[{type:"skill",id:"..."}]，绑定远端 Agent 时该启动请求被拒。Platform、WebClient、Desktop 及环境契约需同批更新；不提供旧等待 Run 的字段转换。
