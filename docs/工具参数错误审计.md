## 新诊断契约

`internal/toolinput` 只处理确定的本地输入契约，不做字符串到数字的隐式转换。JSON 整数按 JSON 解码后的数字检查整数性。`1` 和 `100` 有效；`0`、`101`、`1.5`、`"100"`、null 都拒绝。

示例（省略已有外层字段）：

```json
{
  "error": "control_request_rejected",
  "stage": "admission",
  "executionState": "not_started",
  "field": "args.limit",
  "expected": "JSON integer in range 1–100",
  "actual": "string",
  "message": "args.limit requires JSON integer in range 1–100 (actual: string). Set args.limit to 100; example: limit:100.",
  "recovery": {
    "strategy": "fix_input",
    "message": "Set args.limit to 100; example: limit:100."
  }
}
```

缺失值用 `missing`，显式 null 用 `null`，错误数组元素用如 `args.preservePaths[0]`。预期及示例来自静态契约，不包含用户的 content、凭据、环境值或未知键名。未知字段使用安全路径 `args.<unknown>` 和允许字段列表，以去除不受支持的字段；不保存被拒字段原文。

权限检查仍先于平台控制参数校验；不能用更好的报错扩大权限。`catalog_manage` 和 Chat 删除继续要求原有一次性批准；typed error 穿过审批准备通路时仍使用已有 `tool_review_failed` 外层错误码。Desktop 的 unknown_action、action_tool_mismatch 错误码保持兼容。

## Desktop Kanban 边界方案（未实施）

只读源码位置：相邻 `zenmind-desktop/src/main/modules/desktop-actions/{kanban-actions,kanban-validation,action-values}.ts` 与 `kanban/store-local-issue-model.ts`。

当前 `validateKanbanActionArgs` 检查 input 对象、title、status 和 workflowId/typeId/position 等少数字段，但没有完整未知字段 allowlist；`readKanbanInput` 原样传递对象。`applyIssueUpdate` 按可写字段逐项构造新 issue，不消费 input.runResultMessage。`LocalRunDetails` 单独承载运行结果、错误和时间。这与记录里字段未改变一致，但没有当时版本 SHA，不能证明该实现就是当时二进制。

建议在 Desktop Action 边界为每个动作定义公开可写字段的 allowlist，递归检查 attachments 等受管嵌套结构；遇到未知字段或私有运行字段，整次拒绝后再进入 runtime，避免部分更新却返回整体成功。错误应提供 `args.input.runResultMessage`、`expected: omit runtime-owned field`、`actual: string` 及“删除该字段；人工补充用公开 description；执行结果由受信任运行收尾写入”的指引。不回显字段内容。

公开 Action DTO 应与内部运行写入 DTO 分离：不能照搬内部 KanbanIssueUpdateInput 的 runId/runState 等字段作为外部授权依据。不要为了消除报错直接开放 runResultMessage，也不要把人工 description 标记成独立运行结果。若产品需要独立人工备注，新增显式备注能力并区分 provenance；若需要结果导入，必须是单独受信任、校验 run/issue 关联与版本的入口。

待 Desktop 增加测试：混合合法 description 与私有 runResultMessage 时零写入；未知字段零写入；现有异步运行结果不被覆盖；内部受信任收尾仍能写运行结果；返回成功只表示公开字段已接受。此工作树没有修改 Desktop 文件。
