# 子智能体调度

## 当前状态

运行时有三条用途、所有权和生命周期不同的调度路径：

- `agent_invoke`：普通主 Agent 显式声明后调用普通子智能体。
- `agent_delegate`：仅供 orchestrated Team 的总控 Agent委派当前 Team 成员。
- Mailbox：普通主 Agent 挂载 `builtin.task-control` 后以 `chat_send` 派活或补充，平台自动回信；`chat_notify` 发中途消息，`chat_submit` 代答请示。

`agent_invoke` 保持原有契约。`agent_delegate` 定义在 `internal/resources/tools/agent_delegate.yml`，由 Team 自动、强制注入；普通 `agent.yml` 声明该工具会在 catalog 加载时失败，普通 session 与统一工具入口直接执行也会拒绝。总控 Agent 进入普通 Agent catalog；agent_delegate 不进入公开 Tool catalog。Chat 工具都是 `explicitOnly` Tool，通过 `builtin.task-control` 挂载进入 Agent 有效工具集合，仍受 excludeTools 与 planning 排除配置约束。

三者不能互换：

| 路径 | run/chat 身份 | 结果回流 | 生命周期 |
|---|---|---|---|
| `agent_invoke` | 复用父 `chatId/runId`，创建 child task/session | 子结果聚合为当前工具结果 | 受父 run 控制 |
| `agent_delegate` | 复用 Team 根 run，成员作为 task | 成员结果回注总控 Agent | 受 Team 根 run 控制 |
| Mailbox | 寄给目标 Chat，平台决定开 Run、插入或排队 | 返回 mailId/chatId/delivery，最终结果自动回信 | 受理后投递不依赖发信 Run 存活 |

## `agent_invoke`

```text
普通主 Agent 调用 agent_invoke
  -> 主时间线保留 tool 事件
  -> server 并发启动 1~5 个普通子 Agent
  -> 子流实时汇聚到主 SSE / replay
  -> 子结果按输入顺序聚合并回注主 Agent
```

- Agent 必须在 `toolConfig.tools` 显式声明 `agent_invoke`。
- 每项必须包含 `subAgentKey` 和 `task`，可选 `taskName/files`。
- `subAgentKey` 不得等于当前 `Agent Identity.key`；服务端在 catalog 解析前按精确 key 拒绝自调用，含自身目标的整批任务不会启动任何 child。
- 可用主 Agent mode：`GENERAL`、`CODER`。
- 可用 child mode：`GENERAL`、`CODER`、`KBASE`、`PROXY`；ACP CODER 当前不能作为 child。
- child session 禁止再次调用子智能体。
- TEAM 总控 Agent不能调用 `agent_invoke`，TEAM 成员也不能携带该工具。
- Agent 候选不再注入 prompt；显式挂载 builtin.platform-control 后通过 catalog_query.list 按需发现。目录不授予调用权限，也不定义 Team roster。
- 旧 contextConfig.agents 与 agents 标签忽略并产生一条非阻断管理 warning；实际调用仍检查目标有效性，Team 必需成员校验不放宽。

## Chat 会话工具组

后台派活统一使用 chat_send，newChat:true 新开会话、chatId 补充同一件事；短时内联任务继续使用 agent_invoke。chat_get_status/chat_interrupt 仅控制由本 Agent 的 letter started 开出的 Run；信派生 Run 保留 run_chaining_not_allowed。参考 [Mailbox](Mailbox.md) 和 task-control 手册。

## TEAM 的 `agent_delegate`

`agents/<agentKey>/agent.yml` 中声明 `mode: TEAM` 与 `teamConfig.members` 创建 TEAM Agent。每个 run 从 embedded definition 克隆 `agent_delegate` schema，并按冻结 roster 动态补充成员枚举和任务上限。

总控 Agent固定拥有四个工具：

```text
agent_delegate
plan_add_tasks
plan_get_tasks
plan_update_task
```

### 参数

`agent_delegate` 只接受 `tasks`：

| 参数 | 必填 | 约束 | 语义 |
|---|---|---|---|
| `tasks` | 是 | 数组，至少 1 项；`maxItems` 等于冻结 roster 大小 | 本次调用需要委派的成员任务 |
| `tasks[].agentKey` | 是 | 必须是动态 `enum` 中的精确成员 key；同一次调用不可重复 | 目标 Team 成员 |
| `tasks[].task` | 否 | string | 自定义任务文本；省略或为空时使用原始用户消息 |
| `tasks[].taskName` | 否 | string | `task.*` 进度事件的标题 |
| `tasks[].files` | 否 | 最多 10 项 | 附加文件或当前 chat 资源，转换成 references 后与原始 references 去重 |

`additionalProperties:false` 同时作用于工具根对象和每个 task。`maxParallel` 不进入工具 schema 的任务上限：它只控制 runtime 同时运行的成员数；`tasks` 数量超过 `maxParallel` 时，仍属于同一次工具调用，由 runtime 分波执行并一次性聚合结果。

目标 `agentKey` 不得等于当前 TEAM session 的执行 Agent key；服务端会在 roster 解析前拒绝自调用，且整批不产生成员任务事件。

成员始终继承原始请求的 `scene`、`references` 和该成员可见的 Team 历史。成员与 `agent_invoke` 子任务的 query 行原样保存调用方在工具参数中写的那一项任务，顶层记 `taskId`、`taskName`（缺省为成员名称时记有效值）、`taskToolId`、`taskAgentKey` 与解析后的 `references`；`task.start` 事件与返回给模型的任务结果同样使用 `taskAgentKey`，工具参数自身的字段名（`agent_invoke` 的 `subAgentKey`、`agent_delegate` 的 `agentKey`）不变。自定义 `task` 只替换 message，不会丢失这些上下文。

### 场景枚举

明确由一个成员回答与给单个成员自定义任务是同一条执行路径：

```json
{"tasks":[{"agentKey":"writer"}]}
```

```json
{
  "tasks": [
    {
      "agentKey": "writer",
      "task": "只检查文档中的事实错误",
      "taskName": "事实检查"
    }
  ]
}
```

无法判断合适成员与明确选择多个成员也是同一条多项委派路径：

```json
{
  "tasks": [
    {"agentKey":"writer"},
    {"agentKey":"reviewer"},
    {"agentKey":"researcher"}
  ]
}
```

```json
{
  "tasks": [
    {"agentKey":"researcher","task":"收集事实依据"},
    {"agentKey":"reviewer","task":"检查潜在风险"}
  ]
}
```

一项和多项没有不同的终止规则。每项都产生 `task.start` 和 `task.complete/error/cancel`，全部结果都回注总控 Agent，随后由总控更新计划、继续委派或生成唯一的 Team 最终回答。

工具结果统一为：

```json
{
  "results": [
    {
      "taskAgentKey": "reviewer",
      "taskName": "风险检查",
      "status": "completed",
      "content": "最终成员结果"
    }
  ]
}
```

失败项可增加 `error`、`errorCode`。一个成员失败不会取消同批其他成员；单成员失败和多成员部分失败也走相同的结构化返回路径，由总控决定改派、解释或继续。

## 计划与执行状态

```text
routing -> waiting_members -> coordinator -> complete
```

- 简单请求可以直接调用一次 `agent_delegate`。
- 复杂请求先用 `plan_add_tasks` 创建有序任务列表，再用 `plan_update_task` 维护状态。任务按数组顺序执行且同时最多一个 `in_progress`；只有当前阶段终态后才能启动下一阶段。
- `plan_get_tasks` 用于读取当前计划；计划工具不自动启动成员。
- 当前计划阶段可以在一次 `agent_delegate` 中并行委派多个成员；成员并行不会产生多个活动计划阶段。`agent_delegate` 本身没有 direct、fanout、invoke、DAG 或串行模式。
- 最前面的非终态 task 可由 `init` 进入 `in_progress` 或直接进入 `completed/failed/canceled`，`in_progress` 可进入任一终态；终态不可复活，需要重试时在计划末尾追加新 task。
- 总控可以直接回答、先使用自己的工具或委派；不要求每回合必须委派。

## 事件、历史与隐私

- 成员事件携带根 `runId`、task `taskId`、成员 `agentKey`、`actor.type:"agent"` 和 `presentation:"task"`。
- 成员正文、reasoning 和 tool chain 不会成为根回答；根 `content`、run summary 与 `AssistantText` 只取总控 Agent的最终 Team 回答。
- 总控 reasoning 和普通工具沿普通事件链路；内部 agent_delegate 不展示工具卡。
- 成员读取专用 Team 历史：保留自己的 tool chain，只读取其他成员最终正文和 Team 最终正文，不读取其他成员 reasoning/tool result。
- 总控保留自己的完整普通历史与工具调用/结果配对，并加入成员最终正文；成员私有工具链不会泄露给总控。

## HITL 与限制

- 成员不注册独立 active run；public `awaitingId` 使用 `taskId:rawAwaitingId`，submit 时映射回 child raw ID。
- 成员的 awaiting 不合并：按到达顺序排队，一次只发布一位成员的等待项，答复后再发布下一项；每项按成员自己的 mode 提交并原样转给对应 child。
- Team-owned run 的 submit 使用 根 `agentKey + runId + awaitingId`，不能使用成员 key。
- interrupt 作用于整个根 run；steer 写入总控 run，不直接选择某个成员。
- Team 不能作为另一个 Team 的成员或 child 目标。
