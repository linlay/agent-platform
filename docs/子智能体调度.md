# 子智能体调度

## 当前状态

运行时有三条用途、所有权和生命周期不同的调度路径：

- `agent_invoke`：普通主 Agent 显式声明后调用普通子智能体。
- `agent_delegate`：仅供 orchestrated Team 的隐藏总控委派当前 Team 成员。
- `chat_start`（发起会话运行）、`chat_get_status`（查询会话运行状态）、`chat_interrupt`（中断会话运行）：普通主 Agent 挂载 `builtin.task-control` 后发起、查询和中断独立 Agent 根 run。

`agent_invoke` 保持原有契约。`agent_delegate` 定义在 `internal/resources/tools/agent_delegate.yml`，由 Team 自动、强制注入；普通 `agent.yml` 声明该工具会在 catalog 加载时失败，普通 session 与统一工具入口直接执行也会拒绝。隐藏总控和 `agent_delegate` 均不进入普通 Agent 或 Tool catalog。三个 Chat 工具都是 `explicitOnly` Tool，只有分别在普通 Agent 的 `toolConfig.tools` 中显式挂载后才进入该 Agent 的模型工具集合。

三者不能互换：

| 路径 | run/chat 身份 | 结果回流 | 生命周期 |
|---|---|---|---|
| `agent_invoke` | 复用父 `chatId/runId`，创建 child task/session | 子结果聚合为当前工具结果 | 受父 run 控制 |
| `agent_delegate` | 复用 Team 根 run，成员作为 task | 成员结果回注隐藏总控 | 受 Team 根 run 控制 |
| Chat 工具组 | 创建或继续目标 chat，并注册独立根 run | chat_start 立即返回 chatId/runId，后续显式查询状态 | 不受调用方 run 中断影响 |

## `agent_invoke`

```text
普通主 Agent 调用 agent_invoke
  -> 主时间线保留 tool 事件
  -> server 并发启动 1~5 个普通子 Agent
  -> 子流实时汇聚到主 SSE / replay
  -> 子结果按输入顺序聚合并回注主 Agent
```

- Agent 必须在 `toolConfig.tools` 显式声明 `agent_invoke`。
- 每项必须包含 `subAgentKey` 和 `task`，可选 `taskName/files`。
- `subAgentKey` 不得等于当前 `Agent Identity.key`；服务端在 catalog 解析前按精确 key 拒绝自调用，含自身目标的整批任务不会启动任何 child。
- 可用主 Agent mode：`GENERAL`、`CODER`。
- 可用 child mode：`GENERAL`、`CODER`、`KBASE`、`PROXY`；ACP CODER 当前不能作为 child。
- child session 禁止再次调用子智能体。
- TEAM 隐藏总控不能调用 `agent_invoke`，TEAM 成员也不能携带该工具。
- Agent 候选不再注入 prompt；显式挂载 builtin.platform-control 后通过 catalog_query.list 按需发现。目录不授予调用权限，也不定义 Team roster。
- 旧 contextConfig.agents 与 agents 标签忽略并产生一条非阻断管理 warning；实际调用仍检查目标有效性，Team 必需成员校验不放宽。

## Chat 会话工具组

`chat_start`、`chat_get_status`、`chat_interrupt` 分别启动、查询和中断独立根 run。它们直接调用平台内部 query admission 与 run-control facade，不通过 localhost HTTP，也不接触 JWT。工具挂载本身就是调用授权：不使用目标白名单，不读取 `visibility` 或 invoke scope；目标通过精确 catalog `agentKey` 选择；省略时使用可信调用上下文中的当前 Agent，不支持 `teamId`。

```yaml
toolConfig:
  tools:
    - chat_start
    - chat_get_status
    - chat_interrupt
```

### 中文意图与工具选择

“会话”和“对话”在这里含义完全相同，均指 Chat；“聊天”“Chat”也是同一对象的常见说法。

- “新开一个会话”“新开一个对话”“另开一个聊天”“新建一个 Chat”：调用 `chat_start`，省略 `chatId`，不得复用当前 Chat ID。
- “继续那个会话／对话”：仅在确定用户指定的已有 Chat 后传入其 `chatId`，仍受 owner 与单 Chat 单 active run 约束。
- 未指定目标 Agent 时可省略 `agentKey`，服务端从可信调用上下文补齐当前 Agent；明确指定目标时使用对应 catalog `agentKey`。`teamId` 按未知参数拒绝。
- 用户给出新会话／对话的名称时填写 `chatName`；需要执行的内容放入 `message`。
- “查看新会话／对话的进度”“中断那个会话／对话的运行”分别使用 `chat_get_status`、`chat_interrupt`，传入启动结果中的 `runId`。中断仅作用于该次运行，不删除或关闭 Chat。
- `agent_invoke` 是当前执行中的 Agent 调用，`agent_delegate` 是 Team 内成员委派；两者都不能代替明确的新开会话／对话请求。

例如：“用当前智能体新开一个对话，分析权限设计，命名为‘权限检查’”，可省略 `agentKey`，以 `message: "分析权限设计"`、`chatName: "权限检查"` 调用 `chat_start`，省略 `chatId`。

以上意图规则由模型工具说明表达；`runId` 用于定位 Chat 内的一次执行。

### `chat_start`

```json
{"agentKey":"webOperator","message":"查找最新资料"}
```

```json
{"chatName":"权限检查","message":"分析权限设计"}
```

- `message` 必填；`agentKey` 可选，省略时使用可信 `RunOrigin.AgentKey`。显式空串、空白、`null` 或非字符串仍拒绝；缺少默认目标的可信调用方身份返回 `run_context_required`。不接受 `teamId`，也不回退全局默认 Agent。
- `Agent Identity` section 只提供身份事实；`chat_start` 的工具描述规定：用户以“当前智能体”“本智能体”“你自己”指定目标时，可省略 `agentKey`，或原样使用当前 system prompt 的 `Agent Identity.key`，不得使用目录中其他 Agent 的 key 替换当前身份。
- `chatId` 可选；省略时创建新 chat，提供既有 chat 时目标必须与该 chat 的公开 owner 完全一致，省略 `agentKey` 也按当前 Agent 校验，不能切换 Chat owner，不能继续 Team-owned Chat。
- 顶层可选 `accessLevel`（`default/auto_approve/full_access`）、`mustUseSkills`（技能 ID 数组）和 `chatName`（新 Chat 初始名称）。三者都不是必填；省略 `accessLevel` 继承父 Run 调用当时的当前权限（含运行中切换），指定 `chatId` 续聊也一样；子 Run 启动后不随父 Run 后续权限切换联动；省略或空 `mustUseSkills` 不额外强制技能。
- 顶层可选 `modelKey` 与 `reasoningEffort` 只作用于本次 Run：`modelKey` 是模型注册表的 key（不是供应商 `modelId`），`reasoningEffort` 取 `NONE/LOW/MEDIUM/HIGH/XHIGH/MAX`，可单独提供；二者映射到 Query 的 `model.key/model.reasoningEffort`，沿用同一准入校验，未注册或非 chat 模型在权限审阅计划生成前失败，启动准入再次校验，失败不创建 Chat、不消费审批。省略时使用目标 Agent 自身配置；同一调用方可用不同模型发起多个子 Chat，续聊也可换模型。ACP 目标只接受其 bridge 提供的模型。二者计入请求摘要与提升审批的审阅内容。可选 key 通过同一连接器的 `chat_query` `models` 动作列出（仅 chat 类型模型），无需挂载 `builtin.platform-control`。
- `chatName` 去除首尾空白后必须非空，沿用现有 Chat 手工命名规则（不按首条消息的 40 字截断）；与 `chatId` 互斥。名称在新 Chat 创建时写入，后续正常续聊不覆盖；省略则沿用现有命名。没有 `taskName` 别名。
- 权限按 `default < auto_approve < full_access` 与父 Run 受理时的实时档位比较：省略继承，显式同级或降级直接启动，显式高于父档位必须在父 Chat 中由用户人工批准本次启动。批准只决定新 Run 的初始权限，不改变父 Run 或 Agent 配置。无论继承还是显式指定，都受目标 `interactionConfig.accessLevel` 和原有权限准入限制；ACP/Proxy 沿现有路径转发，不另设特例。旧 `runQuery.allowAccessLevelOverride` 已移除，`tools.yml` 出现 `runQuery` 时启动失败并提示运行 `config-migrate`。
- 提升审批是强制人工 HITL：父 Run 的 `auto_approve/full_access`、规则级免审（`approve_rule_run`）、等待期间切换父 Run 档位、模型自述或伪造参数都不能代替；`approved`、`grant` 等字段按未知参数拒绝。审阅页 `chat_start_review` 展示调用方、目标、新建或续聊、权限变化、完整任务内容和指定技能，只有“批准本次启动”和拒绝，表单返回值不能改写调用参数。等待时间沿用通用工具审批（Run 的 HITL budget，未配置时 600 秒），超时按拒绝处理；拒绝、超时、中断均不启动任务，审批前也不创建 Chat、不注册 Run。
- 批准后由 Runtime 在父 Run 权限的短临界区（授权受理点）内复核父 Run 是否仍活动、当前档位与版本，并同步消费一次性收据。已形成审批计划的调用必须按其冻结基线消费收据：等待期间父权限版本变化（包括切走后又切回，或升到不再跨档）返回可重试的 `run_start_review_stale`；原判定不跨档但受理时父权限已下降返回可重试的 `run_start_approval_required`；继承档位在准入与受理之间变化返回 `run_parent_access_level_changed`。这三类错误均带 `executionState: not_started` 与 `retryable: true`，模型以相同目标、任务和档位发起新的工具调用后按新的父档位重新判断；已进入审阅的那次调用在父 Run 结束前始终保留其冻结基线，重放同一 `toolId` 不会重新判断，也不能无收据启动。收据缺失或已使用、用户拒绝不属于可重试错误，不得通过省略或降低 `accessLevel` 规避审批。收据只在进程内存在，只授权一次启动尝试，启动失败不恢复，重启后不重放。
- 目标准入在消费收据之前完成，被目标拒绝的请求不消耗人工审批。Runtime 对所有跨档请求执行上述检查，不依赖调用入口；Run 管理器不提供原子受理能力时返回 `run_start_authorization_unavailable`，不退化为普通状态读取。审计中的父档位与版本取自受理点实际核验的值：缺少消费回调、摘要不匹配或收据已消费都在创建 Chat 前失败。调用方 context 在受理前取消返回 `chat_start_cancelled`，父 Run 已结束返回 `run_parent_not_active`；受理后新 Run 的生命周期与调用方分离。`auto_approve` 不等于全部免审，破坏性操作等仍可能等待人工，硬约束继续生效。
- `mustUseSkills` 不经权限审批，仍经目标 `interactionConfig.mustUseSkills`、技能可用性与既有只读挂载校验。连接器技能禁止选择；不修改目标 Agent 定义或增加权限档位。
- 不接受 `requestId/runId/role/model/stream/planningMode/editingMode` 等其他字段。未知字段返回 `unknown_argument`，错误类型、空白字符串、显式 null、非法枚举和字段冲突返回 `invalid_request`。兼容性变化：过去 handler 可能静默忽略 `taskName` 等字段，现在明确拒绝，`taskName` 错误会提示使用 `chatName`。
- 返回前已完成 catalog/admission、chat/run 注册和 event bus 建立，然后异步执行本地或 Proxy 目标。
- 新 chat 的 source 为 `run-query:<agentKey>`；目标 `request.query` 使用 `runOrigin {agentKey, chatId, runId, toolId, permission}` 记录调用方 Agent、父 Chat、父 Run 与具体工具调用，但不含 subject。`permission` 记录 `parentAccessLevel/parentAccessVersion`、可选 `requestedAccessLevel`、实际 `accessLevel`、`source`（`inherited/explicit/approved`）、`requestDigest`，人工批准时另含 `approvalDigest`。
- 目标 run 不继承父 run 的 target。Desktop 模式下，它首次调用 `desktop_action` 或网页控制工具时按独立 run 绑定当前 `desktop-main`；父 run 结束不撤销该绑定。Standalone 仍要求目标 run 自己通过 query/attach 获得 client target。
- 同一父 `runId + toolId` 成功后的合法重试返回同一个目标 `chatId/runId`，不重新命名、不修改启动配置、不再次审批；同一调用携带不同启动参数返回 `idempotency_conflict`（省略 `agentKey` 与显式当前 Agent 使用补齐后的相同目标摘要；省略 `accessLevel` 与显式 `default` 视为不同参数，父权限变化不影响该判断）。确定未启动的失败会清除幂等记录，可以重试；启动后无法确认状态时返回 `run_start_outcome_unknown`（`executionState: unknown`，附 `run.runId/chatId`）并保留记录，重试只对账该 Run，不再次启动。这是进程内幂等，不构成跨进程的恰好一次保证。不同 tool ID 可并行创建独立 run，没有额外并发上限。

### `chat_get_status` 与 `chat_interrupt`

```json
{"runId":"..."}
```

```json
{"runId":"...","message":"无需继续"}
```

- status 是只读工具，可在 BTW/read-only 策略中调用；返回 `running/awaiting/completed/failed/interrupted`、`lastSeq` 和时间字段，终态返回最终 `content/error`。query/status 的 `run.accessLevel` 取 Run 当前值，运行中调整后更新，终态保留最终档位；不扩大既有状态保留期限。
- awaiting 支持 `question/approval/form/planning`，返回 `awaitingId/mode/itemCount`。活动等待不止一个时，按公开 awaiting ID 字典序稳定选择一个，`run.awaitingCount` 表示活动等待项总数。`itemCount` 是选中等待项的真实条数，不是摘要条数。
- 审批 `summaries` 仅含工具名、描述、策略原因，最多 3 项，每个字符串最多 200 个 Unicode 字符，裁剪标记 `truncated:true`。摘要随活动等待项保存和克隆，Team 成员等待项发布时保留摘要，不依赖可能被淘汰的事件缓存；恢复等待无活动项时读取持久化 ask，旧记录缺字段不编造。question 保留原 questions/payload，新支持的其他类型不透传原始 payload。
- 发现人工审批等待时，应告知用户到目标 Chat 处理，不持续轮询；本工具组不提供代审批能力。
- Chat 工具组不提供 submit/steer；awaiting 必须由用户在目标会话中处理，普通 `/api/submit` 与 `/api/steer` 协议不变。
- interrupt 复用普通 run owner 校验与 Proxy forwarding。
- status/interrupt 只接受由 `chat_start` 创建、且调用 Agent 与 subject 均和当前调用方相同的 run；任意外部 run 即使 runId 已知也返回 `run_not_owned`。

### 调用边界

- 只有普通主 Agent 根 run 可以调用；`agent_invoke` child、Team 成员和隐藏协调器均拒绝。
- 允许目标与调用 Agent 自身相同。省略 `chatId` 时创建新 chat；指定另一个 owner 相同且无 active run 的 chat 时允许继续；指定父 run 当前 chat 时沿用单 chat 单 active run 约束并返回 `active_run_conflict`，不会自动替换 `chatId`。
- `chat_start` 创建的目标 run 会携带可信 origin 标记并视为 depth 1；即使目标 Agent 配置了任一 Chat 工具，再次调用仍返回 `run_chaining_not_allowed`。不增加可配置的深度字段。
- 旧 `contextConfig.agents` 已忽略；目录发现不定义目标 allowlist。实际调用不存在的目标仍返回 `agent_not_found`。
- 缺少主 run 上下文返回 `run_context_required`，child/Team 调用返回 `run_caller_not_allowed`，幂等 query 等待被取消返回 `chat_start_cancelled`。

## TEAM 的 `agent_delegate`

目录式 `runtime/teams/<teamId>/team.yml` 创建 orchestrated Team。每个 run 从 embedded definition 克隆 `agent_delegate` schema，并按冻结 roster 动态补充成员枚举和任务上限。

隐藏总控固定拥有四个工具：

```text
agent_delegate
plan_add_tasks
plan_get_tasks
plan_update_task
```

### 参数

`agent_delegate` 只接受 `tasks`：

| 参数 | 必填 | 约束 | 语义 |
|---|---|---|---|
| `tasks` | 是 | 数组，至少 1 项；`maxItems` 等于冻结 roster 大小 | 本次调用需要委派的成员任务 |
| `tasks[].agentKey` | 是 | 必须是动态 `enum` 中的精确成员 key；同一次调用不可重复 | 目标 Team 成员 |
| `tasks[].task` | 否 | string | 自定义任务文本；省略或为空时使用原始用户消息 |
| `tasks[].taskName` | 否 | string | `task.*` 进度事件的标题 |
| `tasks[].files` | 否 | 最多 10 项 | 附加文件或当前 chat 资源，转换成 references 后与原始 references 去重 |

`additionalProperties:false` 同时作用于工具根对象和每个 task。`maxParallel` 不进入工具 schema 的任务上限：它只控制 runtime 同时运行的成员数；`tasks` 数量超过 `maxParallel` 时，仍属于同一次工具调用，由 runtime 分波执行并一次性聚合结果。

目标 `agentKey` 不得等于当前 TEAM session 的执行 Agent key；服务端会在 roster 解析前拒绝自调用，且整批不产生成员任务事件。

成员始终继承原始请求的 `role`、`scene`、`references` 和该成员可见的 Team 历史。自定义 `task` 只替换 message，不会丢失这些上下文。

### 场景枚举

明确由一个成员回答与给单个成员自定义任务是同一条执行路径：

```json
{"tasks":[{"agentKey":"writer"}]}
```

```json
{
  "tasks": [
    {
      "agentKey": "writer",
      "task": "只检查文档中的事实错误",
      "taskName": "事实检查"
    }
  ]
}
```

无法判断合适成员与明确选择多个成员也是同一条多项委派路径：

```json
{
  "tasks": [
    {"agentKey":"writer"},
    {"agentKey":"reviewer"},
    {"agentKey":"researcher"}
  ]
}
```

```json
{
  "tasks": [
    {"agentKey":"researcher","task":"收集事实依据"},
    {"agentKey":"reviewer","task":"检查潜在风险"}
  ]
}
```

一项和多项没有不同的终止规则。每项都产生 `task.start` 和 `task.complete/error/cancel`，全部结果都回注隐藏总控，随后由总控更新计划、继续委派或生成唯一的 Team 最终回答。

工具结果统一为：

```json
{
  "results": [
    {
      "agentKey": "reviewer",
      "taskName": "风险检查",
      "status": "completed",
      "content": "最终成员结果"
    }
  ]
}
```

失败项可增加 `error`、`errorCode`。一个成员失败不会取消同批其他成员；单成员失败和多成员部分失败也走相同的结构化返回路径，由总控决定改派、解释或继续。

## 计划与执行状态

```text
routing -> waiting_members -> coordinator -> complete
```

- 简单请求可以直接调用一次 `agent_delegate`。
- 复杂请求先用 `plan_add_tasks` 创建有序任务列表，再用 `plan_update_task` 维护状态。任务按数组顺序执行且同时最多一个 `in_progress`；只有当前阶段终态后才能启动下一阶段。
- `plan_get_tasks` 用于读取当前计划；计划工具不自动启动成员。
- 当前计划阶段可以在一次 `agent_delegate` 中并行委派多个成员；成员并行不会产生多个活动计划阶段。`agent_delegate` 本身没有 direct、fanout、invoke、DAG 或串行模式。
- 最前面的非终态 task 可由 `init` 进入 `in_progress` 或直接进入 `completed/failed/canceled`，`in_progress` 可进入任一终态；终态不可复活，需要重试时在计划末尾追加新 task。
- 每个用户回合至少成功发起一次 `agent_delegate` 后，总控才能输出最终答案；只调用计划工具不算完成路由。

## 事件、历史与隐私

- 成员事件携带根 `runId`、task `taskId`、`teamId`、成员 `agentKey`、`actor.type:"agent"` 和 `presentation:"task"`。
- 成员正文、reasoning 和 tool chain 不会成为根回答；根 `content`、run summary 与 `AssistantText` 只取隐藏总控的最终 Team 回答。
- 协调器 reasoning、`agent_delegate` 工具卡和原始工具结果不发送给客户端，也不进入普通工具 catalog。
- 成员读取专用 Team 历史：保留自己的 tool chain，只读取其他成员最终正文和 Team 最终正文，不读取其他成员 reasoning/tool result。
- 根总控历史保留用户轮次、Team 最终正文和带成员标识的成员最终正文，排除 child prompt、reasoning、tool chain 与原始中间结果。
- 历史回放仍识别旧 `team_delegate` / `team_invoke` 调用，但只转换为 `agent_delegate agentKeys=...` 安全摘要；新 run 不接受旧工具名。

## HITL 与限制

- 成员不注册独立 active run；public `awaitingId` 使用 `taskId:rawAwaitingId`，submit 时映射回 child raw ID。
- 成员的 awaiting 不合并：按到达顺序排队，一次只发布一位成员的等待项，答复后再发布下一项；每项按成员自己的 mode 提交并原样转给对应 child。
- Team-owned run 的 submit 使用 `teamId + runId + awaitingId`，不能传隐藏总控 key。
- interrupt 作用于整个根 run；steer 写入总控 run，不直接选择某个成员。
- Team 不能作为另一个 Team 的成员或 child 目标。
