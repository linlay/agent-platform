# 智能体配置说明

本文件说明 agent / team / skill 的目录化配置、prompt 文件、CODER、KBASE、memoryConfig 与 runtimeConfig。当前 Go runtime 已支持从 `<AP_RUNTIME_DIR>/agents` 读取 `runtime/agents/*.yml` 与 `runtime/agents/<key>/agent.yml`，并将结果直接暴露给 `/api/agents` 与 query agent 选择逻辑。

技能 ID、显示名称、多语言、版本与修订号见 [技能展示元数据](技能展示元数据.md)。

## 当前状态

当前 Go 版运行时：

- `models` 会从 `AP_RUNTIME_REGISTRIES_DIR/models` 读取
- provider 连接配置会从 `AP_RUNTIME_REGISTRIES_DIR/providers` 读取
- catalog 中的 agent/team/skill/tool 已改为目录驱动
- `runtime/agents/*.yml` 与 `runtime/agents/<key>/agent.yml` 都会参与装载
- Team 只接受 `runtime/teams/<teamId>/team.yml`；平铺 `runtime/teams/*.yml|yaml` 会使启动失败

## Agent YAML 保存顺序

结构化保存（包括修改模型、工具、技能和连接器）共用 `internal/catalog/agent_editor.go` 的 `agentYAMLKeyOrder`，整份 YAML 按固定语义顺序输出：

- 身份定位：`key`、`name`、`mode`、`role`、`description`、`icon`。
- 模型与限制：`modelConfig`、`budget`、`interactionConfig`。
- 执行环境：`runtimeConfig`、`projectConfig`、`proxyConfig`、`channelConfig`。
- 能力与上下文：`toolConfig`、`skillConfig`、`connectorConfig`、`contextConfig`、`kbaseConfig`、`memoryConfig`、`promptFile`、`runtimePrompts`、`stageSettings`。
- 展示引导：`visibility`、`controls`、`greetings`、`introductions`、`wonders`。

排序不会补写缺失字段。已知字段之后的扩展字段按名称升序排列。嵌套路径 `modelConfig` 按 `modelKey/serviceTier/reasoning/sampling`，`modelConfig.reasoning` 按 `enabled/effort`，`contextConfig` 按 `tags/agents` 排列；其他对象按字段名排序。所有列表保留元素顺序。

首次结构化保存会统一排序、两空格缩进和字符串格式，不保留原注释、空行或引号风格；相同数据重复保存的文本保持一致。原始 YAML 编辑入口保留提交文本，但下一次结构化保存仍按上述规则输出。部署新代码不会主动批量改写已有 Agent 文件。

## Agent 配置示例

以下示例展示常用配置字段：

```yaml
key: agent_key
name: agent_name
role: 角色标签
description: 描述
icon: "emoji:🤖"
greetings:
  - 今天想让我帮你做点什么？
introductions:
  - 我可以帮你总结材料、拆解问题，并给出下一步行动建议。
  - 需要快速进入状态时，我会先帮你找最值得处理的切入点。
wonders:
  - 帮我总结这段材料
  - 给我 5 个可以马上执行的下一步
modelConfig:
  modelKey: qwen3-max
toolConfig:
  tools: ["bash", "datetime"]
connectorConfig:
  connectors:
    - flowcenter
mode: GENERAL
plain:
  systemPrompt: |
    系统提示词
```

字段含义如下：

- `modelConfig.modelKey` 引用 `registries/models/*.yml`；除 PROXY 与 ACP CODER 外，所有 agent 都必须显式声明
- `toolConfig.tools` 声明普通工具名列表，`connectorConfig.connectors` 声明连接器 id 列表；不支持旧式 `toolConfig.overrides/backends/frontends/actions`
- `mode` 决定 agent 类型，`engine` 决定由谁执行

### 类型与执行引擎

| 界面类型 | `agent.yml` | 执行 |
|---|---|---|
| 通用智能体 | `mode: GENERAL`（缺省） | Platform 内置引擎 |
| 编程智能体 | `mode: CODER` | Platform 内置引擎 |
| 知识库智能体 | `mode: KBASE` | Platform 内置引擎 |
| 外部引擎 | `engine: acp` + `runtimeConfig.acpBridgeId` | ACP bridge |

- `GENERAL` 是通用智能体的类型名；YAML、管理接口和 mode 筛选只接受 `GENERAL`，提交 `REACT` 会报错，现有 `agent.yml` 必须改为 `GENERAL`。仅历史 Chat/Run 数据中的 `REACT` 兼容读取，存储不改写，接口响应映射为 `GENERAL`。
- 顶层 `engine` 取 `native` 或 `acp`，缺省为 `native`，不会根据 `runtimeConfig.acpBridgeId` 推断。`native` 是默认值，管理接口保存时不写入文件。
- `engine: acp` 没有自己的 mode：`mode` 可以省略，写了只能是 `CODER`；必须同时配置 `runtimeConfig.acpBridgeId`。只写 `acpBridgeId` 而没有 `engine: acp` 会使配置校验失败，旧文件需要补上这一行。
- `/api/agents` 与 `/api/agent` 返回 `engine`（`native` / `acp`）；`engine: acp` 的 Agent 仍返回 `mode: CODER`。PROXY、CHANNEL 不由 Platform 执行，不返回 `engine`。
- Agent 是对话型还是项目型只取决于 Workspace：没有 `runtimeConfig.workspaceRoot` 或使用 `@root` 是对话型，`/api/agents` 的 `workspaceDir` 为空；配置了具体目录是项目型，`workspaceDir` 返回该目录。

### 工具白名单与 Mode 默认值

`toolConfig.tools` 是 Agent 自身声明的普通工具列表；Native 普通 Agent 还会合并 Platform 的 `preset-tools`，再应用 `toolConfig.excludeTools`；`connectorConfig.connectors` 是 Agent 自身连接器挂载列表（包含 MCP、CLI 和技能），普通 Native Agent 再合并平台 `preset-connectors`。Platform 在新 Run 创建时将所选 Server 当前同步成功的工具加入 Agent 最终工具集合。MCP Registry 只负责连接、鉴权和同步，不通过反向 binding 修改 Agent 权限。

- `GENERAL` 未声明自身工具时仍获得 Platform 预置工具；未预置且未声明工具、未挂载连接器时为无工具；技能、环境和能力开关不授予工具。其他普通工具列入 `tools`，MCP 工具可以逐项列入 `tools`，也可以通过挂载连接器导入其全部 MCP 工具。
- native `CODER` 与 GENERAL 共用预置和显式声明规则；空列表不触发 mode profile 工具回退，main/execute 不补充计划任务工具。
- `engine: acp` 不使用 Platform 工具；非空 `toolConfig.tools`、`toolConfig.excludeTools` 或 `connectorConfig.connectors` 会使配置校验失败。
- 专用 `KBASE` 没有固定工具集合：工具取自预置工具与 `toolConfig.tools` 合并并排除后的结果，分发示例通过 `kbase.preset-tools` 提供五个知识库工具；技能和 CLI 连接器不追加 `bash`。未声明任何文件工具时 Agent 仍可加载，但无法浏览或编辑 Workspace，加载日志会给出 `kbase_file_tools_missing` 警告。通过管理接口创建 KBASE 时，Platform 会从创建默认值中的 `datetime` 与五个文件工具中扣除当前预置项，仅把剩余项写入 `agent.yml`。

Skill、Sandbox、runtime env、`memoryConfig` 和知识库绑定均不隐式追加工具。最终工具集合会冻结到 run session；后续 catalog 变化只影响新 run。

连接器挂载会自动增加 bin PATH 并导入全部技能；这些技能不进入 mustUseSkills 可选列表，显式传入其 key 也会拒绝。包结构与新配置示例见 [连接器](连接器.md)。旧 `toolConfig.mcp-servers` 在解析时硬失败。

## Model Sampling

agent 可在 `modelConfig.sampling` 声明默认采样参数；`PLAN-EXECUTE` 可用 `stageSettings.plan/execute/summary.modelConfig.sampling`，planningMode 可用 `stageSettings.planning/execute.modelConfig.sampling` 按字段覆盖：

```yaml
modelConfig:
  modelKey: qwen3-max
  sampling:
    temperature: 0.7
    topP: 0.9
    presencePenalty: 0
    frequencyPenalty: 0
    seed: 42

stageSettings:
  execute:
    modelConfig:
      sampling:
        temperature: 0.4
```

继承优先级为 `stageSettings.<stage>.modelConfig.sampling` > `modelConfig.sampling` > 运行时默认。未配置时，OpenAI-compatible 主链路仍发送 `temperature: 0`，保持确定性默认行为。

字段使用 camelCase：`temperature`、`topP`、`presencePenalty`、`frequencyPenalty`、`seed`。OpenAI-compatible 协议会映射为 `temperature`、`top_p`、`presence_penalty`、`frequency_penalty`、`seed`；Anthropic 协议只发送 `temperature` 和 `top_p`。

## Agent Identity 与 SOUL.md 边界

`agent.yml` 是 agent 身份与能力元数据的唯一事实源：

- `key`
- `name`
- `role`
- `description`
- `greetings`
- `introductions`
- `wonders`
- `mode`
- `toolConfig`
- `skillConfig`
- `runtimeConfig`

运行时会先根据 `agent.yml` 生成统一的 `Agent Identity` prompt section，再拼接其他 prompt 层。该 section 只包含 `key/name/role/description/mode` 身份事实，不混入工具路由或当前目标解析说明。

`Agent Identity.key` 是当前执行 Agent 的唯一模型可见身份事实。需要按当前 Agent 选择调用目标时，由对应工具描述定义解析规则；当前 `chat_start` 会把“当前智能体”“本智能体”“你自己”解析为该 key，并禁止用其他 runtime agent 候选摘要替代。

`SOUL.md` 的职责是长期行为提示，不是配置副本：

- 允许写人格、协作方式、风险姿态、硬边界、非目标
- 允许写长期稳定的行为约束
- 不应重复 `key/name/role/description/mode`
- 不应复制 tools、skills、sandbox、环境路径或一次性任务说明

推荐结构：

```md
# Soul

## Persona

## Boundaries

## Working Style

## Long-Term Notes
```

## Greetings、Introductions 与 Wonders

三者都是 UI 展示元数据，不参与 agent identity prompt 或系统提示词。

- `greetings`：主标题问候语数组，新会话随机显示一条；支持客户端固定占位符 `${agent}`，显示智能体名称并在有其他智能体时提供切换按钮。缺失或没有有效文本时，客户端显示“与 <agentName> 对话”。Platform 原样返回模板，不执行表达式，`introductions` 不解析占位符。
- `introductions`：自我介绍数组，输入框为空时随机显示一条作为 placeholder；缺失时使用客户端默认输入提示，不回退到 `greetings`。
- 两个数组独立选择，普通重渲染期间保持稳定。运行时过滤空文本，通过 `/api/agent` 返回；`/api/agents` 列表摘要不携带这些字段。单数 `greeting` 不再作为兼容来源。

```yaml
greetings:
  - 今天想让我帮你做点什么？
  - 很高兴见到你，我们开始吧。
introductions:
  - 我可以帮你练习词汇、复盘错题，也能把今天的学习拆成小步骤。
  - 你可以把单词表发给我，我会帮你设计一轮轻量测验。
```

原先用于输入框的自我介绍文本应移到 `introductions`；`greetings` 现在只用于主标题，不自动复制或迁移内容。

`wonders` 保持原语义：具体的 query 问题参考，也就是用户可以直接点选或提交的示例问题。

```yaml
wonders:
  - Quiz me on vocabulary
  - 帮我检查当前工作区的变更
  - |-
    帮我制定一个三步学习计划
    并给出今天可以开始的第一步
```

## Agent 契约与 mode 关系

Go 实现不使用类继承。`internal/agent` 定义 mode descriptor、profile、capabilities、system-init spec 与公共 prompt 渲染契约；`internal/agent/coder`、`internal/agent/kbase`、`internal/agent/team` 分别持有自身 mode 规则，`internal/agent/builtin` 只做静态分派。KBASE 公共契约与 KBX 执行门面独立于具体 mode：

```text
internal/agent
├── coder                 # CODER 具体 mode
├── kbase                 # KBASE 专用 mode 的 profile/prompt/boundary/create
├── team                  # TEAM 内部 mode 与集中调度规则
└── builtin               # 静态分派，不是插件生命周期

internal/knowledge        # mode 中立的 config/source/DTO/tools 与路径过滤
internal/kbx              # 受管 CLI、检索、监听和维护调度
app/knowledge_adapter.go  # catalog 快照 -> knowledge.AgentSpec
catalog.TeamSnapshot      # run-scoped Team/成员/协调器配置快照
```

CODER、KBASE 和 TEAM 都是 `internal/agent` 契约下的具体 mode，但 KBASE capability 不依赖 mode 或 catalog；app adapter 为绑定 libraryId 的 Agent 构造 `AgentSpec`，来源范围由中心库 collections 决定，Workspace 只作为文件工作目录。TEAM 只服务于目录式 Team：运行时从 `TeamSnapshot` 合成隐藏协调器，不把它注册成普通 `AgentDefinition`。普通 Agent YAML 声明 `mode: TEAM` 会校验失败，管理接口也不能创建 TEAM agent。

## Team 类型与配置

Team 配置事实源是 `runtime/teams`。只接受目录式定义；平铺 `runtime/teams/<teamId>.yml|yaml`、`defaultAgentKey` 和 `runtimeMode: legacy` 均已移除，发现即启动失败。

### Team

目录式 Team 使用以下结构：

```text
runtime/teams/research/
  team.yml
  SOUL.md       # 可选：Team 人格
  AGENTS.md     # 可选：Team 工作规则
```

`teamId` 来自目录名。最小 `team.yml`：

```yaml
name: Research Team
description: 研究、写作与复核
agentKeys:
  - researcher
  - writer
  - reviewer
orchestrator:
  modelConfig:
    modelKey: qwen3-max
    reasoning:
      enabled: true
      effort: HIGH
    sampling:
      temperature: 0.2
  budget:
    maxSteps: 40
    tool:
      maxCalls: 20
  maxParallel: 3
```

- `orchestrator.modelConfig.modelKey` 必填；`defaultAgentKey` 禁止出现。
- `maxParallel` 默认为 5，只接受 1–5 的整数；它只限制同时执行的成员数。一次 `agent_delegate` 可以列出整个冻结 roster，超出并发数时由 runtime 分波执行。
- `SOUL.md`、`AGENTS.md` 会进入协调器 system prompt，但不能覆盖 `internal/agent/team` 的硬编码路由、安全和隐私规则。
- 目录式 Team 的成员列表为空或任一成员失效时，query/automation 返回不可用，不回退到全局默认 Agent。

隐藏总控每个用户回合统一调用 `agent_delegate`：一项和多项使用相同的 `tasks[]` 契约；`agentKey` 来自本次 run 冻结 roster，`task` 可省略并默认使用原始用户消息，`taskName/files` 可选。同一次调用中成员不可重复，`tasks.maxItems` 等于 roster 大小。成员继承原始 role、scene、references 和专用 Team 历史，附加 files 会转换并去重。

复杂任务由总控先用 `plan_add_tasks` 创建有序任务，再用 `plan_get_tasks`、`plan_update_task` 维护状态。flat plan 同时最多一个 `in_progress`；最前面的非终态 task 可由 `init` 进入 `in_progress` 或直接进入 `completed/failed/canceled`，`in_progress` 可进入任一终态；当前阶段终态后才能操作下一阶段，终态重试必须追加新 task。一个当前阶段仍可在单次 `agent_delegate` 中并行委派多个成员，成员并行不等于多个计划阶段同时运行。每个用户回合至少成功发起一次委派后才能生成最终答案；所有成员结果都回注总控，根回答只由总控输出。

`agent_delegate` 是 embedded、session-local、internal-only 工具：Team 自动注入，普通 Agent 配置会校验失败，`/api/admin/tools` 不返回它，tool/reasoning 事件也不下发客户端。成员输出复用 task/content 事件，并携带 `actor`、`teamId`、成员 `agentKey` 和 `presentation:"task"`。

### 共同边界

run 启动时 catalog 会原子解析 Team、有效/失效成员、成员 `AgentDefinition`、协调器配置与 prompt，生成本次 run 使用的不可变快照。

- `teamId` 在 chat 创建后固定；已有无 Team chat 也不能补绑 Team。
- Team 请求只传 `teamId`，传入 `agentKey` 会被视为绕过协调器并返回 400。
- Team 的公开 run owner 是 `teamId`；协调器执行 key 不出现在普通 Agent catalog、常规 run 事件、chat summary 或控制接口中。
- Team 成员不能再调用 `agent_invoke`，也不能把另一个 Team 作为成员或子任务目标；ACP CODER 当前不能作为 child。
- Automation、HTTP、WebSocket、submit continuation 与子智能体准入使用同一 Team resolver。历史 chat、archive、restore 与 derive 保留原始身份字段，但历史记录不再恢复旧 Team 路由。
- 运行中的 Team 快照不受 catalog 热重载影响；下一次 run 才读取新成员、prompt 与协调器配置。

## 当前仍有边界

- TEAM 不提供委派级 DAG DSL；计划状态和后续总控轮次表达串行、分支与重试。
- `agent_delegate` 的并行 HITL 按并发波次合并为 Team-level form。
- ACP CODER 不能作为 Team/`agent_invoke` child；普通 Agent 管理接口也不提供 TEAM 创建或编辑入口。

## Context Tags

当前 Go runtime 不会为所有 agent 自动附加一组全局默认 `context tags`；每个 agent 只从 `contextConfig.tags` 读取声明：

```yaml
contextConfig:
  tags:
    - system
    - session
```

支持标签：

- `system`
- `session`
- `owner`
- `memory-global`
- `memory-agent`

其中：

- `session` 会暴露运行时上下文
- `owner` 会注入 `<AP_RUNTIME_DIR>/owner` 下的 markdown 内容；`mode: CODER` 不会默认启用，需要显式声明
- `sandbox` 不再通过 `context tags` 控制；只要 agent 声明了 `runtimeConfig.environmentId`，运行时会自动注入 sandbox context
- `memory-global` 注入总体 `summary.md`，`memory-agent` 注入当前 Agent 的 `agents/<agentKey>/summary.md`，顺序跟随 tags；默认不注入，不使用旧 `memory` 标签。
- `memoryConfig.enabled` 仅控制对话是否参与记忆采集，与上下文注入独立。全局 `memory.enabled: false` 关闭采集与注入；ACP/Proxy/CHANNEL 不注入。

### Agent 发现与旧候选配置

Agent 候选不再自动注入 system prompt。需要发现目标的总管 Agent 显式挂载 `builtin.platform-control`，按需调用 `catalog_query`：

```json
{"action":"list","args":{"resourceType":"agent","status":"valid","limit":100}}
```

列表不按调用 Agent 的候选配置过滤，包含当前 Agent，排除内部 TEAM 协调器；沿 `nextCursor` 翻页才是完整目录。Agent 条目保留 `resourceKey/resourceType/valid/diagnostics`，补充 `key/name/role/description/mode/invocable`。`invocable` 仅表示目标满足 `agent_invoke` 的静态条件（visibility 含 invoke/internal、mode 支持子调用或使用受支持的 ACP 后端、有效工具中不含 agent_invoke），不代表调用者获得授权，也不豁免自身调用、嵌套或执行时有效性检查。`chat_start` 不受这些子调用目标条件限制，保留给当前 Agent 自己创建独立 Chat 子任务的能力。当前身份始终以 `Agent Identity.key` 为准。

兼容例外：旧 `contextConfig.agents`（包括空值及非法类型）和 `contextConfig.tags` 中的 `agents` 均忽略，不拒绝加载，也不解析或验证候选引用。加载后的管理列表与详情合并显示一条 `severity: warning`、`code: context_agents_ignored` 诊断，提示改用 catalog_query.list；该 warning 不改变 Agent 的 ready 状态和有效性。删除旧配置并重载后告警消失，不逐 Run 写日志。新编辑器不再提供 agents 标签。其他旧分散配置的拒绝规则不变。

升级不要求先迁移。可选运行 `config-migrate --config-dir <部署目录> --agents-dir <Agent目录>` 预览，再加 `--apply` 清理旧声明；不传 `--agents-dir` 不扫描 Agent。扫描覆盖该根目录中的 `.yml/.yaml` 和其子目录中名为 `agent.yml` 的文件，非根目录 `agent.yaml` 不在该迁移扫描范围内。命令也执行其已有的其他配置迁移，应先查看预览；它不自动挂载连接器或改变调度权限。历史 Chat 不改写。

platform-control 是显式管理授权，除摘要 list 外仍包含完整配置 get 与其他管理工具，并非摘要专用权限。本次不改变 task-control 预置、chat_start、agent_invoke、Automation 或 Team 调度授权；没有目录发现能力不等于禁止跨 Agent 调用。

## Prompt Files

目录式 agent 会按约定读取 prompt 文件：

- 普通模式默认读取 `AGENTS.md`
- 顶层 `promptFile` 可显式覆盖普通模式 prompt
- `PLAN-EXECUTE` 默认读取 `AGENTS.plan.md`、`AGENTS.execute.md`、`AGENTS.summary.md`
- `stageSettings.<stage>.promptFile` 可显式覆盖对应阶段
- `PLAN-EXECUTE` 阶段缺少约定文件时，先回退顶层 `promptFile`，再回退 `AGENTS.md`
- `mode: CODER` 还会按 `configs/agent-settings.yml` 读取 `runtimeConfig.workspaceRoot/AGENTS.md`，用于注入项目级 workspace 规则；配置了 `projectConfig.promptFiles` 时改按该列表读取
- `mode: KBASE` 不读取 knowledge source 中的 `AGENTS.md`，只通过 KBASE 系统提示和知识库工具工作；普通 Agent 附加 KBASE capability 时仍按自身 mode 规则加载 prompt files

`PLAN-EXECUTE` 的阶段配置推荐统一放在 `stageSettings.<stage>` 下：

```yaml
stageSettings:
  plan:
    promptFile: AGENTS.plan.md
    modelConfig:
      modelKey: qwen3-max
    toolConfig:
      tools: ["file_read", "file_grep"]
```

阶段内 `modelConfig` 支持 `modelKey`、`reasoning`、`sampling`、`maxOutputTokens` 等运行参数；`PLAN-EXECUTE` 阶段内 `toolConfig.tools` 覆盖该阶段可用工具。原生 GENERAL、CODER、KBASE 的 `stageSettings.planning/execute.toolConfig.tools` 不支持，出现即加载失败，原生 GENERAL、CODER、KBASE 的 `stageSettings.planning/execute` 也不允许声明 `modelKey`，规划与执行一律使用 Agent 自身模型；规划与执行的工具差异统一由 `agent-settings.yml` 的 `planning-mode` 决定，见 [Agent 配置合并](Agent配置合并.md#planning-mode-工具排除)。

## CODER Mode

CODER 是一等 agent mode。内建 icon、工具、context、budget、cache key、创建前缀及 capability 的代码事实源是 `internal/agent/coder`；catalog 只在 YAML 未显式声明对应字段时应用该 profile。所有 CODER（native、ACP、host、sandbox）都必须配置可解析为现存绝对目录的 `runtimeConfig.workspaceRoot`；`@chat` 不再是合法 Workspace。

native CODER 使用 platform 的本地工具循环。工具来自全局/mode preset 与 Agent 显式声明，应用 `excludeTools` 后再合并挂载连接器自身工具。main / execute 保持该结果；planning 按排除清单收窄并追加 `finalize_planning`，缺省排除清单包含 `artifact_publish`。

配置 `engine: acp` 的 ACP CODER 由 ACP bridge 自行决定可用能力，platform 不声明、透传或模拟任何工具。因此它的 effective `tools` 始终为空，且 `toolConfig.tools` 只能省略或设为空列表；任何非空列表都会使 Agent 配置校验失败。

通过管理接口 `/api/admin/agents/create` 创建 `mode: CODER` 或 `mode: KBASE` agent 时，请求只需要表达创建意图；两者都必须传 `runtimeConfig.workspaceRoot`，ACP CODER 额外传顶层 `engine: acp` 与 `runtimeConfig.acpBridgeId`。创建前缀和 mode profile 分别由 `internal/agent/coder`、`internal/agent/kbase` 维护；创建 `mode: GENERAL` 时沿用调用方提供的 key，只用 `configs/agent-settings.yml` 的 `general.default-agent` 代填缺省的模型、reasoning 与 budget，创建规则由 `internal/agent/general` 维护；配置文件只提供可覆盖的模型、reasoning 与 budget 输入。存在最终 Workspace 时，生成流程会把缺省 `name` 设为目录 basename。

## 智能体创建

客户端通过 `GET /api/admin/agents/creation-defaults` 获取类型、可用模型、默认模型、建议基础工具与 ACP bridge。品牌功能分组由 Desktop 的环境包或 WebClient 的静态配置定义，客户端依据实时资源目录检查可用性并展开为具体配置。

`POST /api/admin/agents/create` 接收 JSON `{definition, key?, isProject?, soulPrompt?, agentsPrompt?}`。`definition` 使用 Agent 配置结构，包含 `mode`、`engine`、`runtimeConfig`、`modelConfig` 以及具体的 `toolConfig.tools`、`skillConfig.skills`、`connectorConfig.connectors`。Platform 应用 mode 创建默认值、校验并写入 `agent.yml`；提示词分别写入 `SOUL.md` 和 `AGENTS.md`。客户端不上传 YAML 文本，平台不维护或展开品牌分组。

`isProject` 是可选 boolean，省略或 false 沿用普通 Agent 创建规则。Desktop 和 WebClient 的项目创建入口传 `isProject:true`：此时 `definition.runtimeConfig.workspaceRoot` 必须是用户指定的具体、现存绝对目录，拒绝空值、`@root`、文件、不存在的目录和 canonical 文件系统/驱动器/共享根（包括指向根的 symlink）。允许空项目目录，不要求 Git 仓库；原有 Chat 与 KBASE 目录边界继续生效。失败在写入 Agent 目录前返回 `400 invalid_project_workspace`。该标志只表达本次请求意图，不写入 `agent.yml`，Projects 仍由公开 `workspaceDir` 判断。

模型通过 `catalog_query.validate` 与 `catalog_manage.apply` 创建或修改项目 Agent 时，在 args 中同样传 `isProject:true`，并把用户给定目录写入候选 YAML 的 `runtimeConfig.workspaceRoot`。校验复用 HTTP 创建规则，审批绑定该标志并在发布前重新检查；`@root` 表示没有具体项目工作目录的通用根目录智能体，不进入 Projects，不能用它替代用户给定的项目目录。

创建接口的类型基础工具是写入配置的推荐值，不是加载或执行时的隐式权限。客户端根据需要提交工具声明。全局预置能力仍由运行时提供，不要求客户端重复声明。ACP 客户端提交显式 `engine: acp` 与 bridge ID，不添加 Native 工具、技能或连接器。

### Agent ZIP 导入

管理接口 `POST /api/admin/agents/import` 接收 multipart `file` 与可选布尔 `overwrite`。Agent Key 只读取 ZIP 根目录或唯一一层包装目录内的 `agent.yml` / `agent.yaml`，不接受调用方另传 Key。导入按目录原样保留 prompt、专属 Skills、`.config`、知识文件和其他普通资源，不注入创建默认值，也不重写绝对 Workspace 路径。

同 Key 来源存在时，默认返回 409 并要求显式确认；`overwrite=true` 会完整替换旧来源而非合并。已有目录型 Agent 原位替换，平铺 YAML Agent 转换为 `<agentsDir>/<key>/agent.yml` 形式的目录来源。替换使用隐藏 staging/backup；catalog 硬重载失败会恢复旧来源。catalog 正常发布但单个 Agent 因当前机器缺少模型、工具、Workspace、KBASE 或 Skill 而无效时，导入内容会保留，响应 `status: invalid` 并携带 diagnostics，便于在管理台继续修复。

ZIP 仅接受普通文件，拒绝路径逃逸、反斜杠路径、symlink、大小写/重复路径及文件目录冲突；`__MACOSX` 和 `.DS_Store` 被忽略。上传和单文件上限均为 32 MiB，解压总量上限为 256 MiB，最多 4096 个条目，Agent YAML 必须是最大 1 MiB 的 UTF-8 文本。`.config` 可能含敏感内容，只应导入可信 ZIP，落盘时该目录及文件使用私有权限。

显式配置 `platform_control` 的治理 Agent，可以在不调用 HTTP 管理接口、不传递 JWT 的前提下读取同一组有效创建默认值。`catalog.defaults.get` 的 `params.path` 只接受 `agents.creation.general`、`agents.creation.coder` 与 `agents.creation.kbase` 三个精确路径，返回 `keyPrefix`（GENERAL 没有固定前缀，不返回）、小型 `definitionDefaults`、`ready` 与 `missingFields`；它不回显 ACP、provider、MCP 或 runtime env 中的凭据。`catalog.validate` 可只读校验完整的 agent、team、skill 或 MCP server 候选内容，校验本身不写文件、不触发 catalog 重载。实际创建和修改仍由现有文件工具完成，并由目录 watcher 在落盘后热重载。Skill 只提供调用知识，不会替 Agent 挂载 Tool。

## KBASE 公共能力与 Mode

所有 Native GENERAL/CODER/KBASE 和 PLAN-EXECUTE 通过一个 `kbaseConfig.libraryId` 绑定共享中心库。mode 只决定模板与模式行为，不改变知识库的所有权和授权。省略绑定即不启用知识库能力。绑定不隐式授予工具，按 preset 或 `toolConfig.tools` 声明 `kbase_search/kbase_files/kbase_read/kbase_status`。

```yaml
key: research-assistant
name: 研发知识助手
mode: KBASE
modelConfig:
  modelKey: deepseek-v4-pro
runtimeConfig:
  workspaceRoot: /absolute/documents/AI建设文档
kbaseConfig:
  libraryId: research
  retrieval:
    topK: 8
    candidateFloor: 30
    candidateMultiplier: 4
    candidateMax: 500
```

KBASE 仍需现存、非根目录的 Workspace，Projects 根据 workspaceDir 展示；Workspace 不要求属于 library 的 sourcePath。GENERAL 是否配置 Workspace 遵守原有规则，知识绑定本身不要求 Workspace。配置中的来源过滤与切块移到 `kbases/<id>/library.yml` 的 collections，embedding 由 library.models.embedding 覆盖 runtime.kbx 默认并引用共享模型 registry。旧 enabled、storage、include/exclude、chunk、tags 和 embedding 均硬失败，不能继续建立 Agent 独立索引。

检索逐字段按平台缺省 → library.retrieval → Agent 显式 retrieval → 单次调用合并；除上述预算外，还支持 minScore、recencyWeight、recencyHalfLifeDays、rerank 和 queryExpansion。省略字段继承，显式 0 / false 保留。重排和查询扩展模型由 library.models 引用共享 registry，不写入 Agent 模型配置；collection.defaultQuery 仅选择默认检索范围。详见 [知识库中心](知识库中心.md#检索默认值可选模型和默认集合)。

专用 Host KBASE 在 Run 启动时冻结 Workspace 与绑定库 editable collection 的 canonical 目录，开启 editingMode 后才可 mutation。修改来源会被库 watcher 异步维护并影响所有绑定 Agent；普通 Agent 不获得额外编辑权限，容器不自动挂载。main/editing 使用同一组声明工具，原有 AccessPolicy/HITL 规则保留。

创建接口 `/api/admin/agents/create` 可传 `createLibrary: {name, sourcePath}`，一次创建库并写入 Agent 的 libraryId；它与显式 kbaseConfig 互斥。创建失败回滚本次新库，Agent 已保存而后续 reload 失败时保留资料供管理端修复。`isProject:true` 继续要求具体 Workspace。WebClient 新建项目可选已有库，或从项目目录创建；已有库仅为 Workspace 提供默认目录，不建立包含约束。

catalog 只验证 ID 格式；Run 和工具检查存在性、就绪和来源指纹。失效绑定在管理端显示 warning，不拖垮平台健康检查。删除有 Agent 引用的库返回 409。路径统一为 `<collection>/<relativePath>`，引用回读按 Chat 已发布来源和库绑定授权。自动维护、故障语义和升级步骤见 [KBX 接入](KBX接入.md)，库配置见 [知识库中心](知识库中心.md)。

## Budget

运行步数统一配置在 `budget` 下。

推荐写法：

```yaml
budget:
  timeout: 3600
  maxSteps: 240
  hitl:
    timeout: 600
    question:
      timeout: 600
    approval:
      timeout: 600
    form:
      timeout: 600
  tool:
    maxCalls: 200

stageSettings:
  plan:
    budget:
      maxSteps: 20
      tool:
        maxCalls: 40
  execute:
    budget:
      maxSteps: 20
      tool:
        maxCalls: 40
  summary:
    budget:
      maxSteps: 1
```

- `budget.maxSteps` 是整次 run 的模型轮次总上限；resolved budget 中会同步到 `model.maxCalls`。
- `tool.maxCalls` 可显式配置；未配置时，如果同级配置了 `maxSteps`，默认按 `maxSteps * 2` 推导。
- PLAN-EXECUTE 阶段预算写在 `stageSettings.<stage>.budget`。
- `budget.timeout`、`budget.model.timeout`、`budget.tool.timeout`、`budget.hitl.timeout` 等预算超时字段单位都是秒。
- `budget.timeout` 是单次 run 的执行时长上限；一个 run 是一条用户消息触发的 agent 执行，从开始到最终回答结束。planning confirmation 的用户等待时间不计入该预算，其他等待或执行时间仍按既有规则计入。
- `budget.model.timeout` 是模型流式 idle 超时；首个响应 chunk 或任意两个 chunk 之间超过该秒数无响应则报错。chat model registry 顶层 `timeout` 配置后会覆盖该值，常用于 MiniMax / transit-hub 这类可能长时间不发 SSE 心跳的模型。
- `budget.tool.timeout` 是单次工具调用硬上限；bash/file/MCP 等工具不能超过该值。
- CODER 运行时预算优先级为 agent.yml 显式 `budget` > CODER profile fallback；fallback 的代码事实源是 `internal/agent/coder/profile.go`。`configs/agent-settings.yml -> coder.default-agent.budget` 只在创建 CODER agent 时写入默认 `budget`，不会作为运行时动态覆盖；已有显式 budget 不会自动迁移。
- `budget.hitl.timeout` 是当前智能体的 HITL/awaiting 默认，会覆盖 `configs/runtime.yml` 的全局 `budget.hitl`；`question`、`approval`、`form` 可用 mode 覆盖，`approval`、`form` 还会优先使用具体等待项自己的 `timeout` 秒值（如 bash-hook subcommand 或 form/tool 定义）。未配置时内置 fallback 为 `600` 秒。CODER `finalize_planning` 的 planning confirmation 是独立机制，永久等待、不读取 `budget.hitl.plan`，并且 `awaiting.ask(mode=planning)` 不下发 `timeout`；遗留 `budget.hitl.plan` 静默忽略。CODER 使用 `stageSettings.planning` 与 `budget.stages.planning`；旧的 CODER `stageSettings.plan` / `budget.stages.plan` 会在加载时失败。`plan_*` 与 plan-tasks 是执行任务跟踪，和 planning confirmation 无关。其他事件中的 `awaiting.ask.timeout` 单位为秒：配置值 `0` 表示未配置，事件值 `0` 表示无限等待、不自动超时，正值由后端按真实时间独立计时，不受 observer / attach / detach 状态影响。
- `GENERAL` 使用 `react` 单阶段；普通 `CODER` 使用 `execute` 阶段；任一原生 Agent 的规划 Run 使用 `planning` 预算阶段，由已确认计划启动的执行 Run 与该 Agent 的普通 Run 使用相同阶段；`PLAN-EXECUTE` 支持 `plan`、`execute`、`summary` 三个预算阶段。

`planningMode` 是原生 Agent 的通用能力，不属于某个 mode：请求顶层 `planningMode: true` 对原生 `GENERAL`、`CODER`、`KBASE` 生效，Team、`PLAN-EXECUTE` 等其他 mode 会被拒绝，ACP CODER 把该字段交给 bridge 处理。规划 Run 与执行 Run 是同一个 Agent 的两个独立 Run，不存在 Run 内的阶段切换；规划 Run 不会自己执行计划。KBASE 的规划 Run 即使带 `editingMode:true` 也不开启 Workspace 修改，该字段在执行 Run 生效。规划 Run 的工具是 Agent 有效工具去掉 `planning-mode.exclude-tools` 后再追加 `finalize_planning`，Agent 未挂载的工具（包括 `ask_user_question`）不会因规划而出现；`finalize_planning` 只接收完整 `markdown`，后端不补标题、不重排正文，并把该 Markdown 原样写入 `AP_RUNTIME_CHATS_DIR/<chatId>/.tools/planning/<runId>_planning_<revision>.md`。live 事件按 `planning.start`、多条 `planning.delta`、`planning.end`、`awaiting.ask(mode=planning)` 的顺序发送；后者是永久等待的 planning confirmation，不下发 `timeout`，并在 `planning` 对象中携带 `planningId` 与 `planningFile`。其 `awaitingId` 与原始 `finalize_planning` tool call id 相同，并随 `_type:"react"` step 的 `awaiting[]` 持久化，不把 Markdown 正文写入 JSONL。JSONL 会保留原始 assistant `tool_calls`，并在用户 approve/reject 后追加匹配同一 `tool_call_id` / `name:"finalize_planning"` 的 `_type:"react-tool"` / `role:"tool"` 结果。`GET /api/chat` 回放时读取该文件并恢复顶层最新 `planning`，同时在对应 `awaiting.ask` 前合成 replay-only 的 `planning.snapshot` 事件供时间线使用。后端不持久化 `planning.start` / `planning.delta` / `planning.end`。

原生 Agent 中，用户以 `mode=planning` approve 后会结束当前 planning run：旧 live stream 先出现 `awaiting.answer`，再出现旧 run 的 `run.complete`，随后以 stream terminal `reason:"done"` 结束；旧 live stream 不追加新 run 的 `run.start`，也不继续桥接 execution 的 content/tool 事件。服务端在旧 stream done、旧 run finished 后启动新的 execution run，并通过 WebSocket push `run.started { runId, chatId, agentKey }` 让客户端发现新 `runId`；客户端应 attach 新 `runId` 读取新 run 自己的执行流。新的 execution run 首部为 execution run bootstrap `request.query(message:"Execute planning", requestId:<execution request id>)`，随后是新 run 的 `run.start`，完整执行 prompt 只写入 JSONL/model messages；execution run 是该 Agent 的一次普通 Run：关闭 `planningMode`，使用与普通 Run 相同的系统提示词，已确认计划作为它的输入消息；工具为 Agent 有效工具去掉 `planning-mode.execute-exclude-tools`（缺省 `ask_user_question`、`ask_user_form`），CODER 仍保留 `plan_add_tasks`、`plan_get_tasks`、`plan_update_task` 作为可选轻量任务追踪工具。规划 Run 自身不执行计划：批准时若没有可交接的新 Run，会以 `planning_continuation_unavailable` 结束。这些工具不接管执行，但任务状态仍遵守有序、单活动和终态不可复活规则。`plan_add_tasks` / `plan_update_task` 会把当前任务快照按 execution run 写入 `AP_RUNTIME_CHATS_DIR/<chatId>/.tools/plan-tasks/<runId>_plan.json`，`/api/chat` 读取该目录的最新快照作为顶层 `plan`；重启后同一 `chatId` 的新 query 不复活旧 run / SSE，但在 CODER 执行类阶段会从最新快照恢复 plan task 内存状态，`plan_get_tasks` 可直接读到恢复结果，后续 `plan_update_task` 会写入新 run 的快照。`plan_add_tasks` 默认追加到当前 plan；当用户开启新的目标/计划时，调用方可传 `mode:"new"` 创建新的 `planId`，并让本次 tasks 成为新 plan 的完整初始任务列表。execution 阶段的最终回复就是用户可见收尾，不再额外启动 `coder-summary` 模型调用。reject 后当前 planning 不会执行，也不会启动新 run，模型可在原 planning run 中生成下一版 planning revision 或直接结束本轮。

规划提示词按 mode 解析：CODER 使用 `configs/agent-prompt.yml → coder.planning-prompt`，其余原生 mode 使用 `shared.planning-mode.planning-prompt`，都未配置时不追加规划指令，源码不再内置规划提示词。CODER 专属系统提示词从 `configs/agent-prompt.yml → coder` 读取；普通 Run 与执行 Run 都使用 `system-prompt`，不再有单独的 execute stage prompt。随包 `agent-prompt.example.yml` 的 coder 节 的 `system-prompt` 还为 native CODER 约定：仅在量化对比、趋势、分布或占比明显受益时输出独立的 `echarts` 代码块，块内必须是无注释、无尾逗号和无 JavaScript 表达式的合法 JSON；内联图表不是文件产物，不调用 `artifact_publish`。`summary-system-prompt` / `summary-user-prompt-template` 已从 CODER 专属 prompt 配置中删除；`PLAN-EXECUTE` 的 summary prompt 配置不受影响。

### ACP CODER Backend

Desktop 插件通过 Platform 的 `PUT /api/desktop/acp-bridges` 注册、`DELETE /api/desktop/acp-bridges` 注销。Desktop 只转发经过本机插件身份校验的请求，不直接读取或改写 `coder-settings.yml`；Platform 在该文件中同时保存连接配置和插件归属。接口字段见 `internal/config/acp_registration.go` 和 `internal/server/handler_acp_registration.go`。

注册写入按进程内互斥串行，配置与归属使用同一次文件替换。macOS 使用 rename，Windows 使用支持替换的 MoveFileEx；替换失败保留原配置，调用方可重试。不会获取连接器装配或 Agent 租约锁。进程内互斥不协调外部编辑器或多个 Platform 进程；同一配置目录由单个 Platform 管理，人工编辑须在停机时进行。

旧无归属条目只能在连接参数完全一致时被注册插件认领；参数冲突或其他插件已拥有该条目时拒绝写入，无归属条目不能直接注销。不迁移旧 `acp-proxies`，也不修改其他配置段。当前运行路由保持启动快照，响应的 `changed` 表示落盘变化，`restartRequired` 表示持久注册表与启动快照不同；重复请求可以返回 `changed: false`、`restartRequired: true`，重启加载后才变为无需重启。

顶层 `engine: acp` 配合 `runtimeConfig.acpBridgeId`，改由 `configs/agent-settings.yml` 中的 ACP bridge 执行。此时 `mode` 可以省略（写了只能是 `CODER`），接口仍按 `mode: CODER` 返回，执行链路会转发到本机 `codex-acp-bridge` 或 `claude-acp-bridge`。除 PROXY 外，ACP CODER 也允许缺省 `modelConfig.modelKey`；如果配置了 `modelConfig.modelKey`，该值会作为上游 bridge 的模型参数使用。未声明 `engine` 时默认使用 native 引擎，必须显式配置 `modelConfig.modelKey`：

```yaml
# configs/agent-settings.yml
acp-bridges:
  codex:
    base-url: http://127.0.0.1:17071
    timeout-ms: 300000
    auth-token: ${CODEX_ACP_BRIDGE_AUTH_TOKEN:}
```

```yaml
engine: acp
modelConfig:
  modelKey: gpt-5-codex
runtimeConfig:
  acpBridgeId: codex
  workspaceRoot: /absolute/project/path
projectConfig:
  git:
    expectedBranch: main
```

ACP CODER 的模型可以只作为转发给 bridge 的外部模型参数注册，不需要配置平台原生 provider：

```yaml
# registries/models/gpt-5-codex.yml
key: gpt-5-codex
name: GPT-5 Codex
protocol: ACP_PASSTHROUGH
modelId: gpt-5-codex
```

ACP CODER 中，编程项目配置仍由 platform 的 `agent.yml` 管理，包括可选的 `modelConfig.modelKey`、`runtimeConfig.workspaceRoot` 和 `projectConfig.git.expectedBranch`。Codex CLI、网络代理、Codex app-server/exec 参数由 `codex-acp-bridge` 自身配置管理；平台 `toolConfig.tools` 不受支持，bridge 工具必须由 bridge 自行配置。ACP CODER 支持把平台 `planningMode` 透传给上游 ACP bridge；具体 planning mode 语义由 `codex-acp-bridge` 与 Codex app-server 实现。ACP CODER v1 不支持 `projectConfig.promptFiles`；工作区规则由 Codex 在目标工作目录中自行读取。

#### 本机 ACP 工作目录契约

ACP bridge 是受信任的执行器，部署时必须能访问与 Platform 相同的 Workspace 绝对路径及文件。顶层 `engine: acp` 与 `runtimeConfig.acpBridgeId` 显式选择这一共享文件系统契约，`acp-bridges` 是部署配置授权边界。地址配置保持原有兼容性，不新增 loopback IP、DNS 名称或远端地址限制，也不根据 URL 主机名推断是否可以传递工作目录。部署方负责保证 bridge 可访问同一 Workspace，并按需配置 `auth-token`。此契约保持端口通信，上游执行仍走 WebSocket `/ws`，模型发现沿用 HTTP `/api/models`；未增加 stdio 传输或 bridge 启动管理。

执行链路为 `runtimeConfig.workspaceRoot → Session.WorkspaceRoot → bridge query params.cwd`：

1. Catalog 要求所有 CODER 声明真实 Workspace；Session 构建复用通用路径解析，展开受支持的路径配置、解析符号链接，校验现存目录与既有 Workspace/Chat、Git 分支约束，冻结 canonical Host 绝对路径。目录不可用时 query 失败，不回退 Chat、进程 cwd 或 Agent 运行目录。
2. 只有由 ACP 路由解析成功后生成的私有 `ProxyConfig.LocalACP` 标记，才允许共用转发器向 bridge 的 query 参数副本写入 `cwd`。该标记不从 Agent YAML 或用户 params 读取，不序列化为公开配置；普通 loopback PROXY 也不获得此能力。
3. HTTP 与 WebSocket 客户端入口共享此规则。用户显式传 `params.cwd`（包括空字符串和 null）仍返回 400；转发器额外移除传入副本里的 `cwd`，再用冻结的 Workspace 写入。原始 query 不增加 `cwd`，bridge 回传 `request.query` 时也会剥离其中的 `params.cwd`，本地请求事件与持久化不保存该注入字段。
4. 普通 PROXY、CHANNEL 和 Proxy child 不注入宿主 Workspace，继续使用既有远端引用物化契约。ACP 仍禁止作为 child；附件通过资源 URL 传递，与执行工作目录独立。

两个 bridge 继续将 `params.cwd` 作为必填值，用于 backend 进程目录及 ACP session `cwd`；Platform 不要求 bridge 猜测项目路径。需要远端执行的部署应使用 PROXY/CHANNEL，由远端管理自己的目录；ACP 注册地址必须满足共享 Workspace 的部署前提。

## CHANNEL Mode

`mode: CHANNEL` 表示“把外部 platform/adaptor 上的 agent 导入为本地 agent”。该模式不进入本地 LLM engine，也不要求 `modelConfig.modelKey`；运行时会根据 `channelConfig.channelId` 找到对应 channel，再用 `remoteAgentKey` 作为上游 agent key 发起 `platform-ws` 请求。`channel.mode` 只表示连接建立方向：`client` 由本端主动连出到 `endpoint.url`，`server` 由本端开放 `/ws/channel` 等待对端连入；两者都可以承载 CHANNEL agent 调用。

```yaml
key: remote-coder
name: Remote Coder
mode: CHANNEL
channelConfig:
  channelId: peer-a
  remoteAgentKey: coder
```

`mode: CHANNEL` 的校验规则：

- 必须配置 `channelConfig.channelId` 与 `channelConfig.remoteAgentKey`
- 禁止配置 `channelConfig.exports`
- 对应 channel 必须存在于 `configs/channels.yml`
- `mode: client` channel 必须配置可连接的 `endpoint.url`
- `mode: server` channel 必须已有活跃对端连接；未连接时 `/api/query` 返回 `503 channel <channelId> is not connected`

本地 agent 导出给外部 channel 时，不使用 `mode: CHANNEL`。本地 `GENERAL / CODER / PLAN-EXECUTE / PROXY` 等 agent 可以声明 `channelConfig.exports`：

```yaml
key: assistant
name: Assistant
mode: GENERAL
modelConfig:
  modelKey: deepseek-v4-pro
channelConfig:
  exports:
    - channelId: public-entry
      externalAgentKey: assistant
      allow:
        query: true
        submit: true
        fileTransfer: true
```

`exports[].channelId` 必填。`exports[].externalAgentKey` 可选；省略或为空时，默认使用本地 agent 的 `key` 作为外部调用名。例如 `key: kbaseOrchestrator` 的 agent 可以只写：

```yaml
channelConfig:
  exports:
    - channelId: singapore-webclient
      allow:
        query: true
```

外部调用时使用 `{"externalAgentKey": "kbaseOrchestrator"}` 即可匹配。

`exports[].allow.query` 默认 `true`；`submit`、`steer`、`interrupt`、`fileTransfer` 默认 `false`，需要显式开启。导出请求只能从匹配的 channel 进入，并按 `externalAgentKey`（或其默认值）映射到本地 agent key，再检查 allow 权限。

接出注册与 channel 的建连方向无关。`mode: client` 由本 Platform 主动连出，`mode: server` 由对端连接 `/ws/channel`；两种连接都必须先收到对端的 v1 `push connected`，随后由本 Platform 发送 `agent.list / agent.register / agent.unregister`。同一 server channel 的多条连接按独立 Session 分别对账，不共享注册所有权。

注册范围只认普通 Agent 上显式声明、且 `allow.query: true` 的匹配 export；`mode: CHANNEL` Agent 永远不会作为本地接出项注册。旧 `agents: "*"` 配置已移除并会导致加载失败。注册 payload 只包含：

- `agentKey`：优先使用 `externalAgentKey`，缺省回退本地 Agent key。
- `name`：Agent name，空值回退本地 key。
- `role`、`description`：来自 Agent 定义，空值省略。
- `capabilities`：`query / steer / interrupt / hitl` 分别映射 `allow.query / steer / interrupt / submit`。

`fileTransfer`、Skill、Tool、Tag、Prompt、Workspace、KBASE 隐式能力和模型配置均不进入 v1 注册。四项稳定能力全部开启且对端正好支持这四项时发送 `["all"]`，否则按固定顺序发送显式能力列表。字段按 Gateway v1 的长度与非法控制字符规则校验；公开元数据仍需由维护者预先完成隐私脱敏。

每轮先通过 `agent.list` 查询当前 `platformKey` 下所有 Session 注册的 Agent，但只操作 `ownedByCurrentSession:true` 的项目。删除 export 或关闭 query 会触发 `agent.unregister`；展示字段或展开后能力变化会再次 `agent.register` 做完整替换。`SINGLE_EMPLOYEE` 连接若匹配多个有效 export 会整体报配置错误。详细帧格式、Session 生命周期和重试语义见 [API与协议](API与协议.md#channel-agent-接出注册-v1)。

## PROXY Mode

PROXY agent 用于把平台请求转发给兼容的上游服务。新 platform-to-platform / adaptor 接入优先使用 `mode: CHANNEL` 与 `channelConfig`。PROXY 仍可用，只要求 `proxyConfig.baseUrl`，不要求本地 `modelConfig.modelKey`；旧配置中保留的 `modelConfig.modelKey` 仍可被加载并回显，但运行链路不会依赖它：

```yaml
key: codeAssistant.demo
name: 星码
role: CLI 代码助手
description: 透传到 CLI 模式代码助手服务
mode: PROXY
runtimeConfig:
  workspaceRoot: /absolute/project/path
proxyConfig:
  baseUrl: http://127.0.0.1:3210
```

`proxyConfig` 字段语义：

- `baseUrl` 必填，指向上游代理服务根地址
- `transport` 可选，默认 `ws`；显式设为 `sse` 时使用上游 `/api/query` SSE 链路
- `agentKey` 可选，用于覆盖转发给上游的 agent key
- `token` / `tokenEnv` 可选，仅当上游服务启用 Bearer 鉴权时配置；默认不需要 token
- `timeout` 可选，默认 `300`（秒）；通常不需要显式配置

`POST /api/query` 中的 `model` 字段在 PROXY 模式下原样透传给上游，由上游服务解释；platform 不要求该模型存在于本地 model registry，也不会把它写入本地 session/stage settings。

## Markdown Memory

个人记忆统一保存于 Platform 的 `owner/OWNER.md`、`memory/summary.md` 和 `memory/daily/YYYY-MM-DD.md`；Agent 私有静态 memory 文件及 SQLite Memory 已退役。

Agent 通过 `memoryConfig.enabled: true` 显式启用共享个人记忆；全局 `memory.enabled` 默认 true。新 Run 注入有界长期记忆与记录原则；不挂载专用记忆工具。memory_read、memory_search、memory_write、memory_update 已下线，显式声明会报错。Agent 按需声明 bash 以调用 memx 获取记忆，以及 file_write/file_edit 修改 Markdown，仍受目录权限和审批约束。managementTools、embedding、autoRemember 配置不再接受。Owner 仍由 owner context tag 控制，只读取 OWNER.md，活动 Native Run 冻结其内容。文件管理独立于当前 Agent。

协议、写入边界与记录原则见 [记忆系统](记忆系统.md)。

## Runtime Config

Go runtime 当前支持在 `agent.yml -> runtimeConfig` 下声明：

```yaml
runtimeConfig:
  environmentId: shell
  level: RUN
  workspaceRoot: /absolute/project/path
  hostAccess:
    readRoots:
      - "@owner"
      - "@temp"
    writeRoots:
      - "@temp"
  sandboxMounts:
    - platform: owner
      destination: /owner
      mode: rw
  env:
    HTTP_PROXY: "http://127.0.0.1:7890"
    HTTPS_PROXY: "http://127.0.0.1:7890"
    TZ: "Asia/Shanghai"
```

约束与语义：

- `env` 只接受 `map[string]string`
- `runtimeConfig.runEnv` 已移除；遗留字段静默忽略，不产生动态环境策略、校验或权限
- key 必须非空，且不能包含空白字符或 `=`
- `AP_AGENT_CONFIG_HOME`、`AP_WORKSPACE_DIR`、`AP_CHAT_DIR` 与 `AP_ACCESS_TOKEN` 是平台保留变量，agent `runtimeConfig.env`、skill `.runtime-env.json` 或调用级 env 声明任一变量都会使校验失败；普通 Host Shell 不自动获得 `AP_ACCESS_TOKEN`；经验证的单条直接 oneid-token CLI 调用在独立子进程中使用该变量，已挂载 oneid-token stdio MCP 也按有效 identity 文件当前内容注入，默认文件为 `<有效 StateDir>/identity/access-token`，显式 `--identity-file <absolute-path>` 优先
- value 必须是字面量字符串；空字符串允许并原样注入 host bash 或下发到 Container Hub
- 不支持 `${VAR}` 或其他宿主环境变量展开
- `runtimeConfig.workspaceRoot` 定义 Agent 的宿主 Workspace；必须可展开为现存绝对目录，不能为 `@chat`。普通 Workspace 不能等于 ChatsRoot 或位于 ChatsRoot 内，但可以包含 ChatsRoot，`/` 合法；KBASE Workspace 额外禁止文件系统根和任意方向的 ChatsRoot 重叠
- `runtimeConfig.hostAccess.readRoots/writeRoots` 追加单个 agent 的 host-side 可操作目录，只影响 host `bash` 与 `file_*` 工具；root 支持绝对路径、`~/...`、`@workspace`、`@chat`、`@agent`、`@skills`、`@skills-center`、`@owner`、`@temp`。`@temp` 已无条件进入 effective default roots，显式写入 hostAccess 主要用于自说明
- 当前 access level 的 `readonly-roots` 在 writeRoots、hostAccess 与 HITL 之前硬阻断；`mustUseSkills` 还会为本次选中的 canonical Skill 目录建立 trusted read + readonly roots，未选中技能中心目录不继承，`full_access` 和 approval 也不能写入选中目录
- `runtimeConfig.sandboxMounts` 配置额外挂载；`/workspace`、`/chat` 及其子路径为保留目标，不能覆盖
- `runtimeConfig.acpBridgeId` 必须与顶层 `engine: acp` 同时出现，并引用 `configs/agent-settings.yml` 中的 `acp-bridges` 条目；`engine` 缺省为 `native`，此时出现 `acpBridgeId` 会校验失败。`timeout-ms` 的默认值为 `300000`；修改 `coder-settings.yml` 后必须重启 runtime 才会生效
- 工具路径中的 `@chat` 会解析为当前 `AP_RUNTIME_CHATS_DIR/<chatId>`；这不意味着它可以写入 `workspaceRoot`
- `runtimeConfig.environmentId` 是 sandbox context 的唯一入口；不需要也不支持再在 `contextConfig.tags` 中声明 `sandbox`
- agent `runtimeConfig.env` 作为基础值，组装后 Skill 目录下的 `.runtime-env.json` 会按 agent 声明顺序叠加并覆盖同名键；运行时不回退原始 Agent 或 skills-center
- 当前普通 native root run 可通过 preset 或自身声明的 `run_env` 调用 `set/unset/update`；动态 env 位于静态 Agent/Skill env 之上，调用级 env 与 Platform reserved context 位于它之上。只有当前 run 成功 set 的 key 才能 unset，删除动态层后回退同名静态/Host 值。Skill 和 `mustUseSkills` 都不会替 Agent 挂载 Tool
- `/api/agent` 与 `/api/admin/agents` 的 `sandbox` meta 不会回显 `env`，避免暴露代理地址、凭据或私有 endpoint；sandbox mounts 仍可对外暴露，因为它描述的是白名单路径而非敏感值。`/api/agents` 仅返回列表摘要，不包含 `meta`。
- `/api/agent`、Catalog 与 tool result 都不会回显动态 value；set/unset 成功只返回 key、changed、idempotent、revision。完整限制见 [Platform 控制工具设计与实现](./Platform控制工具设计.md)

所有 CODER、所有配置 Container Hub sandbox 的 Agent 与所有 enabled KBASE 都必须解析出 Workspace。无 sandbox 的 GENERAL、PLAN-EXECUTE、PROXY、CHANNEL 可以没有 Workspace，但相对路径、`@workspace`、省略 `cwd` 的 Bash、省略 `path` 的 glob/grep 和 Workspace Terminal 会返回 `workspace_unavailable`，不会回退 Chat 或进程 cwd。无 Workspace session 的模型工具 schema 会把这些参数动态标为必填；普通 Chat 文件操作应显式使用 `cwd: "@chat"`、`path: "@chat"` 或 `@chat/...`。

### Agent 与 Chat 执行环境

目录型 agent 可在 `runtime/agents/<agentKey>/.config/` 放置 Agent 专属覆盖，Agent 自有或技能中心 Skill 可在自身 `.config/` 提供可分发默认值。Platform 在 Catalog 发布前将它们合入 `ru-agents/<agentKey>/<revision>/.config/`；Skill–Skill 不同内容或结构冲突会隔离该 Agent，Agent `.config` 最后覆盖。完整规则见 [Agent 运行时组装](./Agent运行时组装.md)。

执行 host bash/tool 与 Container Hub session/command 时，平台会计算并冻结：

- `AP_AGENT_CONFIG_HOME`：agent scope 的私有静态配置根；host/terminal 使用实际 `<ru-agents>/<agentKey>/.config`，Container Hub 使用只读挂载后的 `/agent/.config`
- `AP_WORKSPACE_DIR`：Host 使用真实 Workspace（没有 Workspace 时省略），Container Hub 固定为 `/workspace`
- `AP_CHAT_DIR`：Host 使用实际 `AP_RUNTIME_CHATS_DIR/<chatId>`，Container Hub 固定为 `/chat`

Workspace Terminal 只冻结实际 `AP_AGENT_CONFIG_HOME` 与 canonical `AP_WORKSPACE_DIR`，不注入 `AP_CHAT_DIR`。三个变量都由 Platform 保留。长生命周期 Container Hub session 的复用身份包含 environment、canonical Workspace、canonical Chat 和完整 mount fingerprint；Workspace Terminal 的复用身份是 owner boundary、`agentKey` 与 `terminalKey`。

平台不会为 agent 静态配置改写 `XDG_CONFIG_HOME`，也不注入系统配置根。当前 dbx/httpx 会在 agent 中没有同名连接/site 时自行回退 `~/.config/<tool>/`；显式 `--config` 不回退。HTTPX 的 chat secret/state 固定使用 `$AP_CHAT_DIR/.secret/httpx` 与 `$AP_CHAT_DIR/.state/httpx`，HTTPX 不接收 Chat ID，也不会在缺失合法目录时回退 global；敏感内容不得提交。

PROXY/CHANNEL 不再伪造宿主 cwd 或把 Chat 当 Workspace；远程文件引用以带 ticket 的 resource URL 为传输事实源，由接收端物化到自己的 Chat。

CODER 可额外声明顶层 `projectConfig`：

```yaml
projectConfig:
  promptFiles:
    - source: workspace
      path: AGENTS.md
    - source: agent
      path: AGENTS.md
  git:
    expectedBranch: main
```

- `source: workspace` 从 `runtimeConfig.workspaceRoot` 解析后的目录读取
- `source: agent` 从当前 Agent 的 `ru-agents/<agentKey>/<revision>` 运行目录读取
- `promptFiles` 使用 `source/path` 结构声明

## 通用智能体根目录与项目目录

`runtimeConfig.workspaceRoot: "@root"` 显式表示通用根目录智能体。Catalog 保留该意图，同时把运行时 Workspace 解析为本机绝对根目录：macOS/Linux 为 `/`，Windows 为 Platform 当前驱动器根目录。工具相对路径、`@workspace`、运行上下文和目录权限使用解析后的真实路径；该值不增加跨盘权限，不绕过 readonly、审批、KBASE 根目录限制或根目录扫描禁令。

公共 HTTP/WebSocket `/api/agents`（包括 includeTeam）与 Admin 摘要的 `workspaceDir` 只表达项目目录：`@root` 省略该字段，普通绝对目录（包括显式 `/`）继续返回解析后的目录，未配置时也省略。Admin 原始 definition 保存 `"@root"`，编辑、导入、重载不得把它改写为实际根路径。Desktop 据 `workspaceDir` 是否非空区分 Projects，不按 mode 或路径形状猜测通用身份。现有通用智能体的 `/` 配置需显式改为 `"@root"`；不自动迁移所有根路径，以免改变显式项目配置的语义。


## 对话输入能力 interactionConfig

`interactionConfig` 按 Agent 配置用户可选择的对话输入能力，叶子字段只接受布尔值。省略字段按 mode 使用默认值；显式 `false` 保留，未知字段和非布尔值拒绝。`/api/agent` 返回解析后的完整配置，`/api/agents` 不增加该字段。

| 字段 | GENERAL | CODER（含 ACP） | KBASE |
| --- | --- | --- | --- |
| model | true | true | false |
| accessLevel | true | true | false |
| mustUseSkills | true | true | true |
| connectors | true | true | false |
| attachment.localFiles | true | true | true |
| attachment.chatRecords | true | false | false |

```yaml
interactionConfig:
  model: true
  accessLevel: true
  mustUseSkills: true
  connectors: true
  attachment:
    localFiles: true
    chatRecords: true
```

不提供 `attachment.driveFiles`。关闭 `model` 后使用 Agent 已配置模型，拒绝 query 模型覆盖和输入框模型保存；完整管理端定义编辑仍可设置模型。关闭 `accessLevel` 后新请求使用 default，禁止运行中调整，AccessPolicy/HITL 审批保持生效。关闭 `mustUseSkills` 不影响 Agent 已配置技能；关闭 `connectors` 不影响已挂载连接器，但禁止连接器选择接口修改挂载，管理员仍可编辑完整定义。

`attachment.localFiles` 控制通过文件选择、拖放、粘贴及截图添加的文件/图片引用，query 和 steer 均校验；`attachment.chatRecords` 控制 type=chat 引用。网站和纯文本 selection 引用保持原协议。通用上传接口不按 Agent 全局关闭。

ACP CODER 使用同一套默认值和准入开关，模型/推理参数/服务等级仍由对应 bridge 提供，开启开关不扩展 ACP 的实际能力。运行中权限调整在转发前校验。普通 PROXY/CHANNEL 与 Team 不新增普通 Agent query 准入约束。

交互配置在 Run 准入时冻结，快照保存在服务端私有 `.state/run-interactions` 目录供恢复使用，不进入 `/api/query` 请求、`request.query` 事件或 Chat JSONL 的 `query`；目录重载只影响后续新 Run。恢复时兼容读取旧 `query.interactionConfig`；历史 Run 无快照时沿用当前定义的解析值。

## Platform 预置工具

`configs/agent-settings.yml` 的全局和 mode `preset-tools` 自动挂载到 GENERAL、native CODER、KBASE，包括子智能体和 Team 成员；ACP、Team 隐藏协调器不挂载。缺省或 `[]` 表示不预置，配置仅启动时读取，修改后需要重启。未注册的工具名会阻止启动；连接器专属工具和内部会话工具不能作为预置项。

```yaml
toolConfig:
  tools:
    - bash
  excludeTools:
    - wait
```

先合并预置工具与自身工具，去重后排除 `excludeTools`。普通工具不会因为技能、运行环境、Memory、KBASE capability 或 CODER 阶段被补回；连接器自身工具按完整包挂载，不受单项工具排除控制，需调整连接器挂载。预置只决定挂载；Workspace、KBASE editing、AccessPolicy、HITL、模型配置、planning 和 BTW 等调用限制仍生效。

详情接口保留有效 `tools` 列表，另返回 `toolBindings`：`name`、`source`（preset/agent/connector）、`removable`、`excluded`、`active`。被排除项仍展示；连接器自身工具覆盖同名声明的排除时可同时为 excluded 和 active。预置项锁定，提示“由 Platform 配置统一管理”。排除通过 agent.yml 源码修改；结构化编辑保留已有排除设置，不把预置清单写回。已有显式声明的预置项保留，避免以后取消全局预置时丢失原配置。

普通工具的配置来源与 Run 工具列表边界：

- 全局 preset 示例包含 `run_env`；Memory 工具由 Agent 在 `toolConfig.tools` 按需声明，启用 Memory 不自动挂载。
- `kbase.preset-tools` 示例声明 `kbase_search/kbase_files/kbase_read/kbase_status`，GENERAL/CODER 不继承该 mode preset。
- 连接器仅导入自身 Native/MCP 工具；`file_read`、`bash` 需由 preset 或 Agent 声明。CLI 入口授权、环境组装和技能资源挂载不因此改变。
- Native GENERAL/CODER/KBASE 的 `planningMode` Run 均追加 `finalize_planning`；确认后的执行 Run 移除它。TEAM 隐藏协调器保留 `agent_delegate` 和三个 plan 工具；PLAN-EXECUTE 的 plan/execute 协议分别保留 `plan_add_tasks`/`plan_update_task`。
- Agent 详情 `tools/toolBindings` 表示配置期集合，不是某次模型请求快照。挂载 MCP 在 Run 开始时合并当前发现结果；子任务/Team、runtime mode、阶段与连接器准入会进一步过滤，规划协议会追加工具。`/api/tools` 是可注册工具目录，不代表任何 Agent 已获授权。
- 修改示例不会改写既有部署：需要将所需 `run_env` 和 KBASE preset 同步到真实 `agent-settings.yml` 并重启；既有依赖隐式 Memory、Bash 或 GENERAL/CODER KBASE 工具的 Agent 需补显式声明。创建模板的推荐项继续写入新 Agent 配置，不用于既有 Agent 的加载回退。

客户端提交的工具清单和 KBASE 默认清单在保存时动态扣除当前预置项；预置为空时保留提交的具体能力。


## Platform 预置连接器

`configs/agent-settings.yml` 在全局和 mode 节的 `preset-tools` 旁配置 `preset-connectors`：

```yaml
preset-connectors:
  - builtin.web-control
```

配置只在启动时读取，修改后重启；缺省或 `[]` 不预置。适用于 GENERAL、native CODER、KBASE，包括使用这些 Agent 的子任务和 Team 成员；ACP、隐藏 Team 协调器不注入。仍执行阶段、调用方、认证和能力限制。合并预置与 Agent 自身声明后按 ID 去重，再装配完整连接器（工具、技能、运行依赖）；包缺失或冲突走原目录诊断，不能只声明连接器工具名代替挂载。示例只预置网页连接器；平台管理连接器由部署者显式配置到所需 Agent，没有源码内置名单。

预置不写回 `agent.yml`；结构化保存不会把有效挂载列表全部变成源码声明，已有显式声明保留。`GET/PUT /api/admin/agents/connectors` 的 `connectorIds` 表示配置期合并结果，`declaredConnectorIds` 为自身声明，`presetConnectorIds` 为平台预置，`activeConnectorIds` 为当前有效挂载。`reloadPending` 比较合并结果与当前挂载。WebClient 将预置项标为“平台预置”并锁定开关；单 Agent 取消预置项会报错，应修改平台配置后重启。连接器删除也检查预置引用。


### 按需启用 HTML 输入表单

在现有 Agent 的 `toolConfig.tools` 中追加 `ask_user_form` 即可；它默认不在全局 preset-tools。模型调用 `{title,html,values?}`，HTML 只允许声明式控件，表单结果只作为输入返回模型。规划与已确认计划的执行 Run 默认都排除此工具，实际覆盖规则见 [Agent 配置合并](Agent配置合并.md)，HTML 和取值规则见 [独立输入表单](MCP与工具交互.md#独立输入表单-ask_user_form)。
