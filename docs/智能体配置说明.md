# 智能体配置说明

本文件说明 agent / team / skill 的目录化配置、prompt 文件、CODER、KBASE、memoryConfig 与 runtimeConfig。当前 Go runtime 已支持从 `configs/runtime.yml -> paths.agents-dir` 读取 `runtime/agents/*.yml` 与 `runtime/agents/<key>/agent.yml`，并将结果直接暴露给 `/api/agents` 与 query agent 选择逻辑。

## 当前状态

当前 Go 版运行时：

- `models` 会从 `AP_RUNTIME_REGISTRIES_DIR/models` 读取
- provider 连接配置会从 `AP_RUNTIME_REGISTRIES_DIR/providers` 读取
- catalog 中的 agent/team/skill/tool 已改为目录驱动
- `runtime/agents/*.yml` 与 `runtime/agents/<key>/agent.yml` 都会参与装载
- Team 只接受 `runtime/teams/<teamId>/team.yml`；平铺 `runtime/teams/*.yml|yaml` 会使启动失败

因此，这份文档当前主要承担两件事：

1. 说明与 Java 对齐后的 Agent Definition 形态
2. 标注当前 Go 版已接入与仍待补齐的细节

## 目标形态

参考仓库中的完整 Agent Definition 目标形态如下：

```yaml
key: agent_key
name: agent_name
role: 角色标签
description: 描述
icon: "emoji:🤖"
greetings:
  - 我可以帮你总结材料、拆解问题，并给出下一步行动建议。
  - 需要快速进入状态时，我会先帮你找最值得处理的切入点。
wonders:
  - 帮我总结这段材料
  - 给我 5 个可以马上执行的下一步
modelConfig:
  modelKey: qwen3-max
toolConfig:
  tools: ["bash", "datetime"]
mode: REACT
plain:
  systemPrompt: |
    系统提示词
```

长期看，Go 版也会沿用这一思路：

- 前 4 行固定 `key`、`name`、`role`、`description`
- `modelConfig.modelKey` 引用 `registries/models/*.yml`；除 PROXY 与 ACP CODER 外，所有 agent 都必须显式声明
- `toolConfig` 只声明 `tools` 工具名列表；不支持旧式 `toolConfig.overrides/backends/frontends/actions`
- `mode` 决定 agent 执行模式

### 工具白名单与 Mode 默认值

`toolConfig.tools` 是 Agent 的工具 allowlist，不是对全局工具 catalog 的补充或排除列表。普通工具、运行时内置工具和 MCP 同步工具都只有进入 Agent 最终 allowlist 后才会提供给模型；Platform 新增工具或 MCP 热同步不会自动扩大既有 Agent 的权限。

- `REACT` 未声明 `toolConfig.tools` 或声明 `tools: []` 时均为无工具；使用 `web_fetch`、MCP 或其他工具必须显式列出。
- native `CODER` 未声明或声明空列表时使用 CODER mode profile 默认工具；非空列表用于收窄授权，main/execute 仍补全三个计划任务工具。
- ACP `CODER` 不使用 Platform 工具；非空 `toolConfig.tools` 会使配置校验失败。
- 专用 `KBASE` 始终使用 KBASE mode 的固定工具集合，用户列表不能扩大或收窄该边界。

Skill、Sandbox、runtime env、`memoryConfig` 和普通 Agent 的 `kbaseConfig.enabled: true` 仍按各自显式配置追加所需工具。最终工具集合会冻结到 run session；后续 catalog 变化只影响新 run。

## Model Sampling

agent 可在 `modelConfig.sampling` 声明默认采样参数；`PLAN-EXECUTE` 可用 `stageSettings.plan/execute/summary.modelConfig.sampling`，CODER planning 可用 `stageSettings.planning/execute.modelConfig.sampling` 按字段覆盖：

```yaml
modelConfig:
  modelKey: qwen3-max
  sampling:
    temperature: 0.7
    topP: 0.9
    presencePenalty: 0
    frequencyPenalty: 0
    seed: 42

stageSettings:
  execute:
    modelConfig:
      sampling:
        temperature: 0.4
```

继承优先级为 `stageSettings.<stage>.modelConfig.sampling` > `modelConfig.sampling` > 运行时默认。未配置时，OpenAI-compatible 主链路仍发送 `temperature: 0`，保持确定性默认行为。

字段使用 camelCase：`temperature`、`topP`、`presencePenalty`、`frequencyPenalty`、`seed`。OpenAI-compatible 协议会映射为 `temperature`、`top_p`、`presence_penalty`、`frequency_penalty`、`seed`；Anthropic 协议只发送 `temperature` 和 `top_p`。

## Agent Identity 与 SOUL.md 边界

`agent.yml` 是 agent 身份与能力元数据的唯一事实源：

- `key`
- `name`
- `role`
- `description`
- `greetings`
- `wonders`
- `mode`
- `toolConfig`
- `skillConfig`
- `runtimeConfig`

运行时会先根据 `agent.yml` 生成统一的 `Agent Identity` prompt section，再拼接其他 prompt 层。该 section 只包含 `key/name/role/description/mode` 身份事实，不混入工具路由或当前目标解析说明。

`Agent Identity.key` 是当前执行 Agent 的唯一模型可见身份事实。需要按当前 Agent 选择调用目标时，由对应工具描述定义解析规则；当前 `run_query` 会把“当前智能体”“本智能体”“你自己”解析为该 key，并禁止用其他 runtime agent 候选摘要替代。

`SOUL.md` 的职责是长期行为提示，不是配置副本：

- 允许写人格、协作方式、风险姿态、硬边界、非目标
- 允许写长期稳定的行为约束
- 不应重复 `key/name/role/description/mode`
- 不应复制 tools、skills、sandbox、环境路径或一次性任务说明

推荐结构：

```md
# Soul

## Persona

## Boundaries

## Working Style

## Long-Term Notes
```

## Greetings 与 Wonders

`greetings` 与 `wonders` 都是 UI 展示元数据，不参与 agent identity prompt 或系统提示词。

`greetings` 用来配置 agent 的开场/占位介绍，语义是“告诉人类这个智能体能做什么”。它适合展示在聊天输入框 placeholder 或空状态里，例如：

```yaml
greetings:
  - 我可以帮你练习词汇、复盘错题，也能把今天的学习拆成小步骤。
  - 你可以把单词表发给我，我会帮你设计一轮轻量测验。
```

支持配置多条，运行时会过滤空字符串，并通过 `/api/agents` 与 `/api/agent` 原样暴露给客户端；需要随机展示时，前端可以从数组中随机选一条。

单条问候语写法：

```yaml
greeting: 我可以帮你快速看懂这个项目，并给出下一步行动建议。
```

`wonders` 保持原语义：具体的 query 问题参考，也就是用户可以直接点选或提交的示例问题。

```yaml
wonders:
  - Quiz me on vocabulary
  - 帮我检查当前工作区的变更
  - |-
    帮我制定一个三步学习计划
    并给出今天可以开始的第一步
```

## Go 版已落地能力

- agent YAML 文件解析
- 目录式 Team YAML 解析
- skill prompt 目录化装载与 `/api/skills`
- 默认 agentKey 由真实 registry 暴露
- 普通 Agent query 绑定 `agentKey`；Team query 只绑定 `teamId`
- tool 执行器已支持统一 Tool
- Container Hub sandbox 已可参与 tool 执行
- context tags 解析、归一化与 prompt 注入
- model registry 已支持从外部目录读取模型定义
- 目录事件驱动的 catalog/model refresh；所有 enabled KBASE capability 的 Workspace watcher 会在 agent catalog reload 后立即重绑，并保留周期 reconcile 兜底

## Agent 契约与 mode 关系

Go 实现不使用类继承。`internal/agent` 定义 mode descriptor、profile、capabilities、system-init spec 与公共 prompt 渲染契约；`internal/agent/coder`、`internal/agent/kbase`、`internal/agent/team` 分别持有自身 mode 规则，`internal/agent/builtin` 只做静态分派。KBASE 的索引与检索运行时已下沉到独立的 `internal/kbase` 公共能力：

```text
internal/agent
├── coder                 # CODER 具体 mode
├── kbase                 # KBASE 专用 mode 的 profile/prompt/boundary/create
├── team                  # TEAM 内部 mode 与集中调度规则
└── builtin               # 静态分派，不是插件生命周期

internal/kbase            # mode 中立的 config/source/index/watch/retrieval/tools
app/kbase_adapter.go      # catalog 快照 -> kbase.AgentSpec
catalog.TeamSnapshot      # run-scoped Team/成员/协调器配置快照
```

CODER、KBASE 和 TEAM 都是 `internal/agent` 契约下的具体 mode，但 KBASE capability 不依赖 mode 或 catalog；app adapter 只为 enabled capability 构造 `AgentSpec`，其中 `WorkspaceRoot` 是唯一内容根事实。TEAM 只服务于目录式 Team：运行时从 `TeamSnapshot` 合成隐藏协调器，不把它注册成普通 `AgentDefinition`。普通 Agent YAML 声明 `mode: TEAM` 会校验失败，管理接口也不能创建 TEAM agent。

## Team 类型与配置

Team 配置事实源是 `runtime/teams`。只接受目录式定义；平铺 `runtime/teams/<teamId>.yml|yaml`、`defaultAgentKey` 和 `runtimeMode: legacy` 均已移除，发现即启动失败。

### Team

目录式 Team 使用以下结构：

```text
runtime/teams/research/
  team.yml
  SOUL.md       # 可选：Team 人格
  AGENTS.md     # 可选：Team 工作规则
```

`teamId` 来自目录名。最小 `team.yml`：

```yaml
name: Research Team
description: 研究、写作与复核
agentKeys:
  - researcher
  - writer
  - reviewer
orchestrator:
  modelConfig:
    modelKey: qwen3-max
    reasoning:
      enabled: true
      effort: HIGH
    sampling:
      temperature: 0.2
  budget:
    maxSteps: 40
    tool:
      maxCalls: 20
  maxParallel: 3
```

- `orchestrator.modelConfig.modelKey` 必填；`defaultAgentKey` 禁止出现。
- `maxParallel` 默认为 5，只接受 1–5 的整数；它只限制同时执行的成员数。一次 `agent_delegate` 可以列出整个冻结 roster，超出并发数时由 runtime 分波执行。
- `SOUL.md`、`AGENTS.md` 会进入协调器 system prompt，但不能覆盖 `internal/agent/team` 的硬编码路由、安全和隐私规则。
- 目录式 Team 的成员列表为空或任一成员失效时，query/automation 返回不可用，不回退到全局默认 Agent。

隐藏总控每个用户回合统一调用 `agent_delegate`：一项和多项使用相同的 `tasks[]` 契约；`agentKey` 来自本次 run 冻结 roster，`task` 可省略并默认使用原始用户消息，`taskName/files` 可选。同一次调用中成员不可重复，`tasks.maxItems` 等于 roster 大小。成员继承原始 role、scene、references 和专用 Team 历史，附加 files 会转换并去重。

复杂任务由总控先用 `plan_add_tasks` 创建有序任务，再用 `plan_get_tasks`、`plan_update_task` 维护状态。flat plan 同时最多一个 `in_progress`，合法迁移为 `init -> in_progress -> completed/failed/canceled`；当前阶段终态后才能启动下一阶段，终态重试必须追加新 task。一个当前阶段仍可在单次 `agent_delegate` 中并行委派多个成员，成员并行不等于多个计划阶段同时运行。每个用户回合至少成功发起一次委派后才能生成最终答案；所有成员结果都回注总控，根回答只由总控输出。

`agent_delegate` 是 embedded、session-local、internal-only 工具：Team 自动注入，普通 Agent 配置会校验失败，`/api/admin/tools` 不返回它，tool/reasoning 事件也不下发客户端。成员输出复用 task/content 事件，并携带 `actor`、`teamId`、成员 `agentKey` 和 `presentation:"task"`。

### 共同边界

run 启动时 catalog 会原子解析 Team、有效/失效成员、成员 `AgentDefinition`、协调器配置与 prompt，生成本次 run 使用的不可变快照。

- `teamId` 在 chat 创建后固定；已有无 Team chat 也不能补绑 Team。
- Team 请求只传 `teamId`，传入 `agentKey` 会被视为绕过协调器并返回 400。
- Team 的公开 run owner 是 `teamId`；协调器执行 key 不出现在普通 Agent catalog、常规 run 事件、chat summary 或控制接口中。
- Team 成员不能再调用 `agent_invoke`，也不能把另一个 Team 作为成员或子任务目标；ACP CODER 当前不能作为 child。
- Automation、HTTP、WebSocket、submit continuation 与子智能体准入使用同一 Team resolver。历史 chat、archive、restore 与 derive 保留原始身份字段，但历史记录不再恢复旧 Team 路由。
- 运行中的 Team 快照不受 catalog 热重载影响；下一次 run 才读取新成员、prompt 与协调器配置。

## 当前仍有边界

- TEAM 不提供委派级 DAG DSL；计划状态和后续总控轮次表达串行、分支与重试。
- `agent_delegate` 的并行 HITL 按并发波次合并为 Team-level form。
- ACP CODER 不能作为 Team/`agent_invoke` child；普通 Agent 管理接口也不提供 TEAM 创建或编辑入口。

## Context Tags

当前 Go runtime 不会为所有 agent 自动附加一组全局默认 `context tags`；每个 agent 只从 `contextConfig.tags` 读取声明：

```yaml
contextConfig:
  tags:
    - system
    - session
```

支持标签：

- `system`
- `session`
- `owner`
- `agents`

其中：

- `session` 会暴露运行时上下文
- `owner` 会注入 `configs/runtime.yml -> paths.owner-dir` 下的 markdown 内容；`mode: CODER` 不会默认启用，需要显式声明
- `agents` 会注入模型可见的 `Runtime Context: Sub-Agent Candidates` 候选摘要；只写 `tags: [agents]` 表示当前 Agent 之外的全部 agent，也可用 `contextConfig.agents` 指定部分 agent key
- `sandbox` 不再通过 `context tags` 控制；只要 agent 声明了 `runtimeConfig.environmentId`，运行时会自动注入 sandbox context
- runtime memory context 不再通过 `context tags` 控制；只有 agent 显式开启 `memoryConfig.enabled: true` 时，运行时才会自动注入 memory context

注入当前 Agent 之外的所有候选摘要：

```yaml
contextConfig:
  tags:
    - system
    - session
    - agents
```

只注入指定候选摘要：

```yaml
contextConfig:
  tags:
    - system
    - session
    - agents
  agents:
    - coder
    - planner
    - customer-service
```

`contextConfig.agents` 也支持逗号字符串或 `"*"`：

```yaml
contextConfig:
  tags:
    - agents
  agents: "coder,planner"
```

`agents` 只影响 prompt 中的候选摘要，不影响 channel 可访问范围、`agent_invoke` / `agent_delegate` / run 工具权限或 catalog 可见性，也不是 `run_query` 的目标白名单。当前 Agent 无论来自缺省全量还是显式 `contextConfig.agents` 都会静默排除；过滤后没有其他候选时不生成该区块。候选区块只供目标选择和任务路由参考，当前身份始终以 `Agent Identity.key` 为准。

## Prompt Files

目录式 agent 会按约定读取 prompt 文件：

- 普通模式默认读取 `AGENTS.md`
- 顶层 `promptFile` 可显式覆盖普通模式 prompt
- `PLAN-EXECUTE` 默认读取 `AGENTS.plan.md`、`AGENTS.execute.md`、`AGENTS.summary.md`
- `stageSettings.<stage>.promptFile` 可显式覆盖对应阶段
- `PLAN-EXECUTE` 阶段缺少约定文件时，先回退顶层 `promptFile`，再回退 `AGENTS.md`
- `mode: CODER` 还会按 `configs/coder-settings.yml` 读取 `runtimeConfig.workspaceRoot/AGENTS.md`，用于注入项目级 workspace 规则；配置了 `projectConfig.promptFiles` 时改按该列表读取
- `mode: KBASE` 不读取 knowledge source 中的 `AGENTS.md`，只通过 KBASE 系统提示和知识库工具工作；普通 Agent 附加 KBASE capability 时仍按自身 mode 规则加载 prompt files

`PLAN-EXECUTE` 的阶段配置推荐统一放在 `stageSettings.<stage>` 下：

```yaml
stageSettings:
  plan:
    promptFile: AGENTS.plan.md
    modelConfig:
      modelKey: qwen3-max
    toolConfig:
      tools: ["file_read", "file_grep"]
```

阶段内 `modelConfig` 支持 `modelKey`、`reasoning`、`sampling`、`maxOutputTokens` 等运行参数；阶段内 `toolConfig.tools` 覆盖该阶段可用工具。

## CODER Mode

CODER 是一等 agent mode。内建 icon、工具、context、budget、cache key、创建前缀及 capability 的代码事实源是 `internal/agent/coder`；catalog 只在 YAML 未显式声明对应字段时应用该 profile。所有 CODER（native、ACP、host、sandbox）都必须配置可解析为现存绝对目录的 `runtimeConfig.workspaceRoot`；`@chat` 不再是合法 Workspace。

native CODER 使用 platform 的本地工具循环。未声明 `toolConfig.tools` 时，它会使用 CODER profile 默认工具，其中包括 `artifact_publish`；声明非空列表时，该列表会收窄 native CODER 的平台工具授权。native 的 main / execute 工具选择仍由运行时补全 `plan_add_tasks`、`plan_get_tasks`、`plan_update_task`，planning 固定工具集不包含 `artifact_publish`。

配置 `runtimeConfig.acpBridgeId` 的 ACP CODER 由 ACP bridge 自行决定可用能力，platform 不声明、透传或模拟任何工具。因此它的 effective `tools` 始终为空，且 `toolConfig.tools` 只能省略或设为空列表；任何非空列表都会使 Agent 配置校验失败。

通过管理接口 `/api/admin/agents/create` 创建 `mode: CODER` 或 `mode: KBASE` agent 时，请求只需要表达创建意图；两者都必须传 `runtimeConfig.workspaceRoot`，ACP CODER 额外传 `runtimeConfig.acpBridgeId`。创建前缀和 mode profile 分别由 `internal/agent/coder`、`internal/agent/kbase` 维护；配置文件只提供可覆盖的模型、reasoning、embedding 与 budget 输入。存在最终 Workspace 时，生成流程会把缺省 `name` 设为目录 basename。

### Agent ZIP 导入

管理接口 `POST /api/admin/agents/import` 接收 multipart `file` 与可选布尔 `overwrite`。Agent Key 只读取 ZIP 根目录或唯一一层包装目录内的 `agent.yml` / `agent.yaml`，不接受调用方另传 Key。导入按目录原样保留 prompt、专属 Skills、`.config`、知识文件和其他普通资源，不注入创建默认值，也不重写绝对 Workspace 路径。

同 Key 来源存在时，默认返回 409 并要求显式确认；`overwrite=true` 会完整替换旧来源而非合并。已有目录型 Agent 原位替换，平铺 YAML Agent 转换为 `<agentsDir>/<key>/agent.yml` 形式的目录来源。替换使用隐藏 staging/backup；catalog 硬重载失败会恢复旧来源。catalog 正常发布但单个 Agent 因当前机器缺少模型、工具、Workspace、KBASE 或 Skill 而无效时，导入内容会保留，响应 `status: invalid` 并携带 diagnostics，便于在管理台继续修复。

ZIP 仅接受普通文件，拒绝路径逃逸、反斜杠路径、symlink、大小写/重复路径及文件目录冲突；`__MACOSX` 和 `.DS_Store` 被忽略。上传和单文件上限均为 32 MiB，解压总量上限为 256 MiB，最多 4096 个条目，Agent YAML 必须是最大 1 MiB 的 UTF-8 文本。`.config` 可能含敏感内容，只应导入可信 ZIP，落盘时该目录及文件使用私有权限。

显式配置 `platform_control` 的治理 Agent，可以在不调用 HTTP 管理接口、不传递 JWT 的前提下读取同一组有效创建默认值。`catalog.defaults.get` 的 `params.path` 只接受 `agents.creation.coder` 与 `agents.creation.kbase` 两个精确路径，返回 `keyPrefix`、小型 `definitionDefaults`、`ready` 与 `missingFields`；它不回显 ACP、provider、MCP 或 runtime env 中的凭据。`catalog.validate` 可只读校验完整的 agent、team、skill 或 MCP server 候选内容，校验本身不写文件、不触发 catalog 重载。实际创建和修改仍由现有文件工具完成，并由目录 watcher 在落盘后热重载。Skill 只提供调用知识，不会替 Agent 挂载 Tool。

## KBASE 公共能力与 Mode

KBASE 是一项可组合的 Agent 公共能力。platform 对知识源持续执行文本抽取、切块、embedding、LanceDB generation 检索和增量 watcher；`mode: KBASE` 则是这项能力的专用预设：始终启用、故障策略为 required，并把工具和 memory 严格限制为原有 KBASE mode 边界。`REACT`、`PLAN-EXECUTE` 与原生非 ACP `CODER` 可以用 `kbaseConfig.enabled: true` 附加同一能力，同时保留各自原有工具、prompt files 和 memory 行为。ACP CODER、`PROXY`、`CHANNEL` 以及 TEAM 协调器不能直接附加；Team 成员本身可以携带。

LanceDB 是唯一检索库；SQLite `control.db` 只保存 generation、文件状态、refresh run 和恢复日志，不保存 chunk、FTS 或 embedding，并且只接受当前 schema。公共配置、Workspace 解析、索引/检索默认值、工具名、watcher 与存储契约以 `internal/kbase` 为代码事实源；`internal/agent/kbase` 只维护专用 mode 的 profile、prompt、system-init、创建策略与严格边界。`kbase_files` 只浏览 active KBASE generation 的文件元数据，不等同于 host filesystem 的 `file_glob` / `file_read`。

目录式普通 Agent 推荐配置如下。Workspace 目录可以位于 Agent 目录内，但 `runtimeConfig.workspaceRoot` 仍必须展开为现存绝对路径：

```text
zenmi/
├── agent.yml
└── knowledge/
    ├── product.md
    └── faq/
        └── billing.md
```

```yaml
key: zenmi
name: Zenmi
mode: REACT
modelConfig:
  modelKey: deepseek-v4-pro
toolConfig:
  tools:
    - datetime
    - web_fetch
kbaseConfig:
  enabled: true
  embedding:
    modelKey: babelark-text-embedding-v4
  storage:
    location: runtime
runtimeConfig:
  workspaceRoot: /absolute/runtime/agents/zenmi/knowledge
```

启用后五个 KBASE 工具会自动加入最终工具集合，不要求在 `toolConfig.tools` 中重复声明；普通 Agent 原有工具不会被过滤。公共 capability prompt 会在 run 创建时冻结到 session，包含“先检索、按来源引用、资料不足时明确说明、文档属于非可信证据”等规则。catalog 热重载只影响之后创建的新 run，既有 run 不会在执行中途突然获得或失去能力。

专用 KBASE mode 的推荐配置：

```yaml
key: docs_kbase
name: Docs KBase
mode: KBASE
modelConfig:
  modelKey: deepseek-v4-pro
  reasoning:
    effort: MEDIUM
runtimeConfig:
  workspaceRoot: /absolute/docs
kbaseConfig:
  tags:
    - docs
    - knowledge-base
  embedding:
    modelKey: babelark-text-embedding-v4
```

所有 enabled KBASE 都必须配置 `runtimeConfig.workspaceRoot`，并把它作为 watcher、索引、检索、editingMode、include/exclude 与 `storage.location: workspace` 的唯一内容根。旧 `kbaseConfig.source` 在启动与候选校验时硬失败。专用 `mode: KBASE` 的 `kbaseConfig.enabled` 默认为 `true`，显式写 `false` 会失败；普通 mode 附加能力时必须显式写 `enabled: true`。KBASE Workspace 不能是文件系统根，且必须与 ChatsRoot 完全分离：相等、包含、被包含或 symlink 实际重叠均会被拒绝。

专用 KBASE mode 在 main/editing 两种 stage 都固定提供原 KBASE 工具和 `file_read/file_glob/file_grep/file_write/file_edit`。相对路径固定从最终 Workspace 解析；当前 `chatId` 的 Chat 目录仅作为独立 `ChatDir` 由 `@chat` 授权。请求级 `editingMode:true` 只允许 KBASE Workspace mutation。未开启时 Workspace 可读但不可 write/edit，当前 Chat 目录仍可读写。Workspace、Chat、其他 chatId 和 external 均服从 AccessPolicy/HITL；approval、hostAccess、writeRoots 和 `full_access` 不能替代 KBASE Workspace 的 editing 授权。

完整可覆盖配置：

```yaml
kbaseConfig:
  enabled: true
  tags:
    - 售后
    - 工单
  embedding:
    modelKey: openai-text-embedding-3-small
  storage:
    location: runtime
  include:
    - "**/*.md"
    - "**/*.txt"
    - "**/*.html"
    - "**/*.htm"
    - "**/*.pdf"
    - "**/*.docx"
    - "**/*.pptx"
  exclude:
    - ".git/**"
    - ".kbase/**"
    - "node_modules/**"
  chunk:
    unit: estimatedTokens
    maxTokens: 1000
    overlapTokens: 100
  retrieval:
    topK: 8
    fusion: rrf
    rrfK: 60
    vectorWeight: 0.7
    ftsWeight: 0.3
    candidateFloor: 30
    candidateMultiplier: 4
    candidateMax: 500
```

`modelConfig.modelKey` 是 Agent 回答问题时使用的大模型；`modelConfig.reasoning.effort` 是该回答模型的思考程度。通过管理接口新建专用 KBASE agent 且请求未提供这些字段时，后端会从 `configs/kbase-settings.yml` 读取创建输入并把最终值写入 agent YAML。`kbaseConfig.tags` 是可公开的调度元数据，但不进入 Channel Agent v1 注册 payload；标签不得含知识库原文、路径、凭证或未脱敏隐私。`kbaseConfig.embedding.modelKey` 是索引和检索知识库时使用的 embedding 模型业务别名，必须引用 `runtime/registries/models/*.yml` 中 `type: embedding` 的模型，不控制回答模型或思考程度。`kbaseConfig.chunk` 是每个 capability 独立的切块配置：未配置时使用 estimated token 默认值；字符切块必须显式写 `unit: chars`，再使用 camelCase 的 `maxChars` / `overlapChars`。未写 unit 的字符字段、kebab-case retrieval 键和 unit 别名均会被拒绝。storage 路径规则由 `internal/kbase` 维护；默认 `storage.location: runtime` 写入 `AP_RUNTIME_KBASE_DIR/<agentKey>`，`storage.location: workspace` 写入 Workspace 内的 `.kbase`，一个 canonical storageDir 不允许被多个 Agent 共用。HTML 使用静态抽取，不执行脚本；抽取时会跳过脚本、样式和明显隐藏内容，只索引可见正文。`kbaseConfig.embedding` 只接受 `modelKey`，旧式 `embedding.providerKey/model/dimension/timeout` 不再读取，也不会回退到 provider 顶层 `embedding.*` 或 `provider.memory.embedding`。

故障策略由 capability requirement 决定。`mode: KBASE` 映射为 required：启动期 storage contract 无效时 Agent 以 `invalid_kbase_storage` 留在管理端并从运行 catalog 隔离，sidecar 故障使 `/healthz` 返回 unhealthy。普通 Agent 附加能力映射为 optional：相同存储、embedding 或 sidecar 故障不会移除 Agent，`status` 返回 `degraded/stale`，知识库工具返回明确的 `kbase_unavailable`，而 Agent 的非 KBASE 工具仍可工作；修复后成功 refresh 会清除启动降级状态。两种 requirement 都不迁移、不修复、也不回退旧 SQLite 检索数据。

retrieval 固定使用加权 RRF。每路先取 `candidateK = min(candidateMax, max(candidateFloor, candidateMultiplier * (offset + limit)))`，然后将 vector/FTS 权重归一化并计算 `weight / (rrfK + rank)`。对外 score 再按理论 rank-1 上限归一化并 clamp 到 `[0,1]`；只进入某一路的结果分别标记 `vector` / `fts`，两路同时命中标记 `hybrid`。同分时按 path、startLine、chunk ID 稳定排序。`matchCount` 是有限候选池的去重并集数，不是全库命中数；候选路径达到 `candidateMax` 或分页后仍有结果时 `truncated=true`。

retrieval 中的 topK/RRF/权重/候选池只进入 `queryHash`，修改后立即作用且不会全量重建。embedding 模型或 dimension、chunk、include/exclude、extraction、FTS tokenizer 等进入 `indexHash`，变化时构建新 generation。`force=true` 也构建新 generation，不原地清空 active generation。

Workspace watcher 将 2 秒 debounce 内的事件合并为路径 change set；同一路径去重、父目录覆盖子路径，超过 1000 条或 watcher overflow 时退化为完整 reconcile。日常新增、修改和删除只处理事件路径，手工 `force=false`、启动和 10 分钟周期任务仍扫描整个 knowledge Workspace 对账；只有首次建库、`indexHash` 变化或 `force=true` 创建新 generation。

LanceDB 使用 ICU4X word segmentation 预分词，再用 Lance FTS whitespace tokenizer 建索引，因此不需要分发 Jieba 模型。当前这仍是文本型 KBASE：PDF/DOCX/PPTX/HTML 是抽取文本后检索，没有图片、音频、视频 embedding 管线。存储、迁移、回滚和 sidecar 详情见 [KBASE LanceDB 迁移](KBASE-LanceDB迁移.md)。

## Budget

运行步数统一配置在 `budget` 下。

推荐写法：

```yaml
budget:
  timeout: 3600
  maxSteps: 240
  hitl:
    timeout: 600
    question:
      timeout: 600
    approval:
      timeout: 600
    form:
      timeout: 600
  tool:
    maxCalls: 200

stageSettings:
  plan:
    budget:
      maxSteps: 20
      tool:
        maxCalls: 40
  execute:
    budget:
      maxSteps: 20
      tool:
        maxCalls: 40
  summary:
    budget:
      maxSteps: 1
```

- `budget.maxSteps` 是整次 run 的模型轮次总上限；resolved budget 中会同步到 `model.maxCalls`。
- `tool.maxCalls` 可显式配置；未配置时，如果同级配置了 `maxSteps`，默认按 `maxSteps * 2` 推导。
- PLAN-EXECUTE 阶段预算写在 `stageSettings.<stage>.budget`。
- `budget.timeout`、`budget.model.timeout`、`budget.tool.timeout`、`budget.hitl.timeout` 等预算超时字段单位都是秒。
- `budget.timeout` 是单次 run 的执行时长上限；一个 run 是一条用户消息触发的 agent 执行，从开始到最终回答结束。CODER planning confirmation 的用户等待时间不计入该预算，其他等待或执行时间仍按既有规则计入。
- `budget.model.timeout` 是模型流式 idle 超时；首个响应 chunk 或任意两个 chunk 之间超过该秒数无响应则报错。chat model registry 顶层 `timeout` 配置后会覆盖该值，常用于 MiniMax / transit-hub 这类可能长时间不发 SSE 心跳的模型。
- `budget.tool.timeout` 是单次工具调用硬上限；bash/file/MCP 等工具不能超过该值。
- CODER 运行时预算优先级为 agent.yml 显式 `budget` > CODER profile fallback；fallback 的代码事实源是 `internal/agent/coder/profile.go`。`configs/coder-settings.yml -> default-agent.budget` 只在创建 CODER agent 时写入默认 `budget`，不会作为运行时动态覆盖；已有显式 budget 不会自动迁移。
- `budget.hitl.timeout` 是当前智能体的 HITL/awaiting 默认，会覆盖 `configs/runtime.yml` 的全局 `budget.hitl`；`question`、`approval`、`form` 可用 mode 覆盖，`approval`、`form` 还会优先使用具体等待项自己的 `timeout` 秒值（如 bash-hook subcommand 或 form/tool 定义）。未配置时内置 fallback 为 `600` 秒。CODER `finalize_planning` 的 planning confirmation 是独立机制，永久等待、不读取 `budget.hitl.plan`，并且 `awaiting.ask(mode=planning)` 不下发 `timeout`；遗留 `budget.hitl.plan` 静默忽略。CODER 使用 `stageSettings.planning` 与 `budget.stages.planning`；旧的 CODER `stageSettings.plan` / `budget.stages.plan` 会在加载时失败。`plan_*` 与 plan-tasks 是执行任务跟踪，和 planning confirmation 无关。其他事件中的 `awaiting.ask.timeout` 单位为秒：配置值 `0` 表示未配置，事件值 `0` 表示无限等待、不自动超时，正值由后端按真实时间独立计时，不受 observer / attach / detach 状态影响。
- `REACT` 使用 `react` 单阶段；普通 `CODER` 使用 `execute` 阶段；CODER planning 使用 `planning`、`execute` 两个阶段；`PLAN-EXECUTE` 支持 `plan`、`execute`、`summary` 三个预算阶段。

请求顶层 `planningMode: true` 仅允许 `mode: CODER`；其他 mode 会被拒绝。planning 阶段仅暴露 `file_read`、`file_glob`、`file_grep`、`datetime`、`regex`、`vision_recognize`、`ask_user_question`、`finalize_planning`；`finalize_planning` 只接收完整 `markdown`，后端不补标题、不重排正文，并把该 Markdown 原样写入 `AP_RUNTIME_CHATS_DIR/<chatId>/.tools/planning/<runId>_planning_<revision>.md`。live 事件按 `planning.start`、多条 `planning.delta`、`planning.end`、`awaiting.ask(mode=planning)` 的顺序发送；后者是永久等待的 planning confirmation，不下发 `timeout`，并在 `planning` 对象中携带 `planningId` 与 `planningFile`。其 `awaitingId` 与原始 `finalize_planning` tool call id 相同，并随 `_type:"react"` step 的 `awaiting[]` 持久化，不把 Markdown 正文写入 JSONL。JSONL 会保留原始 assistant `tool_calls`，并在用户 approve/reject 后追加匹配同一 `tool_call_id` / `name:"finalize_planning"` 的 `_type:"react-tool"` / `role:"tool"` 结果。`GET /api/chat` 回放时读取该文件并恢复顶层最新 `planning`，同时在对应 `awaiting.ask` 前合成 replay-only 的 `planning.snapshot` 事件供时间线使用。后端不持久化 `planning.start` / `planning.delta` / `planning.end`。

native CODER 中，用户以 `mode=planning` approve 后会结束当前 planning run：旧 live stream 先出现 `awaiting.answer`，再出现旧 run 的 `run.complete`，随后以 stream terminal `reason:"done"` 结束；旧 live stream 不追加新 run 的 `run.start`，也不继续桥接 execution 的 content/tool 事件。服务端在旧 stream done、旧 run finished 后启动新的 execution run，并通过 WebSocket push `run.started { runId, chatId, agentKey }` 让客户端发现新 `runId`；客户端应 attach 新 `runId` 读取新 run 自己的执行流。新的 execution run 首部为 execution run bootstrap `request.query(message:"Execute planning", requestId:<execution request id>)`，随后是新 run 的 `run.start`，完整执行 prompt 只写入 JSONL/model messages；execution run 关闭 `planningMode`，暴露 CODER 执行工具和 `plan_add_tasks`、`plan_get_tasks`、`plan_update_task` 作为可选轻量任务追踪工具。这些工具不接管执行，但任务状态仍遵守有序、单活动和终态不可复活规则。`plan_add_tasks` / `plan_update_task` 会把当前任务快照按 execution run 写入 `AP_RUNTIME_CHATS_DIR/<chatId>/.tools/plan-tasks/<runId>_plan.json`，`/api/chat` 读取该目录的最新快照作为顶层 `plan`；重启后同一 `chatId` 的新 query 不复活旧 run / SSE，但在 CODER 执行类阶段会从最新快照恢复 plan task 内存状态，`plan_get_tasks` 可直接读到恢复结果，后续 `plan_update_task` 会写入新 run 的快照。`plan_add_tasks` 默认追加到当前 plan；当用户开启新的目标/计划时，调用方可传 `mode:"new"` 创建新的 `planId`，并让本次 tasks 成为新 plan 的完整初始任务列表。execution 阶段的最终回复就是用户可见收尾，不再额外启动 `coder-summary` 模型调用。reject 后当前 planning 不会执行，也不会启动新 run，模型可在原 planning run 中生成下一版 planning revision 或直接结束本轮。

CODER 专属系统提示词从 `configs/coder-prompts.yml` 读取；普通 CODER 使用 `system-prompt`，planning 阶段使用 `planning-prompt`，execute 阶段使用 `system-prompt` 与 execute stage prompt。随包 `coder-prompts.example.yml` 的 `system-prompt` 还为 native CODER 约定：仅在量化对比、趋势、分布或占比明显受益时输出独立的 `echarts` 代码块，块内必须是无注释、无尾逗号和无 JavaScript 表达式的合法 JSON；内联图表不是文件产物，不调用 `artifact_publish`。`summary-system-prompt` / `summary-user-prompt-template` 已从 CODER 专属 prompt 配置中删除；`PLAN-EXECUTE` 的 summary prompt 配置不受影响。

### ACP CODER Backend

CODER 可通过 `runtimeConfig.acpBridgeId` 改由 `configs/coder-settings.yml` 中的 ACP bridge 执行。此时 agent 仍是 `mode: CODER`，但执行链路会转发到 `codex-acp-bridge`。除 PROXY 外，ACP CODER 也允许缺省 `modelConfig.modelKey`；如果配置了 `modelConfig.modelKey`，该值会作为上游 bridge 的模型参数使用。未声明 `acpBridgeId` 时默认使用 native CODER，必须显式配置 `modelConfig.modelKey`：

```yaml
# configs/coder-settings.yml
acp-bridges:
  codex:
    base-url: http://127.0.0.1:17071
    timeout-ms: 300000
    auth-token: ${CODEX_ACP_BRIDGE_AUTH_TOKEN:}
```

```yaml
mode: CODER
modelConfig:
  modelKey: gpt-5-codex
runtimeConfig:
  acpBridgeId: codex
  workspaceRoot: /absolute/project/path
projectConfig:
  git:
    expectedBranch: main
```

ACP CODER 的模型可以只作为转发给 bridge 的外部模型参数注册，不需要配置平台原生 provider：

```yaml
# registries/models/gpt-5-codex.yml
key: gpt-5-codex
name: GPT-5 Codex
protocol: ACP_PASSTHROUGH
modelId: gpt-5-codex
```

ACP CODER 中，编程项目配置仍由 platform 的 `agent.yml` 管理，包括可选的 `modelConfig.modelKey`、`runtimeConfig.workspaceRoot` 和 `projectConfig.git.expectedBranch`。Codex CLI、网络代理、Codex app-server/exec 参数由 `codex-acp-bridge` 自身配置管理；平台 `toolConfig.tools` 不受支持，bridge 工具必须由 bridge 自行配置。ACP CODER 支持把平台 `planningMode` 透传给上游 ACP bridge；具体 planning mode 语义由 `codex-acp-bridge` 与 Codex app-server 实现。ACP CODER v1 不支持 `projectConfig.promptFiles`；工作区规则由 Codex 在目标工作目录中自行读取。

## CHANNEL Mode

`mode: CHANNEL` 表示“把外部 platform/adaptor 上的 agent 导入为本地 agent”。该模式不进入本地 LLM engine，也不要求 `modelConfig.modelKey`；运行时会根据 `channelConfig.channelId` 找到对应 channel，再用 `remoteAgentKey` 作为上游 agent key 发起 `platform-ws` 请求。`channel.mode` 只表示连接建立方向：`client` 由本端主动连出到 `endpoint.url`，`server` 由本端开放 `/ws/channel` 等待对端连入；两者都可以承载 CHANNEL agent 调用。

```yaml
key: remote-coder
name: Remote Coder
mode: CHANNEL
channelConfig:
  channelId: peer-a
  remoteAgentKey: coder
```

`mode: CHANNEL` 的校验规则：

- 必须配置 `channelConfig.channelId` 与 `channelConfig.remoteAgentKey`
- 禁止配置 `channelConfig.exports`
- 对应 channel 必须存在于 `configs/channels.yml`
- `mode: client` channel 必须配置可连接的 `endpoint.url`
- `mode: server` channel 必须已有活跃对端连接；未连接时 `/api/query` 返回 `503 channel <channelId> is not connected`

本地 agent 导出给外部 channel 时，不使用 `mode: CHANNEL`。本地 `REACT / CODER / PLAN-EXECUTE / PROXY` 等 agent 可以声明 `channelConfig.exports`：

```yaml
key: assistant
name: Assistant
mode: REACT
modelConfig:
  modelKey: deepseek-v4-pro
channelConfig:
  exports:
    - channelId: public-entry
      externalAgentKey: assistant
      allow:
        query: true
        submit: true
        fileTransfer: true
```

`exports[].channelId` 必填。`exports[].externalAgentKey` 可选；省略或为空时，默认使用本地 agent 的 `key` 作为外部调用名。例如 `key: kbaseOrchestrator` 的 agent 可以只写：

```yaml
channelConfig:
  exports:
    - channelId: singapore-webclient
      allow:
        query: true
```

外部调用时使用 `{"externalAgentKey": "kbaseOrchestrator"}` 即可匹配。

`exports[].allow.query` 默认 `true`；`submit`、`steer`、`interrupt`、`fileTransfer` 默认 `false`，需要显式开启。导出请求只能从匹配的 channel 进入，并按 `externalAgentKey`（或其默认值）映射到本地 agent key，再检查 allow 权限。

接出注册与 channel 的建连方向无关。`mode: client` 由本 Platform 主动连出，`mode: server` 由对端连接 `/ws/channel`；两种连接都必须先收到对端的 v1 `push connected`，随后由本 Platform 发送 `agent.list / agent.register / agent.unregister`。同一 server channel 的多条连接按独立 Session 分别对账，不共享注册所有权。

注册范围只认普通 Agent 上显式声明、且 `allow.query: true` 的匹配 export；`mode: CHANNEL` Agent 永远不会作为本地接出项注册。旧 `agents: "*"` 配置已移除并会导致加载失败。注册 payload 只包含：

- `agentKey`：优先使用 `externalAgentKey`，缺省回退本地 Agent key。
- `name`：Agent name，空值回退本地 key。
- `role`、`description`：来自 Agent 定义，空值省略。
- `capabilities`：`query / steer / interrupt / hitl` 分别映射 `allow.query / steer / interrupt / submit`。

`fileTransfer`、Skill、Tool、Tag、Prompt、Workspace、KBASE 隐式能力和模型配置均不进入 v1 注册。四项稳定能力全部开启且对端正好支持这四项时发送 `["all"]`，否则按固定顺序发送显式能力列表。字段按 Gateway v1 的长度与非法控制字符规则校验；公开元数据仍需由维护者预先完成隐私脱敏。

每轮先通过 `agent.list` 查询当前 `platformKey` 下所有 Session 注册的 Agent，但只操作 `ownedByCurrentSession:true` 的项目。删除 export 或关闭 query 会触发 `agent.unregister`；展示字段或展开后能力变化会再次 `agent.register` 做完整替换。`SINGLE_EMPLOYEE` 连接若匹配多个有效 export 会整体报配置错误。详细帧格式、Session 生命周期和重试语义见 [API与协议](API与协议.md#channel-agent-接出注册-v1)。

## PROXY Mode

PROXY agent 用于把平台请求转发给兼容的上游服务。新 platform-to-platform / adaptor 接入优先使用 `mode: CHANNEL` 与 `channelConfig`。PROXY 仍可用，只要求 `proxyConfig.baseUrl`，不要求本地 `modelConfig.modelKey`；旧配置中保留的 `modelConfig.modelKey` 仍可被加载并回显，但运行链路不会依赖它：

```yaml
key: codeAssistant.demo
name: 星码
role: CLI 代码助手
description: 透传到 CLI 模式代码助手服务
mode: PROXY
runtimeConfig:
  workspaceRoot: /absolute/project/path
proxyConfig:
  baseUrl: http://127.0.0.1:3210
```

`proxyConfig` 字段语义：

- `baseUrl` 必填，指向上游代理服务根地址
- `transport` 可选，默认 `ws`；显式设为 `sse` 时使用上游 `/api/query` SSE 链路
- `agentKey` 可选，用于覆盖转发给上游的 agent key
- `token` / `tokenEnv` 可选，仅当上游服务启用 Bearer 鉴权时配置；默认不需要 token
- `timeout` 可选，默认 `300`（秒）；通常不需要显式配置

`POST /api/query` 中的 `model` 字段在 PROXY 模式下原样透传给上游，由上游服务解释；platform 不要求该模型存在于本地 model registry，也不会把它写入本地 session/stage settings。

## Static Memory 与 Runtime Memory

agent 目录下的 `memory/memory.md` 当前作为静态背景提示装载：

- 语义：agent 的长期固定背景，不是运行时记忆库
- 注入顺序：`Agent Identity` 与 `SOUL.md` 之后、runtime memory bundle 之前
- 存储位置：随 agent 文件存在，不进入 SQLite memory store

运行时记忆来自 memory store：

- `Stable Memory`：长期稳定、可复用的 `fact`
- `Relevant Observations`：近期观察类 `observation`

`snapshot/*.md` 仅作为导出/审阅视图：

- 不参与 prompt 主链路
- 不作为 runtime memory 的事实源

## Memory Tool 注入

agent definition 可通过 `memoryConfig` 控制默认注入的 memory 工具：

```yaml
memoryConfig:
  enabled: true
  managementTools: true
  embedding:
    providerKey: babelark
  autoRemember:
    enabled: true
    modelKey: minimax-m2_7-anthropic
    timeout: 60
```

规则：

- 未配置 `memoryConfig.enabled` 或配置为 `false` 时，不启用 runtime memory，也不注入 memory tools
- `enabled: true` 时注入基础集：
  - `memory_write`
  - `memory_read`
  - `memory_search`
- `managementTools: true` 时额外注入管理集：
  - `memory_update`
  - `memory_forget`
  - `memory_timeline`
  - `memory_promote`
  - `memory_consolidate`
- `autoRemember.enabled: true` 时，run 完成后自动执行 learn / auto-remember
- `autoRemember.modelKey` 填 `AP_RUNTIME_REGISTRIES_DIR/models/*.yml` 中的 model key，用于记忆筛选、总结、合并
- `embedding.providerKey` 填 `AP_RUNTIME_REGISTRIES_DIR/providers/*.yml` 中的 provider key；embedding 模型、维度和超时优先来自 provider 的 `memory.embedding`，agent 侧也可覆盖

运行时策略：

- `Learn(...)` 成功后会自动执行一轮轻量 observation 整理
- 自动整理默认只做 stale/duplicate 收口，以及“重复出现 observation”的晋升
- 更激进的生命周期治理仍建议通过显式 `memory_consolidate` 触发

## Runtime Config

Go runtime 当前支持在 `agent.yml -> runtimeConfig` 下声明：

```yaml
runtimeConfig:
  environmentId: shell
  level: RUN
  workspaceRoot: /absolute/project/path
  hostAccess:
    readRoots:
      - "@owner"
      - "@temp"
    writeRoots:
      - "@temp"
  sandboxMounts:
    - platform: owner
      destination: /owner
      mode: rw
  env:
    HTTP_PROXY: "http://127.0.0.1:7890"
    HTTPS_PROXY: "http://127.0.0.1:7890"
    TZ: "Asia/Shanghai"
```

约束与语义：

- `env` 只接受 `map[string]string`
- `runtimeConfig.runEnv` 已移除；遗留字段静默忽略，不产生动态环境策略、校验或权限
- key 必须非空，且不能包含空白字符或 `=`
- `AP_AGENT_CONFIG_HOME`、`AP_WORKSPACE_DIR`、`AP_CHAT_DIR` 与 `AP_ACCESS_TOKEN` 是平台保留变量，agent `runtimeConfig.env`、skill `.runtime-env.json` 或调用级 env 声明任一变量都会使校验失败；`AP_ACCESS_TOKEN` 只由普通 Agent Host Bash 按有效 identity 文件当前内容注入，默认文件为 `<AP_RUNTIME_DIR>/identity/access-token`，显式 `--identity-file <absolute-path>` 优先
- value 必须是字面量字符串；空字符串允许并原样注入 host bash 或下发到 Container Hub
- 不支持 `${VAR}` 或其他宿主环境变量展开
- `runtimeConfig.workspaceRoot` 定义 Agent 的宿主 Workspace；必须可展开为现存绝对目录，不能为 `@chat`。普通 Workspace 不能等于 ChatsRoot 或位于 ChatsRoot 内，但可以包含 ChatsRoot，`/` 合法；KBASE Workspace 额外禁止文件系统根和任意方向的 ChatsRoot 重叠
- `runtimeConfig.hostAccess.readRoots/writeRoots` 追加单个 agent 的 host-side 可操作目录，只影响 host `bash` 与 `file_*` 工具；root 支持绝对路径、`~/...`、`@workspace`、`@chat`、`@agent`、`@skills`、`@skills-center`、`@owner`、`@temp`。`@temp` 已无条件进入 effective default roots，显式写入 hostAccess 主要用于自说明
- `runtimeConfig.sandboxMounts` 配置额外挂载；`/workspace`、`/chat` 及其子路径为保留目标，不能覆盖
- `runtimeConfig.acpBridgeId` 仅对 `mode: CODER` 生效，必须引用 `configs/coder-settings.yml` 中的 `acp-bridges` 条目；存在时该 CODER 使用 ACP backend，不存在时默认使用 native backend。`timeout-ms` 的默认值为 `300000`；修改 `coder-settings.yml` 后必须重启 runtime 才会生效
- 工具路径中的 `@chat` 会解析为当前 `AP_RUNTIME_CHATS_DIR/<chatId>`；这不意味着它可以写入 `workspaceRoot`
- `runtimeConfig.environmentId` 是 sandbox context 的唯一入口；不需要也不支持再在 `contextConfig.tags` 中声明 `sandbox`
- agent `runtimeConfig.env` 作为基础值，组装后 Skill 目录下的 `.runtime-env.json` 会按 agent 声明顺序叠加并覆盖同名键；运行时不回退原始 Agent 或 skills-center
- 当前普通 native root run 可通过显式挂载的 `platform_control` 调用 `run.env.set/unset`；动态 env 位于静态 Agent/Skill env 之上，调用级 env 与 Platform reserved context 位于它之上。只有当前 run 成功 set 的 key 才能 unset，删除动态层后回退同名静态/Host 值。Skill 和 `mustUseSkills` 都不会替 Agent 挂载 Tool
- `/api/agent` 与 `/api/admin/agents` 的 `sandbox` meta 不会回显 `env`，避免暴露代理地址、凭据或私有 endpoint；sandbox mounts 仍可对外暴露，因为它描述的是白名单路径而非敏感值。`/api/agents` 仅返回列表摘要，不包含 `meta`。
- `/api/agent`、Catalog 与 tool result 都不会回显动态 value；set/unset 成功只返回 key、changed、idempotent、revision。完整限制见 [Platform 控制工具设计与实现](./Platform控制工具设计.md)

所有 CODER、所有配置 Container Hub sandbox 的 Agent 与所有 enabled KBASE 都必须解析出 Workspace。无 sandbox 的 REACT、PLAN-EXECUTE、PROXY、CHANNEL 可以没有 Workspace，但相对路径、`@workspace`、省略 `cwd` 的 Bash、省略 `path` 的 glob/grep 和 Workspace Terminal 会返回 `workspace_unavailable`，不会回退 Chat 或进程 cwd。无 Workspace session 的模型工具 schema 会把这些参数动态标为必填；普通 Chat 文件操作应显式使用 `cwd: "@chat"`、`path: "@chat"` 或 `@chat/...`。

### Agent 与 Chat 执行环境

目录型 agent 可在 `runtime/agents/<agentKey>/.config/` 放置 Agent 专属覆盖，Agent 自有或技能中心 Skill 可在自身 `.config/` 提供可分发默认值。Platform 在 Catalog 发布前将它们合入 `ru-agents/<agentKey>/.config/`；Skill–Skill 不同内容或结构冲突会隔离该 Agent，Agent `.config` 最后覆盖。完整规则见 [Agent 运行时组装](./Agent运行时组装.md)。

执行 host bash/tool 与 Container Hub session/command 时，平台会计算并冻结：

- `AP_AGENT_CONFIG_HOME`：agent scope 的私有静态配置根；host/terminal 使用实际 `<ru-agents>/<agentKey>/.config`，Container Hub 使用只读挂载后的 `/agent/.config`
- `AP_WORKSPACE_DIR`：Host 使用真实 Workspace（没有 Workspace 时省略），Container Hub 固定为 `/workspace`
- `AP_CHAT_DIR`：Host 使用实际 `AP_RUNTIME_CHATS_DIR/<chatId>`，Container Hub 固定为 `/chat`

Workspace Terminal 只冻结实际 `AP_AGENT_CONFIG_HOME` 与 canonical `AP_WORKSPACE_DIR`，不注入 `AP_CHAT_DIR`。三个变量都由 Platform 保留。长生命周期 Container Hub session 的复用身份包含 environment、canonical Workspace、canonical Chat 和完整 mount fingerprint；Workspace Terminal 的复用身份是 owner boundary、`agentKey` 与 `terminalKey`。

平台不会为 agent 静态配置改写 `XDG_CONFIG_HOME`，也不注入系统配置根。当前 dbx/httpx 会在 agent 中没有同名连接/site 时自行回退 `~/.config/<tool>/`；显式 `--config` 不回退。HTTPX 的 chat secret/state 固定使用 `$AP_CHAT_DIR/.secret/httpx` 与 `$AP_CHAT_DIR/.state/httpx`，HTTPX 不接收 Chat ID，也不会在缺失合法目录时回退 global；敏感内容不得提交。

PROXY/CHANNEL 不再伪造宿主 cwd 或把 Chat 当 Workspace；远程文件引用以带 ticket 的 resource URL 为传输事实源，由接收端物化到自己的 Chat。

CODER 可额外声明顶层 `projectConfig`：

```yaml
projectConfig:
  promptFiles:
    - source: workspace
      path: AGENTS.md
    - source: agent
      path: AGENTS.md
  git:
    expectedBranch: main
```

- `source: workspace` 从 `runtimeConfig.workspaceRoot` 解析后的目录读取
- `source: agent` 从当前 Agent 的 `ru-agents/<agentKey>` 运行目录读取
- `promptFiles` 使用 `source/path` 结构声明

## 当前建议

当前建议：

- 把 `runtime/agents` / `runtime/teams` / `runtime/skills-center` 视为事实源，把 `runtime/ru-agents` 视为可重建且禁止人工编辑的执行目录
- 新增 agent 行为时优先修改 definition 文件，其次再补 `internal/catalog` 与 `internal/engine`
- 若某个字段尚未在 Go 中消费，保持显式报错或显式忽略，避免静默吞掉

## 后续演进原则

- 文件命名尽量与参考仓库保持一致
- 语义清晰优先于实现细节
- 未实现的字段要么明确忽略，要么启动时报错，避免静默吞掉
