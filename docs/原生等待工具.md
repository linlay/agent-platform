# 原生等待工具

`wait` 是 Native Run 内的可中断等待工具，可通过 `preset-tools` 或 Agent 的 `toolConfig.tools` 挂载，通过 `excludeTools` 排除。工具输入统一使用 camelCase。原 `sleep` 定义已移除，不保留别名；ACP 和 BTW / Explain 不开放此工具。

## 输入契约

```json
{
  "offset": "+10m",
  "description": "等待两个独立任务完成",
  "conditions": [
    {"type": "run.terminal", "runId": "run-a"},
    {"type": "run.terminal", "runId": "run-b"}
  ],
  "match": "all"
}
```

- `offset` 或 `base` 至少提供一个；**同时存在时 `offset` 优先**，相对当前时间计算，不把 base 当作 offset 的起点。非法 offset 报错，不回退到 base。
- `offset` 接受可选前导 `+` 和正整数单位组合，例如 `+1H30m`。单位严格区分大小写：`S` 秒、`m` 分钟、`H` 小时、`D` 固定 24 小时。不接受负数、小数、零时长、`M/w/y`；单次最长 24 小时。
- `base` 支持 datetime 的日期、无时区日期时间和 RFC3339 格式，并支持 RFC3339 小数秒。`timezone` 沿用 datetime 的时区解释。只给日期表示该时区当天 00:00:00。过去时间立即完成，结果明确标记 `dateOnly` 和 `deadlineAlreadyPassed`。
- 时间始终是整个等待的上限。事件可选，不在 condition 中混入时间，也不再额外使用 `timeoutMs` 或 `durationMs`。
- 顶层 `description` 每次调用必填（纯时间等待和条件等待均需要），去除首尾空白后为 1～200 个 Unicode 字符。说明正在等待什么及原因，有条件时写明等待目标；缺失、空白或非字符串在开始等待前返回 `invalid_wait_arguments`，不能放进 conditions 项中。
- `conditions` 可选；提供时包含 1～8 项。`match` 默认 `any`，也支持 `all`；没有 conditions 时不能单独传 match。
- `additionalProperties:false`；执行器也校验直接调用。Schema 保持平台的可移植子集，跨字段必填关系由执行器校验。

## 条件

| type | 参数 | 满足语义 |
| --- | --- | --- |
| `run.terminal` | `runId` | 独立 Run 已完成、失败或被中断，且已完成运行时收尾 |
| `file.exists` | `filePath` | 文件系统中该路径已存在 |
| `file.modifiedAfter` | `filePath`, `after` | 修改时间严格晚于 after；after 为 Unix 毫秒 |
| `connector.authorizationTerminal` | `connectorId`, `authorizationId` | 指定授权尝试已成功、失败、取消、过期或因重启中断 |

先读取当前状态，再等待后续状态变化；不存在“开始等以后才算事件”的基线竞态。`all` 保留每项已满足状态。目标失败同样满足 terminal 条件，结果报告状态，不代表目标成功。条件不存在、不可访问或读取失败返回明确工具错误。

当前实现每 250ms 在运行时内部检查未满足条件，不产生模型请求、工具轮次或 shell 进程。事件条件仍是可扩展的窄 provider 接口；文件由 tools 按文件访问策略检查，runops 检查 Run 所有权，app 组合 KBASE 和连接器 provider。

`run.terminal` 复用 run tools 的调用方与 subject 所有权，不允许等待自己。文件只能位于当前已允许读取的作用域；wait 不授予额外文件访问权限。KBASE 目标限当前 Agent，连接器目标必须由当前 Agent 挂载。

连接器 `authorizationId` 对应已有 `sessionId`，不会混淆后续授权尝试；终态不保存授权 URL、凭据或上游诊断正文。独立 Run 状态及其 origin 保存在 `.state/run-status`，供完成保留期结束及重启后查询。重启丢失执行者的运行中目标返回 interrupted。

## 唤醒与结果

结果中的 `reason` 为：

- `elapsed`：纯时间等待到期。
- `event`：事件条件满足。
- `timeout`：事件仍未满足但时间上限已到。
- `steered`：根 Run 接受了新的文字或附件输入；附带 `continued: true` 时表示空白 steer，用户只要求立即继续。
- `canceled`：Run 或调用 context 取消。
- `failed`：事件目标校验或检查失败。

结果包含 `startedAt/deadlineAt/endedAt/elapsedMs`、`resolvedTimezone`、条件状态和 `matchedConditionIndexes`，以及 `waitStats.count/totalWaitMs`。没有目标 Run 正文，需另调 `chat_get_status` 获取。每次调用只有一个最终 `tool.result`。

wait 不消费 steer。模型循环仍在同一个 Run 中处理输入；是否再次等待由模型决定。子任务不能消费、关闭或替换父 Run 的 steer 通道；根输入不会变成子任务模型输入。wait 是串行屏障，同批前序工具先完成、后序工具在 wait 结束后继续，保持普通工具批次语义。

### 提前结束

没有专用的跳过接口，统一走 `/api/steer`：

- **带内容的 steer**（文字或附件）：照常入队、发布 `request.steer` 并持久化；等待以 `steered` 结束，模型在同一 Run 中读到这条用户消息。
- **空白 steer**（无文字、无引用）：表示“立即继续”，是一条正文为空的普通 steer，沿用全部既有规则：入 steer 队列、发布 `request.steer`（`message` 为空）、写入一条 JSONL steer 行，由模型循环在工具结果之后消费。公开 `message` 保持为空，模型输入补充英文指令 `Proceed now with the next step; do not wait any longer.`，历史重建时生成同一句。它不复用空 query 的“接着做”指令，否则模型会把“继续”理解成继续等。等待以 `reason: "steered"`、`continued: true` 结束，结果同时带 `note` 明确告知模型用户选择停止等待、不要补等剩余时间。
- 空白 steer 不是 wait 专属：任何接受 steer 的活动 Run 都接受它，含义统一为“继续”，与空 query 对齐。wait 只是因为监听 steer 通知而提前结束；其他工具执行期间收到的空白 steer 与普通 steer 一样，等当前工具结束后由模型循环消费。Run 已结束或不再接受 steer 时照常返回未接受。

两者都表示用户要求继续，不代表等待的事件已经完成。空白 steer 沿用 steer 的认证、owner、transport、device 和 lane 校验，不使用任何特殊 `steerId`。JSONL 的 steer 行因此允许 `message` 为空且没有引用；旧版本 Platform 的 schema 校验会拒绝这种行，含空白 steer 的 Chat 不能回退到旧版本读取。

steer 只作用于根 Run 的等待；子任务和 Team 成员内的等待不被提前结束，只能到期、条件满足或随 Run 取消结束。

## 预算

`budget.timeout` 是执行时间预算，wait 的耗时计入 `BudgetPaused`；串行异步工具结果合并会将该计数带回真实模型循环。每次 wait 仍计一次工具调用，并返回累计等待统计。

`budget.lifetimeTimeout` 为包含等待的 Run 生命周期上限，单位秒；默认 `max(86400, timeout)`，在创建 Run 时冻结。部署配置 `configs/runtime.yml` 使用 `budget.lifetime-timeout`（同配置解析也接受 camelCase）。生命周期计时器在 wait 期间继续工作，重启不重置期限。超出剩余生命周期返回 `wait_exceeds_run_lifetime` 并提示使用 automation。wait 不套用普通工具的单次超时和重试策略。

子任务等待暂停其自身执行预算，不暂停父 Run 在 `agent_invoke` 上的执行耗时。

## 持久化与恢复

复用现有 awaiting 存储、claim 和续跑链路。`awaiting.mode=wait` 是内部恢复记录，不作为用户表单显示，也不通过 `/api/submit` 回答。等待开始前保存工具调用上下文、绝对期限、条件快照、执行预算和计数；条件更新也持久化。恢复时先恢复等待，唤醒后持久化结果并在原 runId 中继续模型循环。

可恢复边界：普通 Native 根 Run；子任务和 Team 等待重启后明确失败。非空 `run.env` 同样不安全恢复；凭据值和一次性授权不写入检查点，恢复后后续工具按既有机制重新授权。附件 steer 使用恢复后的会话能力进行验证。

恢复发生在同批工具中间时，wait 之后尚未启动的调用得到 `wait_restart_unstarted`、`executed:false` 结果，模型决定是否重新发起；若前序调用缺少持久化结果，则报告执行状态未知，不能声称未执行。正常运行期间的 steer 不改变同批剩余调用规则。

## WebClient 时间线

- `tool.wait` 表示开始，`tool.wait.update` 更新条件状态，`tool.result` 唯一收口。
- 客户端根据绝对 deadline 本地倒计时；纯时间显示“剩余”，事件等待显示“最多再等”，到 0 后显示“正在确认完成”，不自行完成工具。
- 卡片只展示本次调用的 description（实时事件优先，其次调用参数；都没有则不显示说明）、条件满足数量和“立即继续”。“立即继续”发送空白 steer，不经过输入框；客户端对无内容的 `request.steer` 不渲染用户消息；等待中的输入框发送是带内容的 steer。结束后按结果 `reason`（及 `continued`）显示结束原因。
- attach 除正常事件回放外补当前等待快照。快照 `seq:0`、`attachSnapshot:true`，不占 Run 日志序号、不修改续传 cursor。等待完成后不再补发。
- `tool.wait` 过程状态不进入冷回放、导出或 transcript；内部 awaiting 检查点也不显示。历史由工具调用和最终结果表达，Run 结束后停止计时。
