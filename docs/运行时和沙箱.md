# 运行时和沙箱

## 当前状态

运行时目录由 `AP_RUNTIME_DIR` 和目录环境变量白名单决定，其余子目录固定从运行根派生。Platform 在 Catalog 发布前把可编辑的 agents、Agent 自有 Skill 和 skills-center 组装到 `ru-agents/`，执行侧只读取该生成目录。沙箱能力通过 Container Hub 接入；只要 agent 声明 `runtimeConfig.environmentId`，运行时就会为该 agent 注入 sandbox context，并在工具执行时使用 Container Hub session。

宿主机侧工具和 sandbox 工具有明确边界：host bash / FileTools 访问宿主机受本地权限配置约束，sandbox bash 通过 Container Hub 在远端或容器环境执行。

知识库由 Go runtime 以 argv 调用受管 KBX CLI，抽取和索引归 KBX。Go 主程序仍以 `CGO_ENABLED=0` 构建，KBX 不属于 Container Hub sandbox tool。

## 核心流程

```text
agents + skills-center
  -> ru-agents/<agentKey>
agent.yml runtimeConfig
  -> environmentId / workspaceRoot / env / hostAccess / sandboxMounts
  -> session builder
  -> static env + ordinary native root-run process-local Scope
  -> Host/Container command snapshot
```

Container Hub 使用 `dual-root-v2`：双根基础挂载固定为 canonical Host Workspace → `/workspace`（`rw`）与 canonical Host Chat → `/chat`（`rw`），容器 cwd 固定为 `/workspace`。当 ChatsRoot 位于 Workspace 内时，Platform 下发 `/workspace/<ChatsRoot-relative>` mask；Hub 必须先挂 Workspace，再用 tmpfs/opaque mount 遮蔽该路径，最后挂当前 Chat。这样 Chat 只从 `/chat` 可见。此外按既有职责挂载 `/root`、`/skills`、`/pan`、`/agent`、`/owner`、`/memory`；其中 `/agent` 与 `/skills` 来自 `ru-agents/<agentKey>`，`/skills` 仅在 `run/agent` 级别默认挂载。`/workspace`、`/chat`、mask 及其子路径是保留目标，`runtimeConfig.sandboxMounts` 不能覆盖。

## 配置与接口

- `configs/runtime.yml` 的 `container-hub` 节：Container Hub 运行时行为主入口；代码默认值仅作为兜底。
- `AP_RUNTIME_DIR`：runtime 总目录。
- `AP_RUNTIME_REGISTRIES_DIR`：provider / model registry 根目录。
- `AP_RUNTIME_CHATS_DIR`：chat 与上传资源目录。
- `AP_RUNTIME_MEMORY_DIR`：memory 数据目录。
- `AP_RUNTIME_PAN_DIR`：pan 目录映射。
- `AP_RUNTIME_STATE_DIR`：Platform 通用持久化运行状态根，留空时使用 `<AP_RUNTIME_DIR>/.state`。
- 其余 runtime 子目录固定从 `AP_RUNTIME_DIR` 派生；`configs/runtime.yml` 不再接受 `paths` 配置，出现即报错。
- `AP_CONTAINER_HUB_BASE_URL`：非空即启用 Container Hub。
- `container-hub.default-environment-id`：默认 environment id。
- `runtimeConfig.workspaceRoot`：Agent 的 host Workspace，只接受可展开为绝对路径的现存目录；`@chat` 已删除。普通 Workspace 可包含 ChatsRoot，文件系统根 `/` 合法；不能与 ChatsRoot 相等或位于 ChatsRoot 内。
- `runtimeConfig.hostAccess`：host-side `bash/file_*` 额外读写根，支持 `@temp`，不影响 sandbox mounts。
- `runtimeConfig.env`：字面量字符串 map，注入 host bash 或 Container Hub。
- 普通 native root Run 的动态环境通过 `run_env` 的 `set/unset/update` 管理，不写入 Agent 配置。
- `runtimeConfig.sandboxMounts`：沙箱挂载扩展。

## 连接器运行环境

外部 connector 原包安装在 runtime/connectors-center；builtin 原包随 Platform 分发：原生平台／网页控制连接器内嵌于 `internal/resources/connectors`，dbx/httpx 完整包来自已校验的 build cache。两者按 Agent 挂载组装到 runtime/ru-connectors/<id>/<contentDigest>，授权状态独立放在 runtime/.state/connectors。Agent 挂载自动增加运行包的 bin PATH 并导入随包技能元数据；Host Bash 与 Terminal 使用当前 Agent 的包目录，Container 只读挂载所选 `/connectors/<id>` 并使用容器 PATH。bin/libs 不加入 PATH，安装包本身可以携带它。容器需要匹配平台的程序，平台不跨 OS/架构转换二进制。连接器技能不进入 mustUseSkills；完整规则见 [连接器](连接器.md)。

## KBX 知识库执行

Platform worker 负责目录监听、增量路径批次、周期全量对账、刷新回执和重启恢复；KBX CLI 负责抽取、索引、事务和写锁，不运行 kbx watch。CLI 仅从受管 builtin 目录解析，使用私有配置及受限输出，不通过 shell；完整生命周期见 [KBX 接入](KBX接入.md)。

Poppler 的 pdftotext launcher 与隔离原生 runtime 继续随包提供，用于 KBX PDF 抽取及 Agent Bash 直接调用。普通安装不要求用户另装 Rust、Python 或数据库服务。

`/healthz` 探测 KBX 维护能力。专用 KBASE capability 为 required，失败返回 503；只有普通 Agent 的 optional capability 时返回 200 并报告 degraded。公开 JSON 仍使用 data.kbase.sidecar，内部类型为 knowledge.RuntimeState；该字段保留兼容名称。

sync-local-builtins 准备并校验本机缓存，make run/build/release 只消费缓存，不重新构建 builtin。KBX 目前支持 macOS AMD64/ARM64、Windows AMD64；Linux 没有受支持的 KBX 发行目标，因此不能生成完整 Linux/Docker 包。发布规则见 [版本化打包方案](版本化打包方案.md)。

## 约束与注意事项

- `runtimeConfig.env` 不支持 `${VAR}` 展开。
- 动态 env 不调用 `os.Setenv`；每个 Host/Container command 在启动前获取独立 snapshot，已经启动的进程不会被追溯更新。
- env key 不能为空，不能包含空白字符或 `=`。
- `AP_AGENT_CONFIG_HOME`、`AP_WORKSPACE_DIR`、`AP_CHAT_DIR` 与 `AP_ACCESS_TOKEN` 是平台保留变量，agent、skill 和调用级 env 均不能声明或覆盖。
- catalog API 不回显 `runtimeConfig.env`。
- `sandbox` 不再属于 `contextConfig.tags`，由 `runtimeConfig.environmentId` 控制。

Workspace 与 Chat 是语义双根，没有目录回退。canonical 路径按“当前 Chat → 其他 Chat → Workspace（排除整个 ChatsRoot）→ external”分类。相对路径和 `@workspace` 永远从 Workspace 解析；若解析后进入 ChatsRoot，返回 `path_crosses_chat_root`，当前 Chat 必须使用 `@chat`。无 Workspace 时相对路径返回 `workspace_unavailable`。所有 CODER、所有声明 `runtimeConfig.environmentId` 的 Agent和所有 enabled KBASE 都必须有 Workspace；无 sandbox 的 GENERAL、PLAN-EXECUTE、PROXY、CHANNEL 可以没有 Workspace。KBASE 额外拒绝文件系统根以及与 ChatsRoot 任一方向的重叠。

Platform 在 host bash/tool 与 Container Hub session/command 启动时注入三个保留变量。`AP_AGENT_CONFIG_HOME` 在 Host 为 `<ru-agents>/<agentKey>/.config`、在 Container 为 `/agent/.config`；`AP_WORKSPACE_DIR` 在 Host 为真实 Workspace（没有时省略）、在 Container 为 `/workspace`；`AP_CHAT_DIR` 在 Host 为 `<chatsDir>/<chatId>`、在 Container 为 `/chat`。Workspace Terminal 只注入 canonical `AP_AGENT_CONFIG_HOME` 与 `AP_WORKSPACE_DIR`，不注入 `AP_CHAT_DIR`；其复用身份是 owner boundary、`agentKey` 与 `terminalKey`。

Container session base/fingerprint 只包含静态 env 与 reserved context；动态 revision/value 不进入 reuse key。每次 command 才叠加当前动态 snapshot，因而复用 session 后的新 command 可看到 set/unset，后台或已启动进程不更新。子 Agent、Team、独立 root run、Workspace Terminal、MCP stdio/HTTP、ACP、Proxy、Channel、LSP、KBX CLI 与其他长期服务明确不继承动态 Scope。完整矩阵见 [Platform 控制工具设计与实现](./Platform控制工具设计.md)。

`AP_ACCESS_TOKEN` 仅供经验证的单条直接 oneid-token CLI 子进程及对应 MCP 身份链路使用，不进入普通 Host Shell、Terminal 或 Container。CLI 启动前读取有效 identity 文件，stdio MCP 检测身份轮换并重建进程，HTTP MCP 按请求生成 Bearer Header；已启动的 CLI 不受文件变化影响。默认路径和覆盖规则见 [配置化说明](配置化说明.md#env-allowlist)。工具输出不做 token 脱敏，获得凭据的连接器子进程属于可信执行面。

上传和当前 Chat 引用在 Host 使用 Chat 绝对路径，在 Container 使用 `/chat/<relative>`。远程 PROXY/CHANNEL/ACP adapter 使用带 ticket 的 resource URL，由接收端落入自己的 Chat。Artifact 可从 Workspace 或 Chat 读取，但最终统一发布到 Chat 的 `artifacts/`；跨 Agent workspace 文件先复制到 Chat 再交接。

发布前运行 `make audit-workspace-chat`。该命令只读检查无 Workspace 的 CODER/sandbox/KBASE、`workspaceRoot:@chat`、旧 `kbaseConfig.source`、非法 Workspace/Chats 关系、旧 `working-directory` 与保留挂载冲突；合法但无 Workspace 且挂载路径工具的普通 Agent 会得到非阻断提示，列出必须显式传入的 Bash `cwd`、glob/grep `path` 和语义根路径。
- `configs/` 目录固定为项目根下 `configs/`。

## 技能脚本执行边界

已配置普通 Skill 和本次 `mustUseSkills` 选中 Skill 的 `scripts/**` 使用本 Run 内存执行凭据，Host 在启动前复验 canonical 路径和内容 SHA-256。Container 仅映射这些授权技能的实际 Host–guest 目录，在实际容器解析入口并核对摘要；解析或摘要校验失败时回到既有审批策略。整个 `/skills-center` 的只读挂载不授予未选中技能入口豁免。凭据不写文件或数据库，未引入额外运行目录或挂载。Host 不隔离脚本内部文件访问，macOS symlink 与 Windows junction 均不能放宽目录归属检查；Windows 真机与真实 Container 验证需在对应运行环境执行。详细边界见 [工具目录权限](工具目录权限.md#技能脚本入口执行凭据)。
