# 知识库（KBases）

知识库服务统一拥有共享库的配置、索引、自动维护和状态。Agent 只绑定一个 libraryId；库内可有多个 collection。WebClient `/kbases` 可管理来源、过滤规则、索引状态和召回测试；新建项目可选库或从目录同时创建库和 Agent。

## 存储和配置

```text
kbases/<id>/library.yml       # 期望配置
ru-kbases/<id>/state.json     # 状态和已应用来源指纹
ru-kbases/<id>/index.sqlite   # KBX 与配套持久数据
ru-kbases/.worker.lock        # 部署调度锁
```

没有 libraries 中间层；`libraries` 保留不可作为 ID。ID 接受 1–64 位小写 ASCII 字母、数字、下划线或连字符，字母数字开头。非库运行目录用点前缀。ru-kbases 必须跨重启保留，不随 ru-agents 清空，也不能按 ru-* 批量清理。

```yaml
name: "研发知识"
description: "AI 建设与研发述职资料"
collections:
  - name: "ai"
    sourcePath: "/Users/linlay/Documents/知识库测试用文档/AI建设文档"
    description: "现行技术规范"
    editable: true
    include:
      - "**/*.md"
      - "**/*.pdf"
      - "**/*.docx"
      - "**/*.pptx"
    exclude:
      - "private/**"
    chunk:
      unit: "chars"
      maxChars: 3600
      overlapChars: 540
  - name: "research"
    sourcePath: "/Users/linlay/Documents/知识库测试用文档/研发中心各条线述职"
```

省略 include 使用七种默认文本/文档扩展名；显式空 include 拒绝。省略 exclude 使用默认值，显式空数组只关闭自定义默认排除，不关闭 KBX 内置安全排除。chunk 按平台默认 → 库级 chunk → collection.chunk 逐字段覆盖，省略继承，显式 overlapChars: 0 保留零值。默认仅有一处代码事实源 `knowledge.DefaultChunkConfig()`：chars/window/3600/540；策略支持 window、regex、structural，要求正数 maxChars 和 0 <= overlapChars < maxChars。旧 token 单位不再接受。名称/sourcePath/include/exclude/有效 chunk、库级 textEncoding 及部署强制排除目录进入来源指纹，库展示名称、库与 collection 描述、collection editable 及 collection 顺序不改变指纹。更改切块执行全量对账重新发布 chunk；Agent topK 和候选预算不改变指纹。

来源目录在加载与维护前检查 canonical 身份，与 ChatsRoot 分离，禁止读取 StateDir/库配置/运行数据；来源中的 runtime/state 子目录排除。配置按请求读盘，单库错误隔离，手写 YAML 错误显示诊断。仅含 library.example.yml 的模板目录不进入管理操作。来源离线但已应用指纹一致时仍可读取索引，原文件下载需要来源在线。

## Collection 说明与编辑授权

`collections[].description` 是可选文本，最多 4000 字节；`editable` 是严格 boolean，缺省 false。POST/PUT 与 GET 返回同一字段，WebClient 提供说明输入框和开关。保存完整 collections 数组时保留 include/exclude/chunk；省略 collections 保留现有集合。

专用 KBASE 的 Host Run 启动时按冻结 Agent 的 libraryId 读取库配置，将 editable collection 的现存 canonical 目录冻结到 ScopedFilePolicy，并在提示词列出名称、目录、说明和 editable。Workspace 仍独立决定 project 身份和相对路径。运行中的授权不随库修改扩张或撤销，下次 Run 使用新配置；知识检索仍逐次检查当前库范围。普通 GENERAL/CODER 绑定相同库不获得这些目录权限。容器不自动挂载或授予 Host collection 权限。

编辑范围为 Workspace 与 editable collection 的并集，必须开启 editingMode；readonly、平台保护路径和管理员 block 优先。editable=false 只是不新增授权，不撤销原有 Workspace 或其他通用权限。详见 [KBASE 编辑模式](KBASE编辑模式.md)。

指纹按来源与向量合同分开，Run/查询元数据不参与。来源指纹采用显式字段投影；向量维护接口独立于来源扫描，只允许修改向量，失败/中断保留已提交全文并标记 degraded。LibraryEngine 根据有效 embedding 模型合同生成向量指纹；仅模型变化时执行全库 embed --force，不扫描来源、不重划 chunk。retrieval、reranker、queryExpansion 与 defaultQuery 属于查询设置，不参与这两种指纹；graph/metadata 等后续字段仍严格拒绝。

## 调度、状态和删除

知识库服务自动监听：500ms 合并、五分钟全量对账、启动及中断后重新对账、文件增量更新，每库一个维护任务，全局最多两个。查询与刷新不持有跨库全局锁。手工刷新调用同一维护通路，更新期间编辑/删除返回 409。最长维护 35 分钟。详细 CLI 协议见 [KBX 接入](KBX接入.md)。

普通更新保留读取并标记 stale/indexing，读到的是 KBX 已提交内容，不是固定旧快照。全文已完整而 embedding 失败时可读 degraded；未知 partial 或中断不可读，自动重试。来源、集合、过滤/切块变化立即撤销旧范围读取。刷新只写 state.json，不覆盖 library.yml；外部修改会使旧任务的完成指纹与当前配置不符，从而拒绝读取并重新对账。

删除有引用库返回 409 和引用 Agent 列表；引用关系由 App 注入，`internal/kbases` 不 import catalog。管理端 Agent 保存与删库共享 mutation 边界；外部编辑器/Bash 的并发写入不受该边界保护，Run/工具仍逐次重新核验。显式删除移除配置和运行数据，但保留源文件；删除前原子隔离为隐藏 .deleted-* 目录，启动重试清理生成的残留。手工删除 YAML 保留孤儿索引并在列表提示，模板目录受保护。创建回滚只处理本次新建资源。

这是硬切升级：旧 Agent 配置字段和 AP_RUNTIME_KBASE_DIR 明确拒绝。旧 ru-kbases/libraries 布局与旧 Agent 索引目录 runtime/kbase 完全忽略，不进行旧布局检查、不加载、不迁移，也不移动或删除数据。知识库服务按 kbases/<id>/library.yml 配置自动在 ru-kbases/<id>/ 生成索引；需要原有知识时，从来源重建共享库并配置 libraryId 绑定。

## 检索与来源

管理台仍支持 query/search/vsearch/gsearch、collection 筛选和 200 行正文预览。Agent 查询使用完整 Manager 层，保留过滤、minScore、图证据和证据分页；不会复用管理台的薄封装。路径为 collection/relativePath，source ID 包含 libraryId。聊天来源通过专用的 /api/chat/sources/read 和 /file 入口核验已发布引用与当前库绑定，独立于 Workspace 文件权限。

图谱自动构建、上传和知识包导入导出尚未接入。

## 库级配置与模型

`library.yml` 支持顶层 `chunk`、`textEncoding` 和 `models.embedding`。textEncoding 是 WHATWG 回退编码标签（如 gbk、windows-1252），BOM 和合法 UTF-8 优先；非法标签及 replacement 拒绝。有效切块或编码变化撤销旧范围读取，并由 update 重新抽取、发布分块。字段示例见 [library.example.yml](../configs/library.example.yml)。

`models.embedding.modelKey` 选择共享模型 registry 的 embedding 模型，`prompt` 支持 raw、qwen3、embeddinggemma。省略整个 embedding 段继承 `configs/runtime.yml → kbx.embedding`；省略 prompt 继承 runtime 默认。Agent 只能绑定库，不能覆盖模型。库配置不存储 URL 或密钥；模型键缺失、类型错误等执行错误在维护或向量查询时报告，纯全文不依赖模型解析。

POST/PUT 接受上述库级字段并拒绝未知字段，GET 返回原始稀疏声明。PUT 省略 chunk/models/textEncoding 保留原值；`chunk: {}`、`models: {}`、`textEncoding: ""` 分别恢复默认/继承。collection 仍通过完整数组保存，逐字段 chunk 不应补齐后回写，否则会固定继承值。WebClient 目前提供 collection 元数据表单，库级高级配置通过 YAML 或管理 API 修改；表单保留 defaultQuery，避免编辑说明时重置默认检索范围。

Platform 启动校验全局默认并生成 `<StateDir>/kbx/index.yml`；执行时在该目录的 `libraries/<数据库路径摘要>/` 下生成 0600 的每次调用私有配置，包含该库的模型、切块和编码，通过 `--config` 与隔离的 `KBX_CONFIG_DIR` 传给 KBX。子进程结束删除快照，避免并发调用覆盖或积累逐次调用的凭据副本；不修改 KBX，也不继承用户 KBX 配置。

模型键、有效 endpoint/modelId/dimension/prompt 进入向量指纹，密钥、超时和 batchSize 不进入。模型合同变更只重建全库向量，失败/中断仍保留全文；`vectorsPending` 为 true 时 query 使用全文，严格 vsearch 报未就绪。常规内容更新先完成全部 collection 的全文 update，再执行全库 embed，Platform 检测到模型合同变化或 KBX 报合同不兼容时使用全库 `embed --force`；SESSION_LIMIT 后续跑不重复 force。源目录变动、内容事件和重启对账仍按来源维护规则执行。最长维护 35 分钟。

未选择 embedding 时 query 使用全文；重排、查询扩展见下节；图谱抽取模型仍未接入。本机受管 KBX 与 HTTP fixture 已验证三种策略、编码变更重新抽取、逐库模型隔离、仅模型变化不扫描来源、模型失败时全文可读和向量恢复；这些测试不验证真实模型的语义质量或目标部署延迟。

## 检索默认值、可选模型和默认集合

库级 retrieval 支持 topK、candidateFloor、candidateMultiplier、candidateMax、minScore、recencyWeight、recencyHalfLifeDays、rerank、queryExpansion。按平台默认 → 库默认 → Agent 显式字段 → 单次调用合并；省略 Agent 字段继承库配置，显式 minScore/recencyWeight: 0 与 rerank/queryExpansion: false 保留。Agent 未绑定库时的原有默认不变；最终合并仍检查候选预算关系。PUT 省略 retrieval 保留原值，`retrieval: {}` 恢复平台默认。

单次 kbase_search 使用 limit、candidateLimit、minScore、recencyWeight、recencyHalfLifeDays、rerank 和 queryExpansion 覆盖查询；candidateLimit 仍不能超过合并后的 candidateMax（不低于本次 limit）。库和 Agent 默认按方法适用性应用：gsearch 不接收文本排序或模型开关，search 不解析任何模型，rerank 仅支持 query，queryExpansion 支持 query/vsearch。不适用的显式调用参数拒绝。管理接口搜索省略 limit 时同样使用库 topK。

`models.reranker.modelKey` 引用共享 registry 的 `type: reranker` 模型，modelId、provider、timeout 沿用 registry 字段，额外必填 `reranker.endpointPath`，例如 `/v1/rerank`（服务若使用 `/v2/rerank` 应明确填写）。KBX 发出 query/documents/top_n 请求并读取 results[index,relevance_score]，不能把普通聊天模型冒充 reranker。`models.queryExpansion.modelKey` 引用 `type: chat`、`protocol: OPENAI` 的 Chat Completions 模型，使用 provider 的 OPENAI endpoint；不支持 ANTHROPIC、OPENAI_RESPONSES、ACP_PASSTHROUGH、自定义 headers 或 compat 请求配置。

已配置模型且开关省略时启用；显式 false 关闭，显式 true 而未配置模型则报错。检索模型仅注入 query/vsearch 的私有调用配置，全文 search、索引 update/embed、files/read 不解析它们；模型声明变化不触发扫描、切块或向量重建。HTTP 模型调用失败由 KBX 保留原查询/原排序继续，结果 degraded=true，Agent 的 optionalUnavailable 标明 query_expansion/reranker；错误模型键、类型或协议属于配置错误，直接报告。严格 vsearch 仍要求可用向量，不回退全文。

collection.defaultQuery 缺省 true，false 仍索引并可浏览/回读。维护时同步 KBX collection include/exclude；每次查询也按当前配置生成显式 collection 参数，因此修改后下次查询即生效，无需等待维护。kbase_search 的 collections 或管理知识库服务显式选择可查询默认排除的集合，但不能跨绑定库。过滤条件继续与已选范围取交集；全部默认 false 返回空结果，不让空 collection 参数退回全库。defaultQuery 不是文件权限，不改变 KBASE editing 授权。

真实受管 KBX + 本机 HTTP fixture 已验证模型调用、关闭时零调用、故障保留全文、默认排除与范围隔离；成功结果也可能命中 KBX 缓存，扩展向量可增加 embedding 请求，因此不能承诺每次只增加固定次数调用。已使用部署现有模型完成合成小样本的扩展、延迟和故障实测，见 [KBX 接入实测记录](KBX接入.md#2026-10-10-本机真实模型实测)：扩展未改善这组样本的命中，并增加未缓存查询耗时；真实重排因缺少模型配置仍未验证。业务评测集与生产负载尚未覆盖，本文不提供生产延迟承诺。

## HTTP 契约

接口沿用 Platform 现有 HTTP 鉴权和 `{code,msg,data}` 包裹，知识库为部署级资源。

| 方法与路径 | 用途 |
| --- | --- |
| GET /api/admin/kbases | 定义数组，包含单库错误与 `orphaned` 运行数据诊断 |
| POST /api/admin/kbases | `{name,description,collections:[{name,sourcePath,description?,editable?}]}` 创建 |
| GET /api/admin/kbases/{id} | 单库定义、baseRevision、状态与最近错误；坏配置返回可展示诊断 |
| PUT /api/admin/kbases/{id} | `{name,description,collections?,baseRevision}` 编辑；必传当前配置修订，省略集合及库级高级字段保留当前值，名称描述按请求覆盖 |
| DELETE /api/admin/kbases/{id}?baseRevision=… | 必传当前配置修订；有绑定 Agent 时 409，保留源文件 |
| POST /api/admin/kbases/{id}/refresh | 启动后台更新，返回 indexing 定义 |
| GET /api/admin/kbases/{id}/status | 库管理状态；首次索引前可查，就绪后附加 KBX statistics/statsAvailable |
| GET /api/admin/kbases/{id}/files | KBX 文档目录 |
| POST /api/admin/kbases/{id}/search | `{query,limit,collections?,method?}` 召回，默认数量 10、method=query |
| GET /api/admin/kbases/{id}/read?ref=… | 按 `kbx://<collection>/<relativePath>` 读取正文 |

不存在返回 404，索引期间或配置修订冲突返回 409，错误方法返回 405，参数或执行失败返回 400，知识库服务未装配返回 503。查询和读取有 30 秒超时。HTTP 更新/删除调用方升级时必须先 GET 并传 baseRevision；旧无修订调用会被拒绝。修订是 library.yml 的内容 SHA-256，后台索引状态变化不改变它。

## 平台控制工具

显式挂载 builtin.platform-control 后，普通 Native root Run 可用 `kbase_library_query`（list/get/status/validate）和 `kbase_library_manage`（create/update/delete），直接调用 Service，不经过 HTTP 或 token。`catalog_query resourceTypes` 的 relatedCapabilities 提供独立库入口；库不是 catalog_manage 的资源类型。规划 Run 可查询和校验，不可管理。

工具 update 为 patch 合并：省略字段保留、对象逐字段合并、数组整体替换、null 删除可选字段，例如 `{"models":{"reranker":null}}` 只移除重排模型；合并后的完整定义仍需通过校验，name、collections 等必填项不可移除。update/delete 必须提供 get 返回的 baseRevision。create 在管理锁内重新比较 canonical 来源目录、过滤条件和配置，相同则返回真实已有库 ID，不按名称去重。管理操作与 Agent 保存/删库共用 Agent mutation 边界，避免绑定与引用检查竞态。

工具按调用标识或同 Run requestId 保存开始/完成收据。完全相同的已完成请求返回原结果，参数冲突拒绝；完成收据保留 30 天，worker 至多每小时清理一次过期完成项。未知或中断的 started 收据不自动清理、不自动重放。忙库在准备阶段拒绝，避免消耗审批；执行前再次遇到库忙、修订冲突、approval_stale 等确定尚未写入的拒绝，会移除开始收据并返回原错误。同一 requestId 可在原因解决后重试，修订冲突须重新 get、更新 baseRevision 并取得新审批。写入可能开始后的失败仍保留未知结果，旧版遗留 started 也不能直接推断为未写入。

新建库、删除库，以及改变 canonical 来源目录、实际 include/exclude 或 editable 的更新，三档始终需要人工确认；缩小范围或关闭 editable 也算变化。保持这些授权不变的更新在 default 进入 Platform review，auto_approve/full_access 可按同一精确候选自动审批并审计。等价 create 复用不新增授权，无需 mutation 审批。审批明确展示来源目录、过滤、editable 及前后配置/修订。执行前重新校验；改变来源、过滤或 editable 不复用旧审批。StateDir 和部署配置的 identity 文件及其后代、包含这些路径的来源目录在建库、改库与加载时硬拒绝，三档均不进入可放宽审批，exclude 也不能豁免。目录内部符号链接不纳入 KBX 路径维护，原文回读也拒绝符号链接。

创建知识库 Agent 的完成条件是：库已创建/复用，Agent 绑定返回的 libraryId，库索引状态已核实。Workspace 不是来源，首个 Chat 不会自动建库或启动首次索引；服务负责自动维护。管理状态与当前 Agent 的 `kbase_status` 分别查询。工具手册见 [knowledge-libraries.md](../internal/resources/connectors/builtin.platform-control/skills/platform-control/references/knowledge-libraries.md)，缺少工具时应报告流程未完成，不经 Shell/本机 HTTP/.env 凭据绕行。

等价库复用与 Agent 绑定是两次独立检查。`catalog_manage.apply` 新增或切换 libraryId 到含 editable collection 的库时，三档均需人工确认，GENERAL/CODER 新增这类绑定同样受限；已有 Agent 保持绑定但改为原生 KBASE mode 时，仅目标库含 editable collection 才强制人工。审批展示并绑定真实 libraryId、库配置修订、canonical 来源目录及实际过滤/编辑设置，发布前复验；只读库在审批后变为 editable 会使旧自动审批失效，索引状态变化不影响修订。只读库绑定及保持只读绑定切换为原生 KBASE、原绑定不变的普通元数据编辑及 prompt 文件修改仍按原 catalog 策略，在 auto_approve/full_access 下允许自动审批。确认绑定后，Host KBASE 仍需用户显式开启 editing Run 才获得 collection 写权限。

## 管理能力升级注意事项

本次管理契约需要 Platform 与管理客户端同批交付。HTTP PUT 必须提交编辑开始时读取的 baseRevision；DELETE 必须在 query 提交确认删除时冻结的 baseRevision，不能在确认后自动读取最新修订来覆盖并发变更。`/status` 的 data 为库级状态对象，KBX 统计移到可选的 statistics，首次索引前 statsAvailable 为 false。agent-webclient 的知识库编辑、删除和统计读取已按这些字段适配；Desktop 的知识库页面嵌入该 WebClient，须随新版 WebClient bundle 发布。其他调用方也需升级，旧无修订请求会返回 400。

升级前检查存量 Native KBASE 的 libraryId 绑定；缺失绑定的定义将加载失败，需要先创建或复用真实库，再保留原 Agent 配置补入返回的 ID。GENERAL/CODER 未绑定仍可用。已绑定库的定义损坏时，Agent 创建、编辑、改名和改模型入口都会拒绝保存，并提示先修复库定义或重新绑定有效库；库暂未索引就绪不影响此存在性校验。

来源包含或重叠有效 StateDir、外置 identity 文件的存量定义也会变为无效；来源位于库配置或运行数据目录内继续拒绝。比如把整个用户主目录作为来源而它包含这些受保护路径，即使配置 exclude 仍会被拒绝。升级前应把来源缩小到所需的具体文档目录，重新核对过滤条件及 editable；范围变化按新建同等审批。加载时不会替用户自动改写来源或迁移索引。

旧版遗留的 started 回执继续按结果未知处理，不会自动清理或重放。部署管理员应先核对库定义、索引状态和审计记录：已经提交的操作直接报告实际结果，确认未提交的操作重新审批并使用新请求标识，无法确定的继续保留未知状态。不能直接删除回执并盲目重试。

## 验证

`internal/kbases` 测试覆盖多集合持久化、目录/名称校验、配置/运行分离、坏配置隔离、手工编辑快照、孤儿目录与运行数据重建、集合范围、删除保留源文件、并发更新拒绝、路径隔离和中断恢复；审计回归覆盖模板入口保护、离线读取与路径改向、失败刷新禁读、坏状态恢复、删除隔离、创建回滚及 YAML/目录 ID 诊断。Server 测试覆盖单/多集合 CRUD、模板入口 404 与 HTTP 错误。`KBX_KBASES_TEST_BIN=<受管 bin 目录> go test ./internal/kbx -run TestLibrary -count=1` 在临时库验证首次建库、再次更新、跨集合全文/综合召回、正文读取、文档更新与删除同步，以及本机确定性 embedding fixture 的多集合向量构建和范围过滤。`TestLibraryRealSplitStorageLifecycle` 通过真实受管 KBX 验证分离目录建库、检索、删除运行根后重建、真实来源离线后的检索和正文读取，以及删除保留 source。该 fixture 不向外部模型发送用户文档，不代表真实语义质量；完整图谱的查询质量尚未做目标环境验证。

模型注册表的 `embedding.batchSize` 可限制每次向量 HTTP 请求的文本条数，Platform 将其写入全局 KBX 配置的 `models.embedding.batch_size`。省略或为 0 时沿用 KBX 默认值；负数拒绝。接口的批量上限应按所用服务配置，例如本地 text-embedding-v4 接口实测返回过 20 条和 10 条两种限制，部署选用更严格的 10 条。该值不改变源文档或分块策略。

## 召回分数

知识库搜索结果 `score` 表示原始查询与 chunk 的向量相似度，`scoreType` 为 `vector_similarity`；没有对应向量评分时为 `score: null, scoreType: unavailable`。综合 query 通过 `--explain` 读取原始查询的 vec contribution.backendScore，不使用扩展查询分数、RRF 分或 `1 / rank`；严格 vsearch 使用 KBX 返回的向量分。纯全文 search、图 gsearch 和综合检索中的纯全文候选不虚构向量相似度。原 KBX 分数保存在 `rankingScore`，结果顺序、chunk/evidence 和 trace 均保留。WebClient 显示“向量相似度”与四位小数，不可用显示 `—`；相似度不代表答案正确率。
