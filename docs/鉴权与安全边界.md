# 鉴权与安全边界

## 当前状态

服务鉴权以 JWT 为主，支持本地公钥文件与 JWKS。resource ticket 用于保护 `/api/resource` 文件访问。CORS 由 `configs/runtime.yml` 的 `cors` 节控制。敏感配置通过 `.env` allowlist、真实 `configs/*.yml`、真实 `configs/*.pem` 或外部 Secret 注入，不提交仓库。

工具级文件和命令权限不在本文展开，见 [工具目录权限](工具目录权限.md)。

`platform_control` 使用显式 Tool 授权：Agent 在 `toolConfig.tools` 挂载后即可调用全部注册 operation，不再按 Agent 配置 profile/binding。动态 key 无需 Agent 配置声明，只有当前普通 native root run 可 set/unset；Skill 只负责教学，通过 `mustUseSkills` 临时加载或热重载 Skill 都不会替 Agent 挂载 Tool，也不会增加 MCP、Agent hostAccess 或 `accessLevel`。唯一的文件授权是 admission 为本次选中 Skill canonical 目录建立的 trusted read + readonly roots，不扩展到未选中目录或后续 run。

## 核心流程

```text
HTTP / WebSocket request
  -> token 提取
  -> 本地公钥或 JWKS 验签
  -> issuer 等声明校验
  -> handler
```

resource 访问在普通鉴权之外还可启用 ticket：

```text
GET /api/resource?file=...&t=...
  -> 校验 resource ticket
  -> 定位 AP_RUNTIME_CHATS_DIR 内资源
  -> 返回文件
```

浏览器可通过现有 `Authorization: Bearer ...` 或 `access_token` Cookie fetch `/api/resource`；显式 Bearer 优先，非法 Bearer 不会降级使用 Cookie。ChatScope 请求的 `file=<chatId>/<relativePath>` 继续支持 resource ticket；无认证主体时 ticket 必须与逻辑资源键 chatId 匹配，已有合法主体时仍执行当前用户与 active/archive chat 的所有权校验。路径穿越、错误 chatId、其他用户 chat、symlink escape 与内部 `.tools`/`.btw` 路径均拒绝。

`POST /api/resource/image/commit` 不接受 resource ticket，只沿用普通 Bearer/Cookie 主体。服务端重新读取 active Chat summary，拒绝 Team、归档 Chat、错误 `agentKey`、错误 `artifacts|references` 前缀、控制字符、编码 traversal、symlink escape 与 Artifact ID/URL 不一致；覆盖还必须通过 expected revision。客户端或 Desktop 已做过的检查不替代这些校验。

绝对路径请求必须同时提供 `chatId` 与 Bearer/Cookie 主体，resource ticket 永远不能授权。普通 Agent 可读取当前 Workspace 或进程启动时冻结的临时根；当前/其他 Chat 的绝对路径拒绝并要求改用 ChatScope，Team chat 拒绝全部绝对路径。Unix/macOS 临时根包含 `os.TempDir()` 与 canonical `/tmp`（macOS `/tmp`、`/private/tmp` 等价），Windows 只包含 `os.TempDir()`。服务端校验最终 canonical 目标，临时目录 symlink/junction 逃逸拒绝。真实 `/api/resource` 请求地址只属于客户端 adapter 的 HTTP 数据面，不是 Markdown 协议；Markdown 使用实际 Host 绝对路径，不使用 `@temp`。

## 约束与注意事项

- 本地公钥文件路径固定为 `configs/local-public-key.pem`，不提供 YAML 或环境变量覆盖。
- `auth.jwks-uri` 非空时走 JWKS 模式。
- WebSocket 鉴权复用 HTTP token 校验链路。
- JWT `exp` / `iat` 与 resource ticket payload `e` 是 token 内部 NumericDate（秒），不受普通 API epoch-milliseconds 字段约束。只有对 Desktop/WS 公开的 auth expiry 才映射为 `expiresAt` epoch milliseconds；缺少 `exp` 时省略该字段。
- provider `apiKey` 按明文字符串读取，不提供加密或解密机制。
- `runtimeConfig.env` 不通过 catalog API 回显。
- `platform_control` 永远禁止覆盖 `AP_AGENT_CONFIG_HOME`、`AP_WORKSPACE_DIR`、`AP_CHAT_DIR`、`AP_ACCESS_TOKEN` 及其大小写变体；PATH、shell init、动态加载器、语言启动参数、SSH askpass 等 hard deny key 也不能通过配置放宽，`deny-keys` 只能追加。
- run-env value 是可观测的普通 Tool 参数，会进入会话历史、trace 与导出，不得用于传递凭据或其他 Secret。当前有效运行状态只保存在 root run 的进程内 Scope，Platform 重启后不恢复；实现不得调用 `os.Setenv`，子进程内的 `export/set` 也不能反向影响 Platform。
- `security.explain` 只解释 operation 在当前 stage/root/team/run-env 状态下的可用性，以及 run-env key 和 read/write path 的实际决策，不修改策略。
